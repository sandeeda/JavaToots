01
Basic TPS & Little's Law
200 TPS means 200 transactions completed per second, sustained — not 200 requests sitting in a queue. Throughput, latency, and concurrency are locked together by Little's Law: concurrency = throughput × latency.
🚧

Toll booth analogy: Cars/sec through a toll plaza depends on BOTH how fast one booth processes a car (latency) AND how many booths are open (concurrency). One slow booth or too few booths — same result: low throughput.

Java
public class Main {
  public static void main(String[] args) {

    double targetTps = 200;            // transactions/sec we must sustain
    double avgLatencySeconds = 0.150; // 150ms average time per request

    // Little's Law:  L = λ × W
    // L = concurrency needed, λ = throughput (TPS), W = latency
    double requiredConcurrency = targetTps * avgLatencySeconds;

    System.out.println("Target throughput: " + targetTps + " TPS");
    System.out.println("Average latency:   " + (avgLatencySeconds * 1000) + " ms");
    System.out.println("Concurrency needed: " + requiredConcurrency + " in-flight requests");
  }
}
Output
Target throughput: 200.0 TPS Average latency: 150.0 ms Concurrency needed: 30.0 in-flight requests
💡

You cannot fix TPS by tuning only one of throughput, latency, or concurrency — they're mathematically locked together. Every later concept in this guide is really just "how do I supply enough concurrency without blowing up latency."

02
Basic Stateless Service Design
One instance can never sustain 200 TPS forever — you'll need N instances. If a server remembers "this user is logged in" in its own memory, the load balancer is forced to always route that user back to the same instance. That kills horizontal scaling.
👕

Coat check vs carrying your own coat: A coat-check ticket (session ID) only means something to the ONE coat-check counter that issued it. A JWT is more like a coat YOU keep wearing — any door in the building can verify it's yours just by looking, no memory required.

Java❌ Stateful
import org.springframework.web.bind.annotation.*;
import jakarta.servlet.http.HttpSession;

@RestController
public class StatefulLoginController {

  @PostMapping("/login")
  public String login(@RequestParam String username, HttpSession session) {
    session.setAttribute("username", username); // lives in THIS server's RAM
    return "Logged in as " + username;
  }

  @GetMapping("/whoami")
  public String whoAmI(HttpSession session) {
    return "You are: " + session.getAttribute("username");
    // next request lands on a DIFFERENT instance → that instance's
    // memory never saw this login → null / 401, randomly, half the time
  }
}
Java✅ Stateless
import org.springframework.web.bind.annotation.*;

@RestController
public class StatelessLoginController {

  private final JwtUtil jwtUtil; // see the JWT tutorial in this series

  public StatelessLoginController(JwtUtil jwtUtil) {
    this.jwtUtil = jwtUtil;
  }

  @PostMapping("/login")
  public String login(@RequestParam String username) {
    return jwtUtil.generateToken(username); // zero server-side memory
  }
  // every request re-proves identity via the token itself —
  // ANY instance, behind ANY load-balancer algorithm, can serve it
}
💡

No server-side session state is the single biggest enabler of horizontal scaling. It's also why JWT tutorial earlier in this series matters way beyond "just auth."

03
Basic Horizontal Scaling & Load Balancing
Once instances are stateless, a load balancer can spread 200 TPS across N of them. Round robin is simple but blind to load; least-connections adapts to slow instances; consistent hashing keeps the same client/key hitting the same instance (useful for cache locality).
🛒

Supermarket checkout lanes: Round robin = "next customer, next open lane" regardless of cart size. Least-connections = "go to the shortest line." A bad cashier (slow instance) gets fewer customers either way, but least-connections notices faster.

Java
import java.util.List;
import java.util.concurrent.atomic.AtomicInteger;

public class Main {

  static final List<String> servers = List.of("10.0.0.1:8080", "10.0.0.2:8080", "10.0.0.3:8080");
  static final AtomicInteger counter = new AtomicInteger(0); // thread-safe round-robin pointer

  static String nextServer() {
    int index = counter.getAndIncrement() % servers.size();
    return servers.get(index);
  }

  public static void main(String[] args) {
    for (int i=1; i<=6; i++) {
      System.out.println("Request " + i + " -> " + nextServer());
    }
    // Real load balancers (nginx, ALB, Envoy) do this PLUS health checks —
    // a server failing its health check drops out of "servers" automatically.
  }
}
Output
Request 1 -> 10.0.0.1:8080 Request 2 -> 10.0.0.2:8080 Request 3 -> 10.0.0.3:8080 Request 4 -> 10.0.0.1:8080 Request 5 -> 10.0.0.2:8080 Request 6 -> 10.0.0.3:8080
💡

Always provision for peak TPS, not average — a 200 TPS average with bursty traffic might hit 600 TPS for short windows. Capacity planned for the average will fall over during the burst.

04
Intermediate Thread Pool Sizing (Tomcat)
server.tomcat.threads.max caps how many requests Spring Boot handles concurrently. Sizing it bigger than your DB connection pool doesn't add capacity — it just means more threads sit blocked waiting for a free DB connection.
🍽

Tables vs kitchen staff: Seating 200 parties (threads) when your kitchen (DB pool) can only cook for 20 at once doesn't feed people faster — it just means 180 parties sit at their table doing nothing.

YAML
server:
  tomcat:
    threads:
      max: 200        # max concurrent requests Tomcat will accept
      min-spare: 20  # threads kept alive even when idle
    accept-count: 100 # requests queued once all 200 threads are busy
    max-connections: 8192
Java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Semaphore;
import java.util.concurrent.TimeUnit;

public class Main {
  public static void main(String[] args) throws InterruptedException {

    Semaphore dbConnections = new Semaphore(20);             // Hikari maximumPoolSize = 20
    ExecutorService tomcatThreads = Executors.newFixedThreadPool(200); // threads.max = 200

    long start = System.currentTimeMillis();
    for (int i=1; i<=200; i++) {
      tomcatThreads.submit(() -> {
        try {
          dbConnections.acquire(); // the other 180 threads just WAIT here
          try {
            Thread.sleep(50); // pretend DB query takes 50ms
          } finally {
            dbConnections.release();
          }
        } catch (InterruptedException e) {
          Thread.currentThread().interrupt();
        }
      });
    }

    tomcatThreads.shutdown();
    tomcatThreads.awaitTermination(30, TimeUnit.SECONDS);
    System.out.println("200 requests done in " + (System.currentTimeMillis() - start) + "ms");
  }
}
Output
200 requests done in ~500ms
💡

Size your thread pool around your slowest downstream dependency, not bigger "just in case." Extra threads beyond what the DB can serve just queue, and under real load that queueing turns into timeouts that mask the actual bottleneck.

05
Intermediate Database Connection Pooling (HikariCP)
Opening a DB connection means a TCP handshake plus authentication — too expensive to do per-request. A pool keeps a small set of long-lived connections reused across requests. Bigger is not better: an oversized pool causes contention on the database itself.
🔑

Shared meeting-room keys: Minting a brand-new key for every meeting wastes time. A small set of reusable keys, checked in and out, is faster — and handing out 500 keys for 5 rooms just causes a crowd at the door.

YAML
spring:
  datasource:
    url: jdbc:postgresql://db-host:5432/orders
    username: app_user
    password: ${DB_PASSWORD}
    hikari:
      maximum-pool-size: 20       # start small; raise only if metrics show queueing
      minimum-idle: 5
      connection-timeout: 3000    # ms to wait for a free connection before failing fast
      idle-timeout: 600000       # 10 min — close connections idle longer than this
      max-lifetime: 1800000      # 30 min — recycle connections periodically
      leak-detection-threshold: 5000 # warn if held > 5s without being returned
Java
import com.zaxxer.hikari.HikariConfig;
import com.zaxxer.hikari.HikariDataSource;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;

public class Main {
  public static void main(String[] args) throws SQLException {

    HikariConfig config = new HikariConfig();
    config.setJdbcUrl("jdbc:postgresql://db-host:5432/orders");
    config.setUsername("app_user");
    config.setPassword(System.getenv("DB_PASSWORD"));
    config.setMaximumPoolSize(20);

    HikariDataSource dataSource = new HikariDataSource(config);

    try (Connection conn = dataSource.getConnection();  // borrowed from the pool
         PreparedStatement stmt = conn.prepareStatement(
             "SELECT id, status FROM orders WHERE customer_id = ?")) {

      stmt.setLong(1, 42L);
      try (ResultSet rs = stmt.executeQuery()) {
        while (rs.next()) {
          System.out.println(rs.getLong("id") + " -> " + rs.getString("status"));
        }
      }
    } // connection is RETURNED to the pool here — not physically closed

    dataSource.close(); // only at application shutdown
  }
}
💡

try-with-resources on a pooled Connection returns it to the pool, it doesn't kill the TCP connection. Swallowing an exception and skipping the close is the #1 cause of pool exhaustion in production.

06
Intermediate Cache-Aside & the Thundering Herd
Cache-aside: check Redis first; on a miss, read the DB and populate the cache. Cache read-heavy, slow-to-compute, rarely-changing data. The trap: when a hot key expires, dozens of requests can miss at the same instant and all hammer the DB at once — a thundering herd.
🚰

Water cooler line: If everyone's bottle (cache entry) runs dry at the exact same moment, everyone rushes the one tap (the database) simultaneously.

Java
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.stereotype.Service;
import java.time.Duration;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.locks.ReentrantLock;

@Service
public class ProductPriceService {

  private final StringRedisTemplate redis;
  private final ProductRepository productRepository; // your DB layer

  // one lock PER product key — only one thread recomputes a given miss
  private final ConcurrentHashMap<Long, ReentrantLock> locks = new ConcurrentHashMap<>();

  public ProductPriceService(StringRedisTemplate redis, ProductRepository repo) {
    this.redis = redis;
    this.productRepository = repo;
  }

  public String getPrice(long productId) {
    String key = "price:" + productId;

    String cached = redis.opsForValue().get(key);
    if (cached != null) return cached; // HIT — sub-millisecond, no DB

    ReentrantLock lock = locks.computeIfAbsent(productId, id -> new ReentrantLock());
    lock.lock();
    try {
      // re-check — another thread may have filled it while we waited for the lock
      cached = redis.opsForValue().get(key);
      if (cached != null) return cached;

      String price = productRepository.findPriceById(productId); // the slow path

      long jitterSeconds = (long) (Math.random() * 10); // avoid synchronized expiry
      redis.opsForValue().set(key, price, Duration.ofSeconds(60 + jitterSeconds));

      return price;
    } finally {
      lock.unlock();
    }
  }
}
💡

Prevent the herd two ways: request coalescing (one thread refills, the rest wait and reuse the result) and jittered TTLs so millions of keys don't expire in the same second.

07
Intermediate Async / Non-Blocking I/O
In the thread-per-request model, one blocked thread = one wasted thread (see java-threads.html's Thread Pool card). Reactive/WebFlux releases the thread back to the pool while waiting on slow I/O — letting a handful of threads serve thousands of in-flight requests. It does nothing for CPU-bound work.
🍽

Waiter taking many orders vs one waiter per table: A good waiter takes order 2 while order 1 cooks. Reactive is that waiter. Blocking I/O is a waiter standing at one table, frozen, until the kitchen finishes.

Java❌ Blocking
import org.springframework.web.bind.annotation.*;
import org.springframework.web.client.RestTemplate;

@RestController
public class BlockingDashboardController {

  private final RestTemplate restTemplate = new RestTemplate();

  @GetMapping("/dashboard")
  public String dashboard() {
    String users  = restTemplate.getForObject("http://users-service/summary", String.class);  // ~100ms
    String orders = restTemplate.getForObject("http://orders-service/summary", String.class); // ~150ms
    String stats  = restTemplate.getForObject("http://stats-service/summary", String.class);  // ~120ms
    return users + orders + stats; // total ~370ms, ONE thread held the whole time
  }
}
Java✅ Reactive
import org.springframework.web.bind.annotation.*;
import org.springframework.web.reactive.function.client.WebClient;
import reactor.core.publisher.Mono;

@RestController
public class ReactiveDashboardController {

  private final WebClient webClient = WebClient.create();

  @GetMapping("/dashboard")
  public Mono<String> dashboard() {
    Mono<String> users  = webClient.get().uri("http://users-service/summary").retrieve().bodyToMono(String.class);
    Mono<String> orders = webClient.get().uri("http://orders-service/summary").retrieve().bodyToMono(String.class);
    Mono<String> stats  = webClient.get().uri("http://stats-service/summary").retrieve().bodyToMono(String.class);

    // all 3 fire concurrently; the event-loop thread is FREE while waiting
    return Mono.zip(users, orders, stats)
        .map(tuple -> tuple.getT1() + tuple.getT2() + tuple.getT3());
    // total ~150ms (the slowest call) — no thread was ever blocked waiting
  }
}
💡

Reactive wins when you fan out to many slow I/O calls per request. For CPU-bound work (encryption, image resizing) it adds complexity with zero throughput benefit — you still need real CPU cores, see Thread Pool in java-threads.html.

Intermediate Read Replicas & Read/Write Splitting
Most APIs are read-heavy. Routing writes to the primary and reads to one or more replicas multiplies read capacity almost for free. The tradeoff: replication lag — a replica can be milliseconds to seconds behind the primary.
📖

Library main desk vs branch reading rooms: New books (writes) are checked in at the main desk. Branches (replicas) get copies a little later — great for browsing, occasionally stale for "did my new book arrive yet."

Java
import org.springframework.jdbc.datasource.lookup.AbstractRoutingDataSource;
import org.springframework.transaction.support.TransactionSynchronizationManager;

public class ReadWriteRoutingDataSource extends AbstractRoutingDataSource {

  @Override
  protected Object determineCurrentLookupKey() {
    boolean readOnly = TransactionSynchronizationManager.isCurrentTransactionReadOnly();
    return readOnly ? "replica" : "primary";
  }
}

@Service
class OrderService {

  @Transactional(readOnly = true) // routed to a REPLICA — multiplies read capacity
  Order findOrder(long id) {
    return orderRepository.findById(id);
  }

  @Transactional // readOnly = false (default) — routed to the PRIMARY
  void placeOrder(Order order) {
    orderRepository.save(order);
  }
}
💡

Read-your-own-write gotcha: if a client calls placeOrder() then immediately calls findOrder(), the replica may not have caught up yet — the order "disappears" for a few hundred ms. Fix: read the just-saved object directly, or route the immediate follow-up read to the primary.

Advanced Sharding & the Hot Partition Problem
When even a primary + replicas can't keep up, split the data itself across multiple database instances by a shard key (e.g. customerId). Pick the key carelessly and you get a hot partition — one shard takes most of the live traffic while the others sit idle.
🗄️

Filing cabinets by last name A-M / N-Z: Works fine until half your customers are named "Smith" — one cabinet is jammed, the other gathers dust.

Java
public class Main {

  static final int SHARD_COUNT = 4; // 4 separate database instances/schemas

  static int shardFor(long customerId) {
    return (int) (Math.abs(customerId) % SHARD_COUNT); // naive modulo sharding
  }

  public static void main(String[] args) {
    long[] customerIds = { 101, 102, 103, 104, 105, 106, 107, 108 };
    for (long id : customerIds) {
      int shard = shardFor(id);
      System.out.println("Customer " + id + " -> shard " + shard + " (orders_db_" + shard + ")");
    }
    // ⚠️ HOT PARTITION RISK: sequential, recently-created customer IDs skew
    // most LIVE traffic onto 1-2 shards. Real systems hash the key first.
  }
}
Output
Customer 101 -> shard 1 (orders_db_1) Customer 102 -> shard 2 (orders_db_2) Customer 103 -> shard 3 (orders_db_3) Customer 104 -> shard 0 (orders_db_0) Customer 105 -> shard 1 (orders_db_1)
💡

Pick a shard key that distributes load over time, not just values over a range. Hash the key before modulo-ing, and monitor per-shard TPS so a hot partition is caught before it becomes an outage.

Advanced Rate Limiting (Token Bucket)
Rate limiting protects your 200 TPS budget from any single caller hogging it. Token bucket allows short bursts up to a capacity, then settles to a steady refill rate — the most common choice. Leaky bucket smooths to a constant rate; fixed window is simplest but lets two bursts straddle a window boundary.
Java
import java.util.concurrent.Executors;
import java.util.concurrent.ScheduledExecutorService;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicInteger;

public class TokenBucketRateLimiter {

  private final AtomicInteger tokens;
  private final int capacity;

  public TokenBucketRateLimiter(int capacity, int refillPerSecond) {
    this.capacity = capacity;
    this.tokens = new AtomicInteger(capacity);

    ScheduledExecutorService refiller = Executors.newSingleThreadScheduledExecutor();
    refiller.scheduleAtFixedRate(() ->
      tokens.updateAndGet(current -> Math.min(capacity, current + refillPerSecond)),
      1, 1, TimeUnit.SECONDS); // refill once per second
  }

  public boolean tryAcquire() {
    int current;
    do {
      current = tokens.get();
      if (current <= 0) return false; // bucket empty — reject
    } while (!tokens.compareAndSet(current, current - 1)); // CAS retry loop
    return true;
  }

  public static void main(String[] args) {
    TokenBucketRateLimiter limiter = new TokenBucketRateLimiter(5, 5); // burst of 5, refill 5/s

    for (int i=1; i<=8; i++) {
      System.out.println("Request " + i + " -> " + (limiter.tryAcquire() ? "ALLOWED" : "REJECTED (429)"));
    }
  }
}
Output
Request 1 -> ALLOWED Request 2 -> ALLOWED Request 3 -> ALLOWED Request 4 -> ALLOWED Request 5 -> ALLOWED Request 6 -> REJECTED (429) Request 7 -> REJECTED (429) Request 8 -> REJECTED (429)
💡

This AtomicInteger version only protects one JVM. Across multiple instances you need a shared store — Redis INCR + EXPIRE (or a Lua script for atomicity) so all instances share the same budget.

Advanced Backpressure & Load Shedding
When traffic exceeds 200 TPS capacity, an unbounded queue isn't resilience — it's a delayed outage: latency grows without limit until clients give up or the JVM runs out of memory. A bounded queue plus deliberate rejection (429/503) keeps p99 sane.
Java
import java.util.concurrent.*;

public class Main {
  public static void main(String[] args) {

    ThreadPoolExecutor pool = new ThreadPoolExecutor(
      20, 20,                              // core/max — fixed, matches DB capacity
      60, TimeUnit.SECONDS,
      new ArrayBlockingQueue<>(100),         // BOUNDED — not unbounded!
      new ThreadPoolExecutor.AbortPolicy()  // reject instead of queueing forever
    );

    for (int i=1; i<=200; i++) {
      int requestId = i;
      try {
        pool.execute(() -> {
          try { Thread.sleep(50); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        });
      } catch (RejectedExecutionException e) {
        System.out.println("Request " + requestId + " -> REJECTED (503), at capacity");
      }
    }

    pool.shutdown();
  }
}
💡

Rejecting fast at capacity beats queueing forever — by the time a request at the back of an unbounded queue gets served, the caller has often already timed out or retried, doubling your load.

Advanced Circuit Breakers & Bulkheads
A bulkhead gives each downstream dependency its own isolated thread pool, so one slow dependency can't exhaust the pool serving everything else. A circuit breaker stops calling a dependency that's clearly failing instead of piling up slow timeouts.
🚢

Ship bulkheads: Watertight compartments mean one hull breach floods one compartment, not the whole ship. One slow payment gateway shouldn't sink your entire API.

Java
import io.github.resilience4j.circuitbreaker.annotation.CircuitBreaker;
import io.github.resilience4j.bulkhead.annotation.Bulkhead;
import org.springframework.stereotype.Service;
import org.springframework.web.client.RestTemplate;

@Service
public class PaymentGatewayClient {

  private final RestTemplate restTemplate = new RestTemplate();

  @CircuitBreaker(name = "paymentGateway", fallbackMethod = "fallback")
  @Bulkhead(name = "paymentGateway") // isolated pool — only THIS dependency lives here
  public String charge(String orderId, double amount) {
    return restTemplate.postForObject(
        "https://payments.example.com/charge", amount, String.class);
  }

  private String fallback(String orderId, double amount, Throwable t) {
    // circuit OPEN or bulkhead full — fail FAST instead of a slow timeout
    return "PAYMENT_PENDING: will retry " + orderId;
  }
}
YAML
resilience4j:
  circuitbreaker:
    instances:
      paymentGateway:
        sliding-window-size: 20
        failure-rate-threshold: 50      # open if >=50% of last 20 calls failed
        wait-duration-in-open-state: 10s
  bulkhead:
    instances:
      paymentGateway:
        max-concurrent-calls: 10        # isolated capacity — caps blast radius
💡

Without a bulkhead, one slow dependency eventually consumes every thread in a shared pool — taking down requests that have nothing to do with the failing dependency. The circuit breaker stops wasting threads on calls very likely to fail anyway.

Advanced Idempotency Keys
At 200 TPS with real network conditions, timeouts and retries will happen — clients and load balancers retry POST/PUT calls automatically. Without an idempotency key, a retried "charge card" call double-charges the customer.
Java
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.web.bind.annotation.*;
import java.time.Duration;

@RestController
public class PaymentController {

  private final StringRedisTemplate redis;
  private final PaymentService paymentService;

  public PaymentController(StringRedisTemplate redis, PaymentService paymentService) {
    this.redis = redis;
    this.paymentService = paymentService;
  }

  @PostMapping("/payments")
  public String charge(@RequestHeader("Idempotency-Key") String key,
                        @RequestBody ChargeRequest request) {

    String resultKey = "idempotency:" + key;

    // SET ... NX — atomically succeeds only if the key does NOT already exist
    Boolean firstTime = redis.opsForValue().setIfAbsent(resultKey, "PROCESSING", Duration.ofHours(24));

    if (Boolean.FALSE.equals(firstTime)) {
      // this exact key already ran (or is running) — don't re-charge, return cached result
      String cachedResult = redis.opsForValue().get(resultKey);
      return cachedResult != null ? cachedResult : "PROCESSING";
    }

    String result = paymentService.charge(request); // the real side effect — runs ONCE
    redis.opsForValue().set(resultKey, result, Duration.ofHours(24));
    return result;
  }
}
💡

The client generates the idempotency key once per logical operation (a UUID is fine) and resends the same key on every retry of that operation — never a fresh key per retry attempt.

Every millisecond spent inside the synchronous request path eats directly into your Little's Law latency budget. Move non-critical-path work (emails, analytics, inventory sync) onto Kafka/RabbitMQ so the API does only the minimum needed to respond.

import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.web.bind.annotation.*;

@RestController
public class OrderController {

  private final OrderRepository orderRepository;
  private final KafkaTemplate<String, String> kafkaTemplate;

}

Advanced Write Optimization & the N+1 Problem
The N+1 query problem: an ORM lazily loads a related collection inside a loop, firing one extra query per row. Invisible with 1 row of test data, devastating at 200 TPS with real volume. Batching writes turns hundreds of round trips into one.
Java❌ N+1
List<Order> orders = orderRepository.findByCustomerId(customerId); // 1 query
for (Order order : orders) {
  System.out.println(order.getItems().size()); // lazy-loads items — 1 query EACH time!
}
// 50 orders = 51 queries. At 200 TPS that's a 50x multiplier on DB load.
Java✅ Fixed
@Query("SELECT DISTINCT o FROM Order o LEFT JOIN FETCH o.items WHERE o.customerId = :customerId")
List<Order> findByCustomerIdWithItems(@Param("customerId") Long customerId);
// 50 orders = 1 query, regardless of how many orders there are.
JavaBatch Writes
import com.zaxxer.hikari.HikariConfig;
import com.zaxxer.hikari.HikariDataSource;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.SQLException;
import java.sql.Timestamp;
import java.util.List;

public class Main {

  record AnalyticsEvent(long userId, String type, Timestamp timestamp) {}

  public static void main(String[] args) throws SQLException {

    HikariDataSource dataSource = buildDataSource(); // see concept 5 — HikariCP
    List<AnalyticsEvent> events = List.of(
        new AnalyticsEvent(1L, "page_view", new Timestamp(System.currentTimeMillis())),
        new AnalyticsEvent(2L, "click",     new Timestamp(System.currentTimeMillis()))
    ); // in production: 500+ events buffered client-side before flushing

    try (Connection conn = dataSource.getConnection();
         PreparedStatement stmt = conn.prepareStatement(
        "INSERT INTO analytics_events (user_id, event_type, ts) VALUES (?, ?, ?)")) {

      for (AnalyticsEvent e : events) {
        stmt.setLong(1, e.userId());
        stmt.setString(2, e.type());
        stmt.setTimestamp(3, e.timestamp());
        stmt.addBatch(); // buffered, not sent yet
      }
      stmt.executeBatch(); // ONE round trip for all 500 inserts, not 500
    }

    dataSource.close();
  }

  private static HikariDataSource buildDataSource() {
    HikariConfig config = new HikariConfig();
    config.setJdbcUrl("jdbc:postgresql://db-host:5432/analytics");
    config.setUsername("app_user");
    config.setPassword(System.getenv("DB_PASSWORD"));
    return new HikariDataSource(config);
  }
}

Advanced Observability: p50/p95/p99
Average latency hides outliers. At 200 TPS, a "rare" 1% slow path isn't rare at all — it happens roughly twice every second. p95/p99 reveal that constant background problem; average makes it invisible.

  }

Advanced Capacity Planning: A Worked Example
Putting concepts 1, 5, and 6 together: given a 200 TPS target and 150ms p95 DB latency, work out the Hikari pool size and Tomcat thread count — and see exactly how much a 90% cache hit rate shrinks both.
Java
public class Main {
  public static void main(String[] args) {

    double targetTps = 200;
    double dbLatencySeconds = 0.150;       // p95 latency of a DB-hitting request
    double cacheHitLatencySeconds = 0.005; // 5ms for a Redis cache hit

    // Step 1 — Little's Law if EVERY request hit the DB (no cache at all)
    double worstCaseConcurrency = targetTps * dbLatencySeconds;
    System.out.println("No cache: need " + worstCaseConcurrency + " DB connections");

    // Step 2 — only cache MISSES hit the DB; assume a 90% hit rate
    double cacheHitRate = 0.90;
    double missTps = targetTps * (1 - cacheHitRate); // 20 TPS actually reach the DB
    double dbConcurrencyNeeded = missTps * dbLatencySeconds;
    System.out.println("With 90% cache hit rate: " + missTps + " TPS hit the DB");
    System.out.println("Hikari maximum-pool-size needed: ~" + Math.ceil(dbConcurrencyNeeded));

    // Step 3 — Tomcat threads must cover BOTH fast cache hits and slow misses
    double hitConcurrency = (targetTps * cacheHitRate) * cacheHitLatencySeconds;
    double totalConcurrency = hitConcurrency + dbConcurrencyNeeded;
    System.out.println("server.tomcat.threads.max needed: ~" + Math.ceil(totalConcurrency * 1.5) + " (50% burst headroom)");
  }
}
Output
No cache: need 30.0 DB connections With 90% cache hit rate: 20.0 TPS hit the DB Hikari maximum-pool-size needed: ~3.0 server.tomcat.threads.max needed: ~6.0 (50% burst headroom)
💡

A 90% cache hit rate didn't just "help a bit" — it cut the required DB connection pool by 10x (30 → 3). DB connections are usually the scarcest resource in the whole system, which is exactly why caching strategy (concept 6) is so high-leverage.

Advanced Senior Interview FAQ
A crib sheet wiring every concept above into the answers a senior/staff interview actually wants to hear.
Notes
// Q: "How would you design an API to handle 200 TPS?"
// A: Start from Little's Law (concept 1) to size concurrency. Make the
//    service stateless (2) so it scales horizontally behind a load balancer (3).
//    Size the thread pool around the DB pool, not bigger (4, 5). Cache
//    aggressively to multiply effective capacity (6, 17). Use async I/O only
//    where it's genuinely I/O-bound (7). Scale reads via replicas (8), and the
//    DB itself via sharding once replicas aren't enough (9). Protect the
//    budget with rate limiting (10) and shed load deliberately past capacity
//    (11). Isolate failure domains with bulkheads/circuit breakers (12).
//    Make retries safe with idempotency keys (13). Move non-critical work
//    off the request path via queues (14). Eliminate N+1s and batch writes
//    (15). Measure p99, not average (16).

// Q: "What's the difference between throughput and latency, and why do both matter?"
// A: Throughput = work completed per second (TPS). Latency = time for ONE unit
//    of work. Little's Law (concept 1) ties them together via concurrency —
//    you cannot raise throughput without either lowering latency or raising
//    concurrency. A system can have great average latency and terrible
//    throughput (low concurrency) or vice versa.

// Q: "How do you find the bottleneck when TPS is too low?"
// A: Measure concurrency at each layer (Tomcat threads in-use, Hikari
//    active connections, downstream call latency p99). Whichever layer is
//    saturated first — threads waiting on a smaller resource (concept 4) —
//    is the bottleneck. Don't guess; measure each tier independently.

// Q: "What's a thundering herd and how do you prevent it?"
// A: Many requests miss the cache at the EXACT same instant (concept 6),
//    usually because a hot key expired, and all of them hit the DB at once.
//    Prevent it with request coalescing (one thread refills, others wait) and
//    jittered TTLs so keys don't expire in lockstep.
