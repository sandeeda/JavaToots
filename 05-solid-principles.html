SOLID
Why these five rules exist
Coined by Robert C. "Uncle Bob" Martin — five rules for code that survives change without rotting

SOLID isn't five unrelated rules — it's one goal (low coupling, high cohesion, code that's easy to change without breaking unrelated things) approached from five angles: how big a class should be (S), how to add behaviour without editing existing code (O), how subclasses must behave (L), how interfaces should be shaped (I), and which direction dependencies should point (D). Every pattern in the design-patterns.html tutorial in this series is, underneath, a tool for satisfying one of these. Strategy, Decorator, and Observer all exist to satisfy OCP — they let you add new behaviour by adding a new class, not editing an existing one. Dependency Inversion is the principle that makes Spring's entire IoC container worth using: every @Autowired interface field is DIP in action.

🎤 Senior interview questions
Give an example of violating SRP and how you'd refactor it.
A UserService.register() that validates input, hashes the password, saves to the DB, sends a welcome email, and writes an audit log all in one method. Four reasons to change (validation rules, hashing algorithm, persistence, email provider) means four ways this class breaks. Refactor by extracting UserValidator, PasswordEncoder (already exists in Spring Security), EmailService, and AuditLogger, then have UserService orchestrate them.
What's the difference between an LSP violation and just "bad inheritance"?
They're the same thing described two ways. LSP gives you the precise test: can every caller of the base type use any subtype without knowing or caring which one it got, and without anything breaking? If a subclass overrides a method to throw, return null where the base never would, or narrow accepted inputs, callers written against the base contract break — that's the LSP violation, and it's always rooted in forcing an inheritance relationship that doesn't actually hold ("a Penguin is-a Bird, but can't fly()").
How does dependency injection relate to DIP?
DIP is the principle; DI is one mechanism for achieving it. DIP says depend on abstractions. DI is the pattern of having something external (you, a factory, or a framework like Spring) hand you that abstraction's implementation instead of you constructing it yourself with new. Spring's whole IoC container exists to automate DI at scale — which is why "Spring is just DIP as a framework" is a fair one-line description.
Can you over-apply these principles — give an example of premature abstraction?
Yes — creating an interface for every single class "in case we need a second implementation someday" (YAGNI violation), or splitting a 20-line class into five 4-line classes because each method is "technically" a different responsibility. SRP means one reason to change at the level the business actually changes things, not one method per class. If you've never needed a second PaymentStrategy implementation and never will, the interface is ceremony, not design.
PRINCIPLE 01
Single Responsibility
A class should have one reason to change.
CohesionAsked in every interview

🔧 The Swiss Army Knife Problem

A Swiss Army knife does ten things passably. A chef does one thing — cooking — extremely well, and when their knife breaks, only the knife needs fixing. A class that validates, persists, emails, AND logs is a Swiss Army knife: a change to the email provider risks breaking persistence by accident, because it's all tangled in one place.

⚠️ The Problem Without It

UserService.register() validates the email format, hashes the password, saves the user, sends a welcome email, and writes an audit entry — all in one 80-line method. Four unrelated teams (security, DB, marketing, compliance) now all have a reason to touch this one file, and a typo in the email template can fail a unit test for password hashing.

"A class should have one reason to change — bundle unrelated responsibilities together and a change to one breaks, or at least re-tests, all the others."
Java❌ Before — one class, four jobs
public class UserService {

    public void register(String email, String rawPassword) {
        // 1. validation
        if (!email.contains("@")) throw new IllegalArgumentException("bad email");

        // 2. hashing
        String hashed = Integer.toHexString(rawPassword.hashCode()); // pretend hash

        // 3. persistence
        System.out.println("INSERT INTO users(email, password) VALUES (" + email + ", " + hashed + ")");

        // 4. notification
        System.out.println("Sending welcome email to " + email);

        // 5. audit
        System.out.println("AUDIT: user registered -> " + email);
    }

    public static void main(String[] args) {
        new UserService().register("sandeep@email.com", "hunter2");
    }
}
Java✅ After — one job each, one orchestrator
public class UserValidator {
    public void validate(String email) {
        if (!email.contains("@")) throw new IllegalArgumentException("bad email");
    }
}

public class PasswordHasher {
    public String hash(String rawPassword) {
        return Integer.toHexString(rawPassword.hashCode()); // pretend hash
    }
}

public class UserRepository {
    public void save(String email, String hashedPassword) {
        System.out.println("INSERT INTO users(email, password) VALUES (" + email + ", " + hashedPassword + ")");
    }
}

public class EmailService {
    public void sendWelcome(String email) {
        System.out.println("Sending welcome email to " + email);
    }
}

public class AuditLogger {
    public void log(String event) {
        System.out.println("AUDIT: " + event);
    }
}

// Now this is the ONLY class with the reason-to-change "how does registration flow"
public class UserService {
    private final UserValidator validator = new UserValidator();
    private final PasswordHasher hasher = new PasswordHasher();
    private final UserRepository repo = new UserRepository();
    private final EmailService email = new EmailService();
    private final AuditLogger audit = new AuditLogger();

    public void register(String userEmail, String rawPassword) {
        validator.validate(userEmail);
        String hashed = hasher.hash(rawPassword);
        repo.save(userEmail, hashed);
        email.sendWelcome(userEmail);
        audit.log("user registered -> " + userEmail);
    }

    public static void main(String[] args) {
        new UserService().register("sandeep@email.com", "hunter2");
    }
}
⚠️ Over-applying SRP: splitting a 15-line class into five 3-line classes because each method is "technically" different isn't SRP, it's ceremony. SRP is about reasons the business changes things, not about method count.

🌱 Layered Spring beans ARE SRP

The classic Controller → Service → Repository layering is SRP applied at the architecture level: the controller's only job is HTTP translation, the service's only job is business rules, the repository's only job is persistence.

JavaSpring — each bean, one job
@RestController
public class UserController {     // job: HTTP in/out only
    private final UserService userService;
    UserController(UserService s) { this.userService = s; }

    @PostMapping("/users")
    public void register(@RequestBody RegisterRequest req) {
        userService.register(req.email(), req.password());
    }
}

@Service
public class UserService {        // job: orchestrate the business rule
    private final PasswordEncoder encoder;     // hashing's job, not ours
    private final UserRepository repo;       // persistence's job, not ours
    private final ApplicationEventPublisher events; // notification's job, not ours
    // constructor injection omitted for brevity

    public void register(String email, String rawPassword) {
        repo.save(new User(email, encoder.encode(rawPassword)));
        events.publishEvent(new UserRegisteredEvent(email)); // EmailService listens elsewhere
    }
}
PRINCIPLE 02
Open/Closed
Open for extension, closed for modification.
ExtensibilityPairs with Strategy

🔌 The Power Strip

A power strip is closed — you never re-wire its internals — but open for extension: plug in any new device that fits the socket shape (the interface). You never modify the strip itself to support a new lamp.

⚠️ The Problem Without It

A switch (paymentType) block handling STRIPE and PAYPAL. Adding Razorpay means opening this already-tested, already-deployed method and editing it — risking breaking Stripe and PayPal while you're in there.

"You should be able to add new behaviour by adding new code, not by editing code that already works and is already tested."
Java❌ Before — must edit this method for every new type
public class PaymentProcessor {
    public void pay(String type, double amount) {
        if (type.equals("STRIPE")) {
            System.out.println("Stripe: charging $" + amount);
        } else if (type.equals("PAYPAL")) {
            System.out.println("PayPal: charging $" + amount);
        }
        // adding Razorpay means editing THIS method again
    }

    public static void main(String[] args) {
        new PaymentProcessor().pay("STRIPE", 99.99);
    }
}
Java✅ After — new provider = new class, zero edits
interface PaymentStrategy {
    void pay(double amount);
}
class StripePayment implements PaymentStrategy {
    public void pay(double amount) { System.out.println("Stripe: charging $" + amount); }
}
class PayPalPayment implements PaymentStrategy {
    public void pay(double amount) { System.out.println("PayPal: charging $" + amount); }
}
// Adding Razorpay later = a NEW class. PaymentProcessor below never changes again.
class RazorpayPayment implements PaymentStrategy {
    public void pay(double amount) { System.out.println("Razorpay: charging $" + amount); }
}

public class PaymentProcessor {
    private final PaymentStrategy strategy;
    PaymentProcessor(PaymentStrategy strategy) { this.strategy = strategy; }

    public void pay(double amount) { strategy.pay(amount); } // closed — never edited again

    public static void main(String[] args) {
        new PaymentProcessor(new RazorpayPayment()).pay(49.99);
    }
}
⚠️ Over-applying OCP: wrapping every single method behind an interface "for future extension" before a second implementation is ever needed is speculative generality (YAGNI). Apply OCP where change is likely and recurring (payment providers, notification channels) — not everywhere.

🌱 Strategy beans via Spring DI = zero if/else, ever

Register each strategy as a named bean. Spring auto-collects every implementation into a Map<String, X> keyed by bean name — see the Strategy pattern panel in design-patterns.html for the full walkthrough.

JavaSpring — extension without modification
@Service("razorpay") // adding this class is the ENTIRE change required
public class RazorpayPayment implements PaymentStrategy { /* ... */ }

@Service
public class CheckoutService {
    @Autowired Map<String, PaymentStrategy> strategies; // CheckoutService is never edited again

    public void checkout(String provider, double amount) {
        strategies.get(provider).pay(amount);
    }
}
PRINCIPLE 03
Liskov Substitution
Subtypes must be substitutable for their base type without surprises.
Inheritance"Penguin can't fly" question

🐧 The Penguin Problem

Biologically, a Penguin IS a Bird. But if your Bird class has fly(), and Penguin extends Bird, every piece of code written against "any Bird can fly()" now silently breaks for penguins. The taxonomy was right; the code contract was wrong.

⚠️ The Problem Without It

A ReadOnlyRepository extends Repository that overrides save() to throw new UnsupportedOperationException(). Any generic code that does repositories.forEach(r -> r.save(x)) compiles fine and then blows up at runtime — only for the one subtype nobody remembered was special.

"If S is a subtype of T, you must be able to replace any T with an S and the program should keep working — same inputs accepted, no stronger preconditions, no weaker guarantees."
Java❌ Before — a subtype that lies about its contract
public abstract class Repository {
    public abstract void save(String record);
    public abstract String findById(String id);
}

public class ReadOnlyArchiveRepository extends Repository {
    @Override
    public void save(String record) {
        throw new UnsupportedOperationException("archive is read-only"); // breaks the base contract
    }
    @Override
    public String findById(String id) { return "archived-record-" + id; }
}

public class Main {
    static void backupAll(Repository[] repos, String record) {
        for (Repository r : repos) r.save(record); // blows up — but only on SOME repos
    }

    public static void main(String[] args) {
        Repository[] repos = { new ReadOnlyArchiveRepository() };
        backupAll(repos, "new entry"); // throws UnsupportedOperationException at runtime
    }
}
Java✅ After — split the contract instead of faking it
public interface ReadableRepository {
    String findById(String id);
}
public interface WritableRepository extends ReadableRepository {
    void save(String record);
}

// archive only promises what it can actually do — no lie, no surprise
public class ReadOnlyArchiveRepository implements ReadableRepository {
    @Override
    public String findById(String id) { return "archived-record-" + id; }
}
public class SqlRepository implements WritableRepository {
    @Override
    public void save(String record) { System.out.println("INSERT: " + record); }
    @Override
    public String findById(String id) { return "row-" + id; }
}

public class Main {
    // the compiler now PREVENTS the bug — you literally cannot call save() on a ReadableRepository
    static void backupAll(WritableRepository[] repos, String record) {
        for (WritableRepository r : repos) r.save(record);
    }

    public static void main(String[] args) {
        backupAll(new WritableRepository[]{ new SqlRepository() }, "new entry");
    }
}
⚠️ Over-applying LSP: creating a brand-new interface for every minor behavioural difference leads to interface explosion. Split only when callers actually need to treat the types differently — if nobody ever calls save() polymorphically across both, the single class with a documented limitation may be simpler.

🌱 Spring Data's interface hierarchy is built around this

CrudRepository, PagingAndSortingRepository, and read-only projections in Spring Data exist specifically so you only expose the capabilities a given repository actually supports — instead of one giant interface every implementation half-honours.

JavaSpring Data — honest capability interfaces
// A reporting repository that should NEVER allow writes —
// don't extend CrudRepository and override save() to throw.
// Extend only the read-side interface instead:
public interface OrderReportRepository
        extends Repository<Order, Long> {
    List<Order> findByStatus(String status); // read-only, no save() exists to misuse
}
PRINCIPLE 04
Interface Segregation
Don't force a class to implement methods it has no use for.
Interface design"Fat interface" question

🍽️ The Restaurant Menu

A diner-only menu lists breakfast, lunch, AND dinner on one page even at 8am — most of it is irrelevant noise to today's customer. A well-segmented menu hands you just the breakfast card. Interfaces work the same way: a fat interface forces every implementer to scan past methods that don't apply to them.

⚠️ The Problem Without It

A Worker interface with work(), eat(), and sleep(). A RobotWorker must implement all three to compile — but a robot doesn't eat or sleep, so those methods become empty stubs or throw exceptions, which is itself an LSP violation born from an ISP mistake.

"No class should be forced to depend on methods it doesn't use — split fat interfaces into small, focused ones."
Java❌ Before — one fat interface, forced stubs
interface Worker {
    void work();
    void eat();
    void sleep();
}

class HumanWorker implements Worker {
    public void work()  { System.out.println("Coding..."); }
    public void eat()   { System.out.println("Lunch break"); }
    public void sleep() { System.out.println("Sleeping"); }
}

class RobotWorker implements Worker {
    public void work()  { System.out.println("Welding..."); }
    public void eat()   { throw new UnsupportedOperationException("robots don't eat"); } // forced, useless
    public void sleep() { throw new UnsupportedOperationException("robots don't sleep"); }
}

public class Main {
    public static void main(String[] args) {
        Worker r = new RobotWorker();
        r.work();
        r.eat(); // throws — any generic "send everyone to lunch" loop crashes here
    }
}
Java✅ After — small, role-specific interfaces
interface Workable { void work(); }
interface Eatable   { void eat();  }
interface Sleepable { void sleep(); }

// implements only what actually applies — no stubs, no surprise exceptions
class HumanWorker implements Workable, Eatable, Sleepable {
    public void work()  { System.out.println("Coding..."); }
    public void eat()   { System.out.println("Lunch break"); }
    public void sleep() { System.out.println("Sleeping"); }
}

class RobotWorker implements Workable { // honestly only does ONE of the three things
    public void work() { System.out.println("Welding..."); }
}

public class Main {
    static void lunchBreak(Eatable[] eaters) {
        for (Eatable e : eaters) e.eat(); // a RobotWorker can't even be passed here — compiler enforces it
    }
    public static void main(String[] args) {
        lunchBreak(new Eatable[]{ new HumanWorker() });
    }
}
⚠️ Over-applying ISP: splitting every interface into single-method fragments "for purity" makes call sites depend on five tiny interfaces instead of one cohesive one. Group methods that are always used together by the same callers — segregate by actual usage pattern, not by method count.

🌱 Spring Data's Repository family is ISP by design

Repository (marker, no methods), CrudRepository (adds save/find/delete), PagingAndSortingRepository (adds paging) — each layer adds capability, so you pick the smallest interface your class actually needs instead of inheriting a fat one.

JavaSpring Data — pick the smallest interface you need
// Needs paging? Extend the interface that has it.
public interface OrderRepository
        extends PagingAndSortingRepository<Order, Long> {
    List<Order> findByStatus(String status);
}

// Only ever reads, never writes? Don't pull in CrudRepository's save()/delete() at all.
public interface OrderReadRepository
        extends Repository<Order, Long> {
    Optional<Order> findById(Long id);
}
PRINCIPLE 05
Dependency Inversion
Depend on abstractions, not on concrete implementations.
DecouplingWhy Spring DI exists

🔌 The Wall Socket

A lamp doesn't wire itself directly into the power station. It plugs into a standard socket — an abstraction. Swap the power source behind the wall (grid, generator, solar) and the lamp never knows or cares. If the lamp were hard-wired to one specific generator, replacing it would mean re-wiring the lamp itself.

⚠️ The Problem Without It

OrderService does private MySqlOrderRepository repo = new MySqlOrderRepository(); directly inside it. You cannot unit-test OrderService without a real MySQL connection, and switching databases means editing OrderService itself — the high-level business logic is now welded to a low-level storage detail.

"High-level modules shouldn't depend on low-level modules — both should depend on an abstraction, and that abstraction shouldn't depend on the details."
Java❌ Before — high-level class wired to a concrete low-level class
public class MySqlOrderRepository {
    public void save(String order) { System.out.println("MySQL INSERT: " + order); }
}

public class OrderService {
    private final MySqlOrderRepository repo = new MySqlOrderRepository(); // welded — untestable

    public void placeOrder(String order) { repo.save(order); }

    public static void main(String[] args) {
        new OrderService().placeOrder("ORD-1001");
        // to unit test placeOrder() you need a REAL MySQL connection — no way around it
    }
}
Java✅ After — depend on the interface, get the implementation handed to you
public interface OrderRepository {
    void save(String order);
}
public class MySqlOrderRepository implements OrderRepository {
    @Override
    public void save(String order) { System.out.println("MySQL INSERT: " + order); }
}
// a fake for tests — no real DB needed, possible ONLY because OrderService depends on the interface
public class InMemoryOrderRepository implements OrderRepository {
    private final List<String> saved = new ArrayList<>();
    @Override
    public void save(String order) { saved.add(order); System.out.println("in-memory save: " + order); }
}

public class OrderService {
    private final OrderRepository repo; // depends on the abstraction, not the detail
    OrderService(OrderRepository repo) { this.repo = repo; } // handed in, not constructed

    public void placeOrder(String order) { repo.save(order); }

    public static void main(String[] args) {
        new OrderService(new InMemoryOrderRepository()).placeOrder("ORD-1001"); // no DB needed
        new OrderService(new MySqlOrderRepository()).placeOrder("ORD-1002");   // real DB in prod
    }
}
⚠️ Over-applying DIP: introducing an interface for a class that will only ever have one implementation forever (e.g. a math utility class) adds indirection with zero payoff. DIP earns its keep when you actually need to swap implementations — for tests, for environments, or for providers.

🌱 DIP is the whole reason Spring's IoC container exists

Constructor injection of an interface field, with Spring deciding which @Bean satisfies it at startup, is DIP automated. You never write new MySqlOrderRepository() anywhere in business code — Spring wires the concrete implementation in from the outside.

JavaSpring — DIP via constructor injection
@Repository
public class MySqlOrderRepository implements OrderRepository { /* ... */ }

@Service
public class OrderService {
    private final OrderRepository repo; // the field type is the INTERFACE

    // Spring sees one bean implementing OrderRepository and injects it here —
    // swap @Profile("test") to InMemoryOrderRepository and OrderService never changes
    public OrderService(OrderRepository repo) { this.repo = repo; }

    public void placeOrder(String order) { repo.save(order); }
}
