01
Basic Collection Hierarchy
Every collection class implements one of four root interfaces: List (ordered, duplicates allowed), Set (no duplicates), Queue (FIFO/priority processing), or Map (key→value, not technically a Collection but part of the framework).
📚

Library shelves: A List is a numbered shelf (order matters, can repeat). A Set is a club roster (no member twice). A Map is a card catalog (lookup by title, not position).

Java
import java.util.*;

public class Main {
  public static void main(String[] args) {
    List<String> list = new ArrayList<>(); // ordered, allows duplicates
    list.add("a"); list.add("a"); // "a" twice — fine

    Set<String> set = new HashSet<>();   // no order guarantee, no duplicates
    set.add("a"); set.add("a");   // second "a" silently ignored

    Map<String,Integer> map = new HashMap<>(); // key→value lookup
    map.put("a", 1);

    System.out.println("list="+list.size()+" set="+set.size()+" map="+map.size());
  }
}
Output
list=2 set=1 map=1
💡

Map is NOT a Collection in the type hierarchy — it's a sibling interface. Everything else (List/Set/Queue) extends Collection.

02
Basic ArrayList Internals
Backed by a plain resizable array. get(i) is O(1) — direct index access. When it's full, Java allocates a NEW array at 1.5× the size and copies everything over — an O(n) operation that happens occasionally, not every add.
📦

Parking garage: Numbered spots side by side. Park in spot 5 instantly (O(1)). Garage full? Build a bigger garage next door and move every car (O(n), rare).

Java
import java.util.*;

public class Main {
  public static void main(String[] args) {
    List<Integer> nums = new ArrayList<>(); // default capacity 10 internally

    for (int i=0; i<15; i++) nums.add(i); // triggers a resize once we pass 10

    System.out.println(nums.get(12));   // O(1) — direct array index
    nums.add(0, 99);            // O(n) — shifts every element right by one
    System.out.println(nums.get(0));    // 99
  }
}
💡

get(i)/set(i,v) are O(1). add(i,v)/remove(i) in the middle are O(n) because elements must shift. Vector and Stack work the same way but synchronize every method — avoid them; use ArrayList + explicit locking, or Collections.synchronizedList(), or a concurrent collection instead.

03
Basic LinkedList
A doubly linked list — every element is a node holding a value plus pointers to the previous and next node. get(i) is O(n) (must walk from one end), but adding/removing at the head or tail is O(1) since no shifting is needed.
🚃

Train carriages: Each carriage only knows its neighbours. Adding a carriage at the front/back is instant. Reaching carriage #50 means walking through 49 carriages first.

Java
import java.util.*;

public class Main {
  public static void main(String[] args) {
    LinkedList<String> queue = new LinkedList<>();
    queue.addLast("order-1"); // O(1) — just relinks the tail pointer
    queue.addLast("order-2");
    queue.addFirst("order-0"); // O(1) — just relinks the head pointer

    while (!queue.isEmpty()) {
      System.out.println("Processing " + queue.removeFirst()); // O(1)
    }
  }
}
Output
Processing order-0 Processing order-1 Processing order-2
💡

The common belief "LinkedList is faster for inserts" is only true at the head/tail. For random-access reads or middle inserts, ArrayList usually wins even in theory-favoring-LinkedList cases, because array memory is cache-friendly and linked nodes are scattered across the heap. Reach for ArrayDeque over LinkedList for queue/stack use today (see concept 10).

04
Basic equals() & hashCode() Contract
The rule: if two objects are equal() they MUST have the same hashCode(). Break this and HashSet/HashMap silently store "duplicate" entries or fail to find things that should match.
Java
import java.util.*;

class Point {
  final int x, y;
  Point(int x, int y) { this.x = x; this.y = y; }

  // ❌ BROKEN — only overrides equals(), not hashCode()
  @Override
  public boolean equals(Object o) {
    if (!(o instanceof Point p)) return false;
    return x == p.x && y == p.y;
  }
  // no hashCode() override → uses Object's identity hash → BUG
}

public class Main {
  public static void main(String[] args) {
    Set<Point> seen = new HashSet<>();
    seen.add(new Point(1,1));
    boolean hasIt = seen.contains(new Point(1,1)); // expect true...
    System.out.println(hasIt); // prints false! different hashCode = different bucket
  }
}
Output (the bug)
false
💡

Always generate both together: Objects.equals() + Objects.hash(x, y), or let your IDE/record generate them. Java records (record Point(int x, int y) {}) give you a correct equals/hashCode pair for free.

05
Basic HashSet
Backed internally by a HashMap<E, Object> (the value is a dummy constant). add()/contains()/remove() are all O(1) average case because the element's hashCode() tells it exactly which bucket to check — no scanning the whole collection.
Java
import java.util.*;

public class Main {
  public static void main(String[] args) {
    Set<String> visited = new HashSet<>();

    String[] pages = {"/home", "/cart", "/home", "/checkout"};
    for (String p : pages) {
      if (!visited.add(p)) { // add() returns false if already present
        System.out.println("Repeat visit: " + p);
      }
    }
    System.out.println("Unique pages: " + visited.size());
  }
}
Output
Repeat visit: /home Unique pages: 3
💡

HashSet gives zero ordering guarantee — iteration order can change between runs. If you need O(1) lookups AND insertion order, use LinkedHashSet (next card).

06
Intermediate LinkedHashSet & TreeSet
LinkedHashSet = HashSet + a linked list tracking insertion order, so iteration is predictable. TreeSet keeps elements sorted at all times (via a red-black tree) using Comparable or a supplied Comparator — O(log n) instead of O(1), but you get ordering and range queries for free.
Java
import java.util.*;

public class Main {
  public static void main(String[] args) {
    Set<String> insertionOrder = new LinkedHashSet<>();
    insertionOrder.add("banana"); insertionOrder.add("apple"); insertionOrder.add("cherry");
    System.out.println(insertionOrder); // [banana, apple, cherry] — exact insert order

    TreeSet<String> sorted = new TreeSet<>(insertionOrder);
    System.out.println(sorted); // [apple, banana, cherry] — always alphabetical

    System.out.println(sorted.floor("banana"));  // banana — largest element <= "banana"
    System.out.println(sorted.higher("banana")); // cherry — smallest element > "banana"
  }
}
Output
[banana, apple, cherry] [apple, banana, cherry] banana cherry
💡

Pick by need: HashSet = fastest, no order. LinkedHashSet = fast + insertion order. TreeSet = slower (O(log n)) but always sorted, plus floor/ceiling/higher/lower range methods (NavigableSet).

07
Intermediate HashMap Internals
A HashMap is an array of buckets. key.hashCode() picks the bucket index. Multiple keys landing in the same bucket form a small linked list (a collision) — or, since Java 8, a red-black tree once a bucket has 8+ entries, turning worst-case O(n) lookups into O(log n). When the map is ~75% full (the load factor), it doubles its bucket array and rehashes everything.
📮

Post office boxes: Your hashCode picks which box your mail goes in. Two people can hash to the same box (collision) — the clerk just keeps a small list inside that box and checks names with equals().

Java
import java.util.*;

public class Main {
  public static void main(String[] args) {
    Map<String,Integer> inventory = new HashMap<>(16, 0.75f); // initial capacity 16, load factor 0.75

    inventory.put("widget", 100);
    inventory.merge("widget", -5, Integer::sum); // atomic-looking update: 100 + (-5) = 95
    inventory.computeIfAbsent("gadget", k -> 0);    // inserts 0 only if "gadget" missing

    for (Map.Entry<String,Integer> e : inventory.entrySet())
      System.out.println(e.getKey() + " = " + e.getValue());
  }
}
💡

A bad/constant hashCode() degrades a HashMap into a linked list — every operation becomes O(n). This is also why mutable keys are dangerous: change a key's fields after insertion and its hashCode changes, so get() can never find it again — it's looking in the wrong bucket.

Intermediate LinkedHashMap & LRU Cache
LinkedHashMap adds a doubly linked list on top of HashMap to track order. Pass accessOrder=true to its constructor and every get() moves that entry to the end — combine that with overriding removeEldestEntry() and you get a working LRU cache in about 10 lines.
Java
import java.util.*;

class LruCache<K,V> extends LinkedHashMap<K,V> {
  private final int capacity;

  LruCache(int capacity) {
    super(16, 0.75f, true); // true = order by ACCESS, not insertion
    this.capacity = capacity;
  }

  @Override
  protected boolean removeEldestEntry(Map.Entry<K,V> eldest) {
    return size() > capacity; // evict the least-recently-used entry once over capacity
  }
}

public class Main {
  public static void main(String[] args) {
    LruCache<Integer,String> cache = new LruCache<>(2);
    cache.put(1, "a"); cache.put(2, "b");
    cache.get(1);          // touch key 1 — now key 2 is the least-recently-used
    cache.put(3, "c");  // over capacity — evicts key 2, NOT key 1
    System.out.println(cache.keySet()); // [1, 3]
  }
}
Output
[1, 3]
💡

This exact pattern — extend LinkedHashMap, override removeEldestEntry() — is the textbook way to implement an in-process LRU cache, and a very common interview whiteboard question.

09
Intermediate TreeMap & NavigableMap
A TreeMap is a red-black tree keeping keys always sorted. O(log n) for get/put instead of HashMap's O(1), but you gain firstKey(), lastKey(), and range queries — exactly what a HashMap can never give you.
Java
import java.util.*;

public class Main {
  public static void main(String[] args) {
    TreeMap<Integer,String> events = new TreeMap<>();
    events.put(900,  "market open");
    events.put(1200, "lunch report");
    events.put(1600, "market close");

    System.out.println(events.floorKey(1300));   // 1200 — latest event at or before 13:00
    System.out.println(events.ceilingKey(1300)); // 1600 — earliest event at or after 13:00
    System.out.println(events.headMap(1300));   // everything before 13:00
  }
}
Output
1200 1600 {900=market open, 1200=lunch report}
💡

Reach for TreeMap/TreeSet whenever the question is "what's the closest value to X?" — a HashMap simply cannot answer that without scanning everything.

10
Intermediate Queue, Deque & PriorityQueue
ArrayDeque is the modern default for a stack OR a queue — faster than LinkedList for this job because it's backed by a resizable array with two movable ends, no per-node allocation. PriorityQueue is a binary heap — not sorted overall, but peek()/poll() always return the smallest (or highest-priority) element in O(log n).
🏥

Hospital triage: Patients don't get seen first-come-first-served — the most critical case (highest priority) is always pulled next, no matter when they arrived.

Java
import java.util.*;

public class Main {
  record Patient(String name, int severity) {}

  public static void main(String[] args) {
    Deque<String> stack = new ArrayDeque<>();
    stack.push("A"); stack.push("B");
    System.out.println(stack.pop()); // B — last in, first out

    PriorityQueue<Patient> triage = new PriorityQueue<>(
        Comparator.comparingInt(Patient::severity).reversed());
    triage.add(new Patient("Alice", 2));
    triage.add(new Patient("Bob", 9));   // most severe — seen first despite arriving 2nd
    triage.add(new Patient("Cara", 5));

    while (!triage.isEmpty())
      System.out.println(triage.poll().name());
  }
}
Output
B Bob Cara Alice
💡

PriorityQueue is THE go-to structure for top-K problems ("find the 5 largest values in a stream"). For a max-K problem, keep a min-heap of size K — anything bigger than the current minimum bumps the smallest one out.

11
Advanced Fail-Fast Iterators & CopyOnWriteArrayList
Most java.util collections keep an internal modCount. If you structurally modify the collection (add/remove) while iterating it directly — not through the iterator — the next call to next() throws ConcurrentModificationException immediately. This is "fail-fast": better a loud crash than silent corruption.
Java
import java.util.*;
import java.util.concurrent.CopyOnWriteArrayList;

public class Main {
  public static void main(String[] args) {
    List<String> names = new ArrayList<>(List.of("Ann", "Bob", "Cara"));

    try {
      for (String n : names) {
        if (n.equals("Bob")) names.remove(n); // ❌ modifying the list mid for-each
      }
    } catch (ConcurrentModificationException e) {
      System.out.println("Caught CME — must use iterator.remove() instead");
    }

    List<String> safe = new CopyOnWriteArrayList<>(List.of("Ann", "Bob", "Cara"));
    for (String n : safe) {
      if (n.equals("Bob")) safe.remove(n); // safe — iterates over a SNAPSHOT taken at loop start
    }
    System.out.println(safe); // [Ann, Cara]
  }
}
Output
Caught CME — must use iterator.remove() instead [Ann, Cara]
💡

The real fix for plain ArrayList is Iterator.remove() (the only structural change a fail-fast iterator allows). CopyOnWriteArrayList is "fail-safe" — it copies the whole backing array on every write, so it's great for rarely-written/often-read lists (like a list of event listeners), but a poor choice for write-heavy workloads.

Advanced Comparable vs Comparator
Comparable<T> is implemented BY the class itself — its one natural ordering (e.g. numbers sort by value). Comparator<T> is a separate, swappable strategy object — you can have as many of these as you want, and you don't need to modify the original class to add one.
Java
import java.util.*;

public class Main {
  record Employee(String name, int age, double salary) implements Comparable<Employee> {
    @Override
    public int compareTo(Employee other) {
      return Integer.compare(this.age, other.age); // natural order: by age
    }
  }

  public static void main(String[] args) {
    List<Employee> staff = new ArrayList<>(List.of(
        new Employee("Ann", 34, 95000),
        new Employee("Bob", 29, 110000),
        new Employee("Cara", 41, 88000)));

    Collections.sort(staff); // uses compareTo() — sorted by age
    System.out.println(staff.get(0).name()); // Bob (29)

    staff.sort(Comparator.comparingDouble(Employee::salary).reversed()
                              .thenComparing(Employee::name)); // custom: highest salary first, tiebreak by name
    System.out.println(staff.get(0).name()); // Bob (110000)
  }
}
Output
Bob Bob
💡

A class can have only ONE compareTo(), but unlimited Comparators. Comparator.comparing(...).thenComparing(...) chains tie-breakers cleanly without nested if-statements.

Advanced Collections Utility Class & Big-O Cheat Sheet
The Collections class (singular methods, not to be confused with the Collection interface) is a grab-bag of static helpers: sorting, searching, wrapping a list as read-only or thread-safe, and more.
Java
import java.util.*;

public class Main {
  public static void main(String[] args) {
    List<Integer> nums = new ArrayList<>(List.of(5,1,9,3));
    Collections.sort(nums);
    System.out.println(Collections.binarySearch(nums, 9)); // 3 — index found via O(log n) search; list MUST be sorted first

    List<Integer> readOnly = Collections.unmodifiableList(nums);
    try { readOnly.add(99); }
    catch (UnsupportedOperationException e) { System.out.println("Blocked — read-only view"); }

    List<Integer> threadSafe = Collections.synchronizedList(nums); // wraps every method in synchronized
  }
}
Output
3 Blocked — read-only view

ArrayListO(1) / O(n)O(1)O(n)
LinkedListO(n) / O(n)O(1)O(n) to find + O(1) to splice
HashSet / HashMapO(1) avgO(1) avg—
TreeSet / TreeMapO(log n)O(log n)—

binarySearch() on an unsorted list silently returns garbage — it assumes sorted input and never checks. Always sort first.

Advanced Senior Interview FAQ
The questions that come up again and again once you're past the "name 3 collections" stage.
Java
// Q: "How does HashMap work internally?"
// A: Array of buckets. key.hashCode() (then a secondary spread function)
//    picks the bucket index. Same-bucket keys form a linked list, or a
//    red-black tree once a bucket passes 8 entries (Java 8+). Resizes
//    (doubles + rehashes everything) once size exceeds capacity*loadFactor.

// Q: "ArrayList vs LinkedList — when does LinkedList actually win?"
// A: Only when you are repeatedly adding/removing at the HEAD or via an
//    existing Iterator/ListIterator mid-traversal — never for random access
//    or simple end-appends, where ArrayList wins due to cache locality.
//    In practice: prefer ArrayDeque for queues/stacks over LinkedList too.

// Q: "HashMap vs Hashtable vs ConcurrentHashMap?"
// A: Hashtable is legacy, synchronizes the WHOLE map on every call (slow),
//    no null keys/values. HashMap is fast but not thread-safe at all.
//    ConcurrentHashMap locks only small internal segments, so multiple
//    threads can read/write different keys with no contention.

// Q: "Fail-fast vs fail-safe iterators?"
// A: Fail-fast (ArrayList, HashMap, ...) throws ConcurrentModificationException
//    if the collection structurally changes during iteration — it's a bug
//    DETECTOR, not a guarantee. Fail-safe (CopyOnWriteArrayList,
//    ConcurrentHashMap's iterator) iterates a stable snapshot instead and
//    never throws, but may not reflect the very latest writes.
💡

Interviewers aren't testing memorization — they're testing whether you can connect hashing → buckets → collisions → resize into one coherent story, and whether you know the tradeoff behind every "vs" question.
