01
Basic Stream Basics & Laziness
A Stream is a pipeline: a source (Collection.stream(), Stream.of(), Arrays.stream(), IntStream.range()), zero or more lazy intermediate operations (map, filter, ...) that just build up the pipeline without running anything, and exactly one terminal operation (collect, forEach, reduce, count...) that actually triggers execution, element by element, through the whole chain.
🏭

Assembly line: stations for cutting, painting, and packing don't do anything until someone at the very end presses "start". Intermediate operations are the stations; the terminal operation is the button.

Java
import java.util.List;

public class Main {
  public static void main(String[] args) {
    List<String> names = List.of("amy", "bob", "cara");

    System.out.println("Building pipeline... (nothing runs yet)");
    var pipeline = names.stream()
        .map(n -> { System.out.println("map: " + n); return n.toUpperCase(); })
        .filter(n -> { System.out.println("filter: " + n); return n.length() > 3; });

    System.out.println("Pipeline built. Calling terminal op now:");
    List<String> result = pipeline.collect(java.util.stream.Collectors.toList());
    System.out.println("Result: " + result);
  }
}
Output
Building pipeline... (nothing runs yet) Pipeline built. Calling terminal op now: map: amy filter: AMY map: bob filter: BOB map: cara filter: CARA Result: [CARA]
💡

Notice map and filter run per element, not per stage — that's laziness in action. A Stream is also single-use: once a terminal operation runs, calling another operation on the same stream throws IllegalStateException: stream has already been operated upon or closed.

02
Basic map vs flatMap
map() transforms each element 1-to-1 (T -> R). flatMap() transforms each element into its own stream and then flattens all of those streams into one (T -> Stream<R>) — essential whenever you're holding a collection of collections.
Java
import java.util.List;
import java.util.stream.Collectors;

public class Main {
  public static void main(String[] args) {
    List<List<String>> sentences = List.of(
        List.of("the", "quick", "fox"),
        List.of("lazy", "dog")
    );

    // ❌ map() gives you a Stream<List<String>> — a stream of lists, NOT what you wanted
    List<List<String>> wrong = sentences.stream()
        .map(sentence -> sentence)
        .collect(Collectors.toList());

    // ✅ flatMap() gives you a flat Stream<String> of every word
    List<String> words = sentences.stream()
        .flatMap(List::stream)
        .collect(Collectors.toList());

    System.out.println("map()     -> " + wrong);
    System.out.println("flatMap() -> " + words);
  }
}
Output
map() -> [[the, quick, fox], [lazy, dog]] flatMap() -> [the, quick, fox, lazy, dog]
💡

The classic tell: if your map() would produce a return type like Stream<List<X>> instead of a flat result, you wanted flatMap().

03
Basic filter, sorted, distinct, limit/skip
filter(Predicate) keeps matching elements. sorted() / sorted(Comparator) orders them — chain with .thenComparing() for tie-breakers. distinct() removes duplicates using equals()/hashCode(). limit(n) / skip(n) slice the stream, perfect for pagination or "top N" queries.
Java
import java.util.Comparator;
import java.util.List;
import java.util.stream.Collectors;

public class Main {
  record Employee(String name, String dept, double salary) {}

  public static void main(String[] args) {
    List<Employee> employees = List.of(
        new Employee("Amy", "Eng", 142_000),
        new Employee("Bo", "Eng", 168_000),
        new Employee("Cara", "Sales", 98_000),
        new Employee("Deja", "Eng", 201_000)
    );

    List<Employee> top3Engineers = employees.stream()
        .filter(e -> e.dept().equals("Eng"))         // filter BEFORE sorting — less to sort
        .sorted(Comparator.comparing(Employee::salary).reversed())
        .limit(3)
        .collect(Collectors.toList());

    top3Engineers.forEach(e -> System.out.println(e.name() + " - $" + e.salary()));
  }
}
Output
Deja - $201000.0 Bo - $168000.0 Amy - $142000.0
💡

Order matters for performance: filter() before sorted() when possible, so you're not paying to sort elements you're about to discard anyway.

04
Intermediate collect() and Collectors
collect() is the general-purpose terminal operation: it reduces a stream into a container or summary value via a Collector. The most-used java.util.stream.Collectors factories: toList(), toSet(), toMap(keyFn, valueFn) (plus a merge-function overload), and joining(delimiter, prefix, suffix).
Java
import java.util.List;
import java.util.Map;
import java.util.stream.Collectors;

public class Main {
  record Product(String name, double price) {}

  public static void main(String[] args) {
    List<Product> products = List.of(
        new Product("Mug", 9.99),
        new Product("Mug", 12.50), // duplicate name, different price
        new Product("Pen", 1.20)
    );

    // ❌ toMap(keyFn, valueFn) without a merge function throws on duplicate keys
    // Map<String, Double> broken = products.stream()
    //     .collect(Collectors.toMap(Product::name, Product::price)); // IllegalStateException!

    Map<String, Double> prices = products.stream()
        .collect(Collectors.toMap(Product::name, Product::price, Double::max)); // keep the higher price

    System.out.println(prices);
  }
}
Output
{Pen=1.2, Mug=12.5}
💡

toMap() without a merge function throws IllegalStateException: Duplicate key — always add the 3-argument merge function unless you're certain keys are unique.

05
Intermediate groupingBy & partitioningBy
Collectors.groupingBy(classifierFn) buckets elements into a Map<K, List<T>>. Pass a downstream collector — counting(), summingInt(), mapping() — to summarize each bucket instead of just listing elements. partitioningBy(predicate) always produces exactly a Map<Boolean, List<T>> (true/false buckets).
Java
import java.util.List;
import java.util.Map;
import java.util.stream.Collectors;

public class Main {
  record Employee(String name, String dept, double salary) {}

  public static void main(String[] args) {
    List<Employee> employees = List.of(
        new Employee("Amy", "Eng", 142_000),
        new Employee("Bo", "Eng", 168_000),
        new Employee("Cara", "Sales", 98_000)
    );

    Map<String, List<Employee>> byDept = employees.stream()
        .collect(Collectors.groupingBy(Employee::dept));

    Map<String, Long> countByDept = employees.stream()
        .collect(Collectors.groupingBy(Employee::dept, Collectors.counting()));

    Map<Boolean, List<Employee>> highEarners = employees.stream()
        .collect(Collectors.partitioningBy(e -> e.salary() > 100_000));

    System.out.println("byDept keys:      " + byDept.keySet());
    System.out.println("countByDept:      " + countByDept);
    System.out.println("highEarners[true]: " + highEarners.get(true).size() + " people");
  }
}
Output
byDept keys: [Eng, Sales] countByDept: {Eng=2, Sales=1} highEarners[true]: 2 people
💡

Reach for partitioningBy only when the split is truly binary. groupingBy handles both binary and multi-way splits, so it's the more generally useful tool by default.

06
Intermediate reduce()
Three overloads: reduce(BinaryOperator) returns Optional<T>, reduce(identity, BinaryOperator) returns T directly, and the 3-arg reduce(identity, accumulator, combiner) is mainly for parallel streams where per-thread partial results need to be combined.
Java
import java.util.List;
import java.util.Optional;

public class Main {
  public static void main(String[] args) {
    List<Integer> nums = List.of(3, 8, 1, 9, 4);

    // Simple numeric aggregation — prefer IntStream.sum() / Collectors.summingInt() over this
    int sum = nums.stream().reduce(0, Integer::sum);

    // reduce() shines for custom combining logic that has no built-in collector
    List<String> words = List.of("go", "stream", "reducing", "it");
    Optional<String> longest = words.stream()
        .reduce((a, b) -> a.length() >= b.length() ? a : b);

    System.out.println("sum = " + sum);
    System.out.println("longest = " + longest.orElse("none"));
  }
}
Output
sum = 25 longest = reducing
💡

Don't reach for reduce() for things Collectors or IntStream/DoubleStream already do better (sum, average, min, max) — use it when you have genuinely custom combining logic.

Intermediate Optional + Streams
findFirst() is deterministic — it respects encounter order. findAny() may be faster on parallel streams since it doesn't need to determine which match came first. Both return Optional<T>, as do min()/max() with a Comparator.
Java
import java.util.List;
import java.util.NoSuchElementException;
import java.util.Optional;

public class Main {
  record User(String name, boolean admin) {}

  public static void main(String[] args) {
    List<User> users = List.of(new User("amy", false), new User("bo", true));

    // ❌ .get() with no presence check is a NoSuchElementException risk
    // User bad = users.stream().filter(User::admin).findFirst().get();

    Optional<User> admin = users.stream().filter(User::admin).findFirst();
    String label = admin.map(User::name).orElse("no admin found");
    System.out.println("admin: " + label);

    // ✅ safe unwrap with a meaningful failure
    User required = users.stream().filter(u -> u.name().equals("zzz")).findFirst()
        .orElseThrow(() -> new NoSuchElementException("no user named zzz"));
  }
}
Output
admin: bo Exception in thread "main" java.util.NoSuchElementException: no user named zzz
💡

findAny() and findFirst() behave identically on sequential streams — the distinction only matters once you introduce .parallel(), where findAny() can return as soon as any match is found instead of waiting to determine which one is first.

08
Advanced Parallel Streams
.parallelStream() / .stream().parallel() splits work across the common ForkJoinPool and can speed up large, CPU-bound, stateless pipelines. But: shared mutable state causes race conditions, the source needs to split efficiently (arrays/ArrayList split well; LinkedList and I/O-based streams don't), and there's overhead that makes parallel streams slower than sequential on small collections.
Java
import java.util.ArrayList;
import java.util.List;
import java.util.stream.Collectors;
import java.util.stream.IntStream;

public class Main {
  public static void main(String[] args) {
    int n = 100_000;

    // ❌ RACY — a plain ArrayList is not thread-safe; size may not always be n
    List<Integer> broken = new ArrayList<>();
    IntStream.range(0, n).parallel().forEach(broken::add); // data race on the shared list
    System.out.println("broken size (should be " + n + "): " + broken.size());

    // ✅ SAFE — collect() handles thread-safe accumulation internally
    List<Integer> fixed = IntStream.range(0, n).parallel().boxed()
        .collect(Collectors.toList());
    System.out.println("fixed size (always " + n + "): " + fixed.size());
  }
}
Output (typical — the broken run is non-deterministic)
broken size (should be 100000): 97431 ← lost elements to the race! fixed size (always 100000): 100000
💡

Parallel streams are an easy way to introduce silent, hard-to-reproduce concurrency bugs if you touch any shared mutable state inside the pipeline. Always prefer collect()/reduce() over manual shared-state accumulation, and only reach for .parallel() after profiling shows it actually helps.

Advanced Stream Anti-Patterns
The classics: stream-itis (using .stream() for a 3-line loop just because it's available), side effects in map/filter (they're supposed to be pure functions — implementations are free to skip calls in ways that break stateful side effects), reusing a consumed stream (throws IllegalStateException), and collecting to a list just to immediately loop over it instead of chaining .forEach().
Java
import java.util.List;
import java.util.concurrent.atomic.AtomicInteger;
import java.util.stream.Collectors;
import java.util.stream.Stream;

public class Main {
  public static void main(String[] args) {

    // ❌ ANTI-PATTERN: side effect inside map() — mutating an outer variable
    List<Integer> nums = List.of(1, 2, 3);
    AtomicInteger counter = new AtomicInteger();
    List<Integer> doubled = nums.stream()
        .map(x -> { counter.incrementAndGet(); return x * 2; }) // side effect — fragile, avoid
        .collect(Collectors.toList());

    // ✅ FIX: keep map() pure, do side effects in forEach()
    List<Integer> doubledClean = nums.stream().map(x -> x * 2).collect(Collectors.toList());
    doubledClean.forEach(x -> System.out.println("processed: " + x)); // forEach is the right place for side effects

    // ❌ ANTI-PATTERN: reusing a consumed stream
    Stream<Integer> s = nums.stream();
    s.count(); // terminal op #1 — stream is now consumed
    try { s.count(); } catch (IllegalStateException e) {
      System.out.println("caught: " + e.getMessage());
    }
  }
}
Output
processed: 2 processed: 4 processed: 6 caught: stream has already been operated upon or closed
💡

Streams describe what transformation you want, not a mandatory replacement for every loop. If a plain for-loop is clearer for a given case, use it — streams win when there's real transformation/filtering/aggregation logic worth expressing declaratively.

Advanced Senior Interview FAQ
Five questions interviewers love, with the answer a senior candidate is expected to give.
Java
// Q: "What makes intermediate operations 'lazy', and why does that matter?"
// A: They don't execute anything by themselves — they just describe a step and get chained
//    onto the pipeline. Nothing runs until a terminal operation is called, and then every
//    element flows through the ENTIRE pipeline one at a time. This matters because it means
//    you can build a pipeline conditionally without any wasted work if it's never consumed,
//    and short-circuiting ops (findFirst, limit, anyMatch) can stop early without processing
//    the whole source.

// Q: "When would you use flatMap instead of map — what's the tell?"
// A: The moment your map() function itself returns a stream or collection, meaning map()
//    alone would produce a stream-of-streams (e.g. Stream<List<X>>). flatMap flattens that
//    extra layer into a single flat stream.

// Q: "Why does Collectors.toMap() throw on duplicate keys, and how do you fix it?"
// A: toMap's 2-arg form has no way to know what to do when two elements produce the same
//    key — silently picking one would hide data loss, so it fails fast instead. Fix it with
//    the 3-arg overload, supplying a merge function: toMap(keyFn, valFn, (a, b) -> a).

// Q: "What's the actual risk of using parallelStream() carelessly?"
// A: Any shared mutable state touched inside the pipeline (a plain ArrayList, a counter
//    variable) becomes a data race, since multiple threads from the common ForkJoinPool run
//    segments concurrently. The fix isn't "be careful" — it's structural: use collect() and
//    reduce(), which handle thread-safe accumulation for you, instead of manual mutation.

// Q: "Why can't you reuse a Stream after a terminal operation has run?"
// A: A Stream isn't a data structure — it's a one-time description of a computation over a
//    source. Once the terminal op consumes it, the underlying spliterator's cursor state is
//    spent and Java's implementation deliberately throws IllegalStateException on reuse,
//    rather than silently giving you an empty or partial result.
💡

Senior interviews aren't testing whether you can recite Collector names — they're testing whether you understand streams as a one-shot lazy pipeline, not a list-like data structure you can poke at repeatedly.
