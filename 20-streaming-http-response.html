Backend Engineering — Incident Postmortem

The CSV Report
That Wouldn't Download

A financial-transactions export, a gateway that kept killing the connection, a Keep-Alive header that didn't help at all — and the one-line mental model that actually fixed it: a response isn't safe just because it will finish. It's safe because it never goes quiet.

01
Setup
A CSV export, over plain HTTP

The feature was simple on paper: a user picks a date range on a financial transactions dashboard and clicks Download report. The backend queries the transactions, serializes them to CSV, and the browser saves the file. For small accounts and short ranges — a few hundred rows — this worked perfectly, every time.

The problem only showed up for the reports that mattered most: large accounts, wide date ranges, producing CSVs in the tens of thousands of rows — several megabytes of plain text. Those downloads didn't just take longer. They failed outright.

02
Symptom
The browser just... gives up

For the large reports: the download would start (or appear to), sit at "downloading" with no progress, and then the browser would report a failed / interrupted download. No CSV, no partial file worth trusting, no useful error surfaced to the user beyond "something went wrong."

📞

Like being on hold with no hold music. If a phone line goes completely silent for too long, the switchboard assumes the call dropped and hangs up — even if the person on the other end was still there, just quietly writing something down. That's exactly the shape of what was happening on the wire.

03
First theory — wrong
"It must be a connection timeout — bump Keep-Alive"

The first, reasonable-sounding theory: some layer is closing the connection too early because it thinks the request is taking too long. The fix that seemed obvious — extend how long the connection is allowed to stay alive.

HTTP response headers — attempt #1
HTTP/1.1 200 OK
Content-Type: text/csv
Content-Disposition: attachment; filename=transactions.csv
Connection: keep-alive
Keep-Alive: timeout=600   // 10 minutes — should be plenty of runway, right?

It changed nothing. Same reports, same failure, same point of breakdown — which was the actual clue. If a connection-lifetime setting had been the problem, extending it should have fixed at least the largest-but-not-huge reports. Nothing moved. That meant the thing killing the connection wasn't watching how old the connection was at all.

04
Investigation
Two clues, from two different logs

Application logs: the backend finished successfully on every single failing request. The query ran, every row got serialized, the full CSV byte array was built — as far as the service was concerned, it had a complete response ready to send.

Gateway logs (the API gateway / reverse proxy sitting between the browser and the service): a timeout, on exactly those same calls, well before the backend had actually finished. The gateway wasn't waiting for the whole request to complete — it was killing the connection because it had received no bytes at all from the backend for longer than its own idle-read timeout allowed.

💡

This is the whole bug, in one sentence: Keep-Alive controls whether a connection is reused / left open while genuinely idle between requests. It has nothing to do with how long an intermediary will tolerate silence in the middle of a response that's already in flight. That second thing is a completely separate setting — an idle / read timeout — enforced independently by the gateway, and no amount of Keep-Alive tuning touches it.

05
Root cause
The whole response was built before a single byte was sent

The original controller loaded every matching transaction, converted the entire set to CSV text in memory, and only then handed the finished byte array to Spring as the response body. For a large report, that fetch-and-serialize step alone could run well past a minute.

During that entire minute-plus, the connection to the gateway carried zero bytes. Not slow — silent. From the gateway's point of view that's indistinguishable from a hung backend, so it did exactly what an idle-read timeout is designed to do: it cut the connection. The eventual finished CSV never had a chance to leave the building.

06
The fix
Stream the rows out as they're produced — never build the whole file first

The rewrite didn't change what data went to the user. It changed when bytes started leaving the server: instead of assembling the entire CSV and returning it as one block, the response writes each batch of rows straight to the output stream as soon as it's fetched, and flushes regularly.

Java — before (buffered)
@GetMapping("/api/reports/transactions")
public ResponseEntity<byte[]> downloadTransactions(String accountId, LocalDate from, LocalDate to) {

    List<Transaction> rows = repo.findAllByAccountIdAndDateBetween(accountId, from, to);
    // for a wide date range, this alone can be 100k+ rows held in memory

    StringBuilder csv = new StringBuilder("date,description,amount,balance\n");
    for (Transaction t : rows) {
        csv.append(t.getDate()).append(',')
           .append(t.getDescription()).append(',')
           .append(t.getAmount()).append('\n');
    }
    // nothing has reached the socket yet — everything above is happening in memory,
    // and the gateway sees total silence for the whole time this loop runs

    return ResponseEntity.ok()
        .header(HttpHeaders.CONTENT_DISPOSITION, "attachment; filename=transactions.csv")
        .contentType(MediaType.parseMediaType("text/csv"))
        .body(csv.toString().getBytes(UTF_8)); // one giant block, sent only at the end
}
Java — after (streamed)
@GetMapping("/api/reports/transactions")
public ResponseEntity<StreamingResponseBody> downloadTransactions(String accountId, LocalDate from, LocalDate to) {

    StreamingResponseBody body = out -> {
        Writer w = new BufferedWriter(new OutputStreamWriter(out, UTF_8));
        w.write("date,description,amount,balance\n");

        int sinceFlush = 0;
        try (Stream<Transaction> rows = repo.streamAllByAccountIdAndDateBetween(accountId, from, to)) {
            for (Transaction t : (Iterable<Transaction>) rows::iterator) {
                w.write(t.getDate() + "," + t.getDescription() + "," + t.getAmount() + "\n");
                if (++sinceFlush == 500) { w.flush(); sinceFlush = 0; } // push real bytes onto the wire, regularly
            }
        }
        w.flush();
    };

    return ResponseEntity.ok()
        .header(HttpHeaders.CONTENT_DISPOSITION, "attachment; filename=transactions.csv")
        .contentType(MediaType.parseMediaType("text/csv"))
        .body(body); // no Content-Length up front → Transfer-Encoding: chunked
}
⚠️

The gotcha that almost bit us: StreamingResponseBody.writeTo() runs asynchronously, after the controller method has already returned — so the controller's own @Transactional boundary is already closed by the time the stream is actually read. A JPA Stream<Transaction> backed by a DB cursor has to be opened and fully consumed inside a transaction that's still active during the write, so the repository method itself carries @Transactional(readOnly = true) plus a fetch-size query hint — not the controller.

Repository — cursor-based, not "load everything"
@Transactional(readOnly = true)
@QueryHints(@QueryHint(name = HINT_FETCH_SIZE, value = "500"))
@Query("select t from Transaction t where t.accountId = :accountId " +
       "and t.date between :from and :to order by t.date")
Stream<Transaction> streamAllByAccountIdAndDateBetween(String accountId, LocalDate from, LocalDate to);
07
Verification
What changed in Postman was the tell

Before: for a large report, Postman would sit on "Sending request..." with no status at all, then eventually report a failed / reset connection. Nothing ever rendered — because nothing was ever going to arrive as one piece before the gateway gave up.

After: Postman showed 200 OK almost immediately — the status line and headers go out the moment streaming begins, long before the body is complete — and then the response panel visibly filled in over time as chunks kept arriving, finishing cleanly when the stream closed. That "status first, body trickles in after" behaviour is the visible signature of a chunked, streamed response, as opposed to a buffered one that shows nothing until it either fully arrives or fails.

💡

The browser download stopped failing for the exact same reason Postman's behaviour changed: the connection was never silent long enough for anything in between — gateway included — to conclude it had died.

The three mechanisms, side by side
MechanismWhat it actually governsDid it matter here?
Connection: keep-alive / Keep-Alive: timeout=Whether a TCP connection is reused across separate requests, and how long it's kept open while genuinely idle between them.No — this was never the failure point.

Interview pitch
60-second version
Situation
A financial-transactions CSV export failed to download in the browser for any sufficiently large report, while small reports always worked fine.
Task
Find the real cause — not just make the symptom go away — and fix it without an unbounded increase in server memory per export.
Action
Ruled out connection lifetime by raising Keep-Alive, which changed nothing — the real signal. Correlated application logs (backend always finished) against gateway logs (timeout, mid-response) and traced it to an idle-read timeout, not a duration timeout. Found the root cause: the controller built the entire CSV in memory before sending anything, so the connection sat silent for the whole generation time. Rewrote it as a StreamingResponseBody backed by a cursor-based JPA Stream, flushing every batch so real bytes hit the wire continuously from the first row onward.
Result
Downloads of any size completed reliably, memory per request dropped to one batch instead of the whole file, and the fix was visible in Postman itself — 200 OK appeared immediately, with the body visibly streaming in afterward instead of arriving (or failing) as one silent block.
streaming-response-body · chunked-transfer-encoding · gateway-idle-timeout ≠ keep-alive
