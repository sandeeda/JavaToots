SQL — JPA / Hibernate

jakarta.persistence.*

The annotations that map a Java class onto a relational table, wire up foreign keys, and control how Hibernate loads and cascades related rows.

01Entity & table mapping

The baseline set — every JPA entity needs most of these regardless of what it relates to.

AnnotationPurposeKey attributes
@EntityMarks a class as a JPA-managed entity backed by a table.name — optional entity name used in JPQL (defaults to class name).
@TableCustomizes the table this entity maps to.name, schema, uniqueConstraints, indexes.
@IdMarks the primary-key field.No attributes — combine with @GeneratedValue for auto-increment keys.
@GeneratedValueDelegates primary-key generation to the database or a generator.strategy — AUTO, IDENTITY, SEQUENCE, TABLE. See table below.
@SequenceGenerator / @TableGeneratorDefines a named generator for SEQUENCE / TABLE strategies.name, sequenceName, allocationSize — batching PK allocation to cut round trips.
@ColumnCustomizes how a field maps to its column.name, nullable, unique, length, columnDefinition, updatable, insertable.
@TransientExcludes a field from persistence entirely — computed or cache-only fields.No attributes.
GenerationTypeWhat actually happens
IDENTITYRelies on the column's own auto-increment (MySQL AUTO_INCREMENT, Postgres SERIAL/IDENTITY). Simple, but disables JDBC batch inserts since the ID is only known after the row is written.
SEQUENCEPulls the next value from a DB sequence. Works well with batching — Hibernate can pre-allocate a block via allocationSize.
TABLEEmulates a sequence using a dedicated table of counters. Portable across any DB, but slower — rarely chosen unless the DB has no native sequence support.
AUTOLets Hibernate pick a strategy based on the configured dialect.
Java — Customer model, entity & table mapping
@Entity(name = "CustomerEntity") // name used in JPQL — table name is set separately below
@Table(
    name = "customers",
    schema = "shop",
    uniqueConstraints = @UniqueConstraint(name = "uq_customer_email", columnNames = "email"),
    indexes = @Index(name = "idx_customer_last_name", columnList = "last_name")
)
public class Customer {

    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "customer_seq")
    @SequenceGenerator(name = "customer_seq", sequenceName = "customer_id_seq", allocationSize = 50)
    private Long id;

    @Column(name = "first_name", nullable = false, length = 60)
    private String firstName;

    @Column(name = "last_name", nullable = false, length = 60)
    private String lastName;

    // no @Column here — Hibernate defaults to a column named "email"
    private String email;

    @Column(name = "created_at", updatable = false) // set once on insert, never touched again
    private Instant createdAt;

    @Transient // derived at runtime — never read from or written to the DB
    private int loyaltyScoreCache;

    // getters / setters / constructors omitted
}
🔎

Walking through it: @Entity's name only affects JPQL (select c from CustomerEntity c) — the actual table is named by @Table. @Id + @GeneratedValue(strategy = SEQUENCE) pulls the next PK from a DB sequence, and @SequenceGenerator names that sequence and sets allocationSize = 50 so Hibernate grabs 50 IDs per round trip instead of one at a time. @Column is only needed when you want something other than the default (a different name, a length limit, nullable = false) — email above has none, so it just maps to a column called email. @Transient keeps loyaltyScoreCache in the Java object only — it's never selected, inserted, or updated.

02Embedded value objects

For fields that belong to the entity conceptually but aren't entities themselves — an Address, a Money value — and live in the same table.

AnnotationPurposeKey attributes
@EmbeddableMarks a class as a value object that can be embedded into an entity's own table — no table of its own.No attributes.
@EmbeddedPlaced on the field inside the owning entity to embed an @Embeddable type.No attributes.
@EmbeddedIdUses an @Embeddable class as a composite primary key.No attributes — pair with an @Embeddable key class implementing Serializable.
@AttributeOverride(s)Renames the column(s) an embedded field maps to, when the default clashes or needs to differ.name (the embeddable's field), column — a nested @Column.
Java
@Embeddable // says "this class has no table of its own, I just live inside whoever embeds me"
public class Address {
    private String street;   // becomes a plain "street" column on WHATEVER table embeds this
    private String city;     // becomes a plain "city" column, unless overridden (see below)
    private String zipCode;  // becomes a plain "zip_code" column
}

@Entity
public class Customer {
    @Embedded // "flatten Address's fields into MY table" — no separate addresses table, no foreign key
    @AttributeOverride(name = "city", column = @Column(name = "billing_city"))
    // ^ without this, the column would just be called "city" — override it because
    //   "city" alone is ambiguous once you also embed a shippingAddress below
    private Address billingAddress; // columns live directly on the customers table: street, billing_city, zip_code
}
🔎

In plain English: Address isn't a "real" entity — it has no @Id, no table, and can't be queried on its own. @Embeddable just marks it as a reusable group of fields. When Customer declares @Embedded private Address billingAddress, Hibernate doesn't create a relationship at all — it literally copies Address's fields onto the customers table as if you'd typed street, city, and zipCode directly into Customer. @AttributeOverride exists for the one problem this causes: if you embedded a second Address (say, shippingAddress) you'd get a column-name collision, so you rename one field's column to keep them apart. @EmbeddedId (not shown) is the same trick applied to primary keys — useful when a table's real-world key is a combination of fields, like (orderId, lineNumber), rather than one auto-generated column.

03Relationships

The part everyone half-remembers under interview pressure — four cardinalities, two ways to describe the foreign key, and two knobs (cascade, fetch) that decide what actually happens on read and write.

AnnotationCardinalityDefault fetchKey attributes
@OneToOne1 ↔ 1EAGERmappedBy (inverse side), cascade, optional.
@OneToMany1 → manyLAZYmappedBy, cascade, orphanRemoval.
@ManyToOnemany → 1EAGERoptional, fetch — almost always overridden to LAZY in practice.
@ManyToManymany ↔ manyLAZYmappedBy on the inverse side, cascade (avoid REMOVE/ALL here — see gotcha below).
@JoinColumn——Declares the actual foreign-key column, on the owning side. name, referencedColumnName, nullable.
@JoinTable——Declares a link table — the default for @ManyToMany, or for a unidirectional @OneToMany. name, joinColumns, inverseJoinColumns.
💡

Owning side vs. inverse side: the side with the foreign-key column (usually the @ManyToOne) is the owning side — it's the one Hibernate actually writes when you save. The other side declares mappedBy = "fieldNameOnOwningSide" and is purely for convenient navigation; changes made only on the mappedBy side are silently not persisted unless you also update the owning side.

CascadeTypeWhat it propagates to related entities
PERSISTSaving the parent also saves new children.
MERGEMerging detached-state changes on the parent also merges children.
REMOVEDeleting the parent also deletes children — dangerous on shared/many-to-many relations.
REFRESHReloading the parent from the DB also reloads children, discarding in-memory changes.
DETACHDetaching the parent from the persistence context also detaches children.
ALLAll of the above. Common on a strict parent-owns-children relation (e.g. Order → OrderItem); usually wrong on @ManyToMany, where entities are shared, not owned.
Java — bidirectional one-to-many + many-to-many
@Entity
public class Customer {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @OneToMany(mappedBy = "customer", cascade = CascadeType.ALL, orphanRemoval = true)
    // mappedBy = "customer" -> "I don't own the FK, look at the `customer` field over on Order for it"
    // cascade = ALL         -> saving/deleting a Customer also saves/deletes its Orders
    // orphanRemoval = true  -> removing an Order from this list deletes that Order row too
    private List<Order> orders = new ArrayList<>();
}

@Entity
public class Order {
    @Id @GeneratedValue
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    // fetch = LAZY   -> don't load the Customer row until .getCustomer() is actually called
    // optional=false -> every Order MUST have a Customer; generates a NOT NULL FK column
    @JoinColumn(name = "customer_id", nullable = false) // owning side — this is the real FK column
    private Customer customer;

    @ManyToMany
    // no mappedBy here -> Order is the owning side of this relationship
    @JoinTable(name = "order_tags",
        // order_tags is a plain link table: (order_id, tag_id) — Hibernate manages it, you never map it as an entity
        joinColumns = @JoinColumn(name = "order_id"),        // the column pointing back to THIS entity (Order)
        inverseJoinColumns = @JoinColumn(name = "tag_id"))    // the column pointing to the OTHER entity (Tag)
    private Set<Tag> tags = new HashSet<>();
}
🔎

In plain English: a Customer has many Orders, and each Order belongs to exactly one Customer — that's the @OneToMany/@ManyToOne pair. The foreign key (customer_id) physically lives on the orders table, so Order is the "owning" side and gets @JoinColumn; Customer just says "my orders are wherever customer points at me" via mappedBy — it doesn't create or store anything extra. cascade = ALL plus orphanRemoval = true on the Customer side means the app never has to manually delete an order — deleting the customer, or just removing an order from the customer's list, does it automatically. Separately, an Order can have many Tags and a Tag can be on many Orders — that many-to-many needs its own link table (order_tags) to store the pairings, which @JoinTable describes.

⚠️

N+1 by default: @ManyToOne/@OneToOne default to EAGER, which quietly triggers an extra query per row when you fetch a list of parents. Almost every real-world mapping overrides this to fetch = FetchType.LAZY explicitly and reaches for @EntityGraph (see §07) or a JPQL JOIN FETCH when eager loading is actually needed for one specific query.

04Inheritance mapping

For a class hierarchy — Payment → CardPayment, BankTransferPayment — that needs to live in relational tables.

AnnotationPurposeKey attributes
@InheritanceDeclares the table strategy for a class hierarchy, on the root entity.strategy — SINGLE_TABLE (default), JOINED, TABLE_PER_CLASS.
@DiscriminatorColumnNames the column that records which subclass a row belongs to (SINGLE_TABLE).name, discriminatorType.
@DiscriminatorValueThe value stored in that column for a given subclass.e.g. "CARD", "BANK_TRANSFER".
@MappedSuperclassShares common fields (e.g. id, audit columns) across entities without itself being an entity or having a table.No attributes.
💡

SINGLE_TABLE is fastest (no joins, one query for polymorphic reads) but every column from every subclass ends up nullable in one wide table. JOINED is normalized (one table per subclass, joined by PK) at the cost of a join per read. TABLE_PER_CLASS duplicates shared columns into every subclass table and complicates polymorphic queries — the least commonly chosen of the three.

Java — Payment hierarchy, single-table strategy
@MappedSuperclass // NOT an entity, NOT a table — just a field template every subclass inherits
public abstract class BaseEntity {
    @Id @GeneratedValue
    protected Long id;              // every Payment subtype gets an "id" column this way

    @CreatedDate
    protected Instant createdAt;    // and a "created_at" column, without repeating it per class
}

@Entity
@Table(name = "payments")                                  // ONE physical table holds every subtype's rows
@Inheritance(strategy = InheritanceType.SINGLE_TABLE)      // all subclasses share this one table
@DiscriminatorColumn(name = "payment_type", discriminatorType = DiscriminatorType.STRING)
// ^ adds a "payment_type" column that records which subclass each row actually is
public abstract class Payment extends BaseEntity {
    protected BigDecimal amount;    // shared column, present for every subtype
}

@Entity
@DiscriminatorValue("CARD") // rows for this subclass get payment_type = 'CARD'
public class CardPayment extends Payment {
    private String last4;         // column only meaningful for card payments — nullable for other rows
}

@Entity
@DiscriminatorValue("BANK_TRANSFER") // rows for this subclass get payment_type = 'BANK_TRANSFER'
public class BankTransferPayment extends Payment {
    private String iban;           // column only meaningful for bank-transfer payments
}
🔎

In plain English: you have one Java concept, "a payment," that comes in different shapes — a card payment has a card number, a bank transfer has an IBAN — but you still want to query "all payments for this order" as one list. @Inheritance(strategy = SINGLE_TABLE) tells Hibernate to store every subtype in one wide payments table; @DiscriminatorColumn/@DiscriminatorValue add a column (payment_type) that records which subtype each row actually is, so Hibernate knows whether to hydrate a row as a CardPayment or a BankTransferPayment when you read it back. @MappedSuperclass is a separate, simpler trick: BaseEntity isn't part of the inheritance hierarchy Hibernate tracks at all — it's just a way to avoid retyping id and createdAt on every entity in your codebase.

05Auditing & optimistic locking

AnnotationPurposeKey attributes / notes
@VersionTurns on optimistic locking — Hibernate checks this column hasn't changed before committing an update, throwing OptimisticLockException on conflict.Field type Long, Integer, or Timestamp. No attributes.
@CreatedDateAuto-populates the field with the timestamp when the entity is first persisted.Spring Data commons — needs @EnableJpaAuditing on a config class.
@LastModifiedDateAuto-updates the field on every save.Same requirements as @CreatedDate.
@CreatedBy / @LastModifiedByAuto-populates the current principal, via a supplied AuditorAware<T> bean.Requires an AuditorAware implementation registered in the auditing config.
@EntityListeners(AuditingEntityListener.class)The piece that actually wires the four annotations above into the entity's lifecycle callbacks.Placed directly on the entity — easy to forget, and auditing silently does nothing without it.
Java — audited, optimistically-locked entity
@Configuration
@EnableJpaAuditing(auditorAwareRef = "auditorProvider") // turns auditing ON app-wide; without this the annotations below do nothing
public class JpaAuditingConfig {
    @Bean
    public AuditorAware<String> auditorProvider() {
        // tells Spring HOW to figure out "who is the current user" for @CreatedBy/@LastModifiedBy
        return () -> Optional.of(SecurityContextHolder.getContext().getAuthentication().getName());
    }
}

@Entity
@EntityListeners(AuditingEntityListener.class) // hooks the fields below into save/update lifecycle events — easy to forget!
public class Order {
    @Id @GeneratedValue
    private Long id;

    @Version
    private Long version;           // starts at 0; Hibernate checks + increments this on every UPDATE.
                                     // if another transaction changed it first, you get OptimisticLockException

    @CreatedDate
    private Instant createdAt;     // set ONCE automatically, the moment this row is first inserted

    @LastModifiedDate
    private Instant updatedAt;     // re-set automatically on every single update after that

    @CreatedBy
    private String createdBy;      // filled in from the AuditorAware bean above, once, on insert

    @LastModifiedBy
    private String lastModifiedBy; // filled in from the same bean on every update
}
🔎

In plain English: @Version stops two people from silently overwriting each other's changes — if you loaded an order at version=3 and someone else already saved it as version=4, your save fails loudly instead of quietly clobbering theirs. The four "auditing" annotations just auto-fill bookkeeping fields you'd otherwise set by hand in every service method: when a row was created, when it last changed, and who did each. None of that happens for free, though — you need @EnableJpaAuditing on a config class (to turn the feature on) and @EntityListeners(AuditingEntityListener.class) on each entity (to actually apply it there); miss either one and the fields just stay null with no error.

06Type mapping extras

AnnotationPurposeKey attributes / notes
@EnumeratedControls how a Java enum field is stored.EnumType.STRING (readable, safe to reorder) vs. EnumType.ORDINAL (compact, breaks if enum order changes — avoid).
@LobMaps a field to a large-object column — CLOB for String, BLOB for byte[].No attributes.
@TemporalSpecifies precision for legacy java.util.Date/Calendar fields.TemporalType.DATE/TIME/TIMESTAMP. Not needed for java.time types (LocalDate, Instant, etc.) — JPA 2.2+ maps those natively.
@OrderByOrders a collection using a JPQL clause, evaluated by the database on fetch.e.g. @OrderBy("placedAt DESC").
@OrderColumnPersists list order into a dedicated index column instead of sorting on read.name — needed when the collection is a List whose position is meaningful and mutable.
Java — type mapping extras
@Entity
public class Order {
    @Id @GeneratedValue
    private Long id;

    @Enumerated(EnumType.STRING)
    private OrderStatus status;         // stores the word "SHIPPED", not the number 2 — safe if you reorder the enum later

    @Lob
    private String internalNotes;      // maps to a CLOB — for text too long for a normal VARCHAR column

    @Temporal(TemporalType.TIMESTAMP)
    private Date legacyPlacedAt;      // only needed for old java.util.Date fields — tells JPA to keep date+time, not just date

    private Instant placedAt;          // modern java.time type — needs NO @Temporal, JPA 2.2+ handles it natively

    @OrderBy("createdAt DESC")
    private List<OrderNote> notes;    // DB re-sorts this list newest-first on every read — no ORDER BY column stored

    @OrderColumn(name = "item_position")
    private List<OrderItem> items;    // order is instead PERSISTED into an item_position column — needed if you can reorder/insert mid-list
}
🔎

In plain English: these annotations control how "unusual" Java types get stored, not the everyday `String`/`Long` case. @Enumerated(STRING) stores enum values as readable text instead of a fragile numeric position. @Lob is for oversized text/binary content that wouldn't fit a normal column. @Temporal only matters for the old java.util.Date/Calendar API — modern Instant/LocalDate fields don't need it at all. The two ordering annotations solve different problems: @OrderBy just asks the database to sort results at read time (cheap, but the "order" isn't a real stored fact), while @OrderColumn actually writes a position number into the table, which you need when items can be reordered or inserted in the middle of a list.

07Repository & query annotations

AnnotationPurposeKey attributes / notes
@RepositorySpring stereotype; also enables persistence-exception translation into Spring's DataAccessException hierarchy.Usually implicit — JpaRepository subinterfaces get it automatically.
@QuerySupplies a custom JPQL or native SQL query for a repository method.value, nativeQuery = true to drop into raw SQL.
@ModifyingMarks a @Query as an UPDATE/DELETE bulk operation rather than a SELECT.Pair with @Transactional on the calling service.
@ParamBinds a named parameter (:name) in @Query to a method argument.Value must match the placeholder name.
@EntityGraphDeclares which associations to eager-fetch for one specific query — the clean fix for N+1.attributePaths = {"items","customer"}.
@LockApplies a JPA lock mode to the query.LockModeType.PESSIMISTIC_WRITE, OPTIMISTIC, etc.
Java — repository
public interface OrderRepository extends JpaRepository<Order, Long> {
    // extending JpaRepository already gives you save(), findById(), findAll(), delete() for free

    @Query("select o from Order o where o.customer.id = :customerId and o.status = :status")
    // ^ JPQL — queries the ENTITY graph ("o.customer.id"), not raw table/column names
    List<Order> findByCustomerAndStatus(@Param("customerId") Long customerId, @Param("status") OrderStatus status);
    // ^ @Param binds each :placeholder above to the matching method argument by name

    @Modifying // required whenever the query is UPDATE/DELETE instead of SELECT
    @Query("update Order o set o.status = :status where o.id = :id")
    int updateStatus(@Param("id") Long id, @Param("status") OrderStatus status);
    // returns the number of rows updated; caller's service method needs @Transactional

    @EntityGraph(attributePaths = {"items", "customer"})
    // ^ for THIS query only, eagerly fetch items + customer in one go instead of lazily, one query each
    Optional<Order> findWithItemsById(Long id);
}
🔎

In plain English: just extending JpaRepository<Order, Long> already gives you basic CRUD for free — these annotations are for the queries that basic CRUD can't express. @Query lets you write the exact JPQL (or raw SQL, with nativeQuery = true) you want instead of relying on Spring to guess it from a method name; @Param just wires your method arguments into that query's :placeholders. @Modifying is mandatory the moment your @Query changes data instead of reading it — without it Spring assumes every query returns results and errors out. @EntityGraph solves the N+1 problem from §03 at the query level: instead of globally marking a relationship EAGER (which slows down every other query too), you say "just for this one method, also fetch these associations in the same round trip."

08Full example, put together

Java — Customer / Order model
@Entity                                                     // this class is JPA-managed and backed by a table
@Table(name = "customers", indexes = @Index(name = "idx_customer_email", columnList = "email", unique = true))
// ^ table is "customers"; a unique index on email enforces "no two customers share an email" at the DB level
@EntityListeners(AuditingEntityListener.class)                // required for @CreatedDate below to actually fire
public class Customer {

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY) // PK, auto-assigned by the DB's own auto-increment
    private Long id;

    @Column(name = "full_name", nullable = false, length = 120) // required field, capped at 120 chars
    private String fullName;

    private String email;                                      // default column name "email" — uniqueness enforced by the @Table index above

    @Embedded                                                  // Address's fields (street/city/zipCode) flattened onto THIS table
    private Address billingAddress;

    @Enumerated(EnumType.STRING)                               // stored as e.g. "ACTIVE", not an ordinal number
    private CustomerStatus status;

    @OneToMany(mappedBy = "customer", cascade = CascadeType.ALL, orphanRemoval = true)
    @OrderBy("placedAt DESC")                                  // newest order first, every time this list is loaded
    private List<Order> orders = new ArrayList<>();          // inverse side — FK actually lives on Order.customer

    @Version                                                   // optimistic-lock column — prevents lost updates under concurrent writes
    private Long version;

    @CreatedDate                                               // auto-set once, at insert time, by the listener declared above
    private Instant createdAt;
}
🔎

In plain English: this is every annotation from §01–§06 combined onto one realistic entity, so notice how they stack without conflicting. @Entity/@Table set up the basic table mapping and a uniqueness rule on email. @Id/@GeneratedValue handle the primary key. @Embedded pulls in the Address value object's columns directly (no separate table, no join). @Enumerated(STRING) makes the status column human-readable. @OneToMany + @OrderBy exposes this customer's orders, pre-sorted, with cascading deletes handled automatically. And @Version + @CreatedDate (backed by @EntityListeners) add safety and bookkeeping without any manual code in the service layer. Nothing here is new — it's the same annotations you've already seen, just all working together on one class the way they would in a real codebase.

MongoDB — Spring Data

org.springframework.data.mongodb.core.mapping

No tables, no foreign keys, no joins — the annotations here mostly control document/collection naming, indexes, and the choice between embedding data and referencing another collection.

01Document mapping

AnnotationPurposeKey attributes
@DocumentMarks a class as mapping to a MongoDB collection.collection — name override; defaults to the decapitalized class name.
@IdMaps the field to Mongo's _id.Different import from JPA's — org.springframework.data.annotation.Id. If a String-typed @Id is left null on save, Spring auto-generates an ObjectId hex string.
@FieldCustomizes the stored field name and type.name, order, targetType — e.g. force an enum to store as STRING.
@TransientExcludes a field from persistence.org.springframework.data.annotation.Transient (the plain Java transient keyword also works).
Java — Product document
@Document(collection = "products") // this class maps to the "products" collection in MongoDB
public class Product {

    @Id // maps to Mongo's own "_id" field — note: org.springframework.data.annotation.Id, NOT JPA's @Id
    private String id;              // left null on save() -> Spring auto-generates an ObjectId hex string for you

    @Field("display_name") // stored in the document as "display_name", not "name"
    private String name;

    private BigDecimal price;      // no annotation needed — stored as a field literally called "price"

    @Field(targetType = FieldType.STRING) // force this enum to be stored as text, e.g. "IN_STOCK"
    private StockStatus stockStatus;    // (STRING is already Spring Data Mongo's default for enums)

    @Transient // never written to or read from the document at all
    private BigDecimal discountPreview; // e.g. computed in the service layer for a UI preview
}
🔎

In plain English: @Document is Mongo's equivalent of JPA's @Entity — it says "this class is a whole record stored in its own collection," here named products. There's no schema to define up front (Mongo is schemaless), so most fields need zero annotations — a plain price field just becomes a price key in the stored JSON document. You only reach for @Field when you want the stored name to differ from the Java field name, or to force a specific storage type. The trickiest gotcha here: Mongo's @Id comes from a completely different package than JPA's @Id — mixing up the import is the single most common copy-paste mistake between the SQL and Mongo sides of a codebase (see the gotcha box in the Compare section further down).

02Indexing

AnnotationPurposeKey attributes
@IndexedCreates a single-field index.unique, direction, sparse, expireAfterSeconds — the last one turns it into a TTL index that auto-deletes documents.
@CompoundIndexDeclares a multi-field index at the class level.name, def = "{'field1': 1, 'field2': -1}", unique.
@TextIndexedIncludes a field in the collection's full-text search index.weight — relative ranking weight. Only one text index allowed per collection.
@ShardedMarks the shard key for a sharded collection (Spring Data MongoDB 4.1+).shardKey.
Java — indexed Order document
@Document(collection = "orders")
@CompoundIndex(name = "customer_status_idx", def = "{'customerId': 1, 'status': 1}")
// ^ ONE index across two fields together — speeds up queries that filter by BOTH customerId AND status
public class Order {

    @Id
    private String id;

    @Indexed(unique = true)
    private String orderNumber;      // single-field index + a uniqueness rule enforced by MongoDB itself

    @TextIndexed(weight = 2)
    private String description;      // included in the collection's ONE allowed full-text search index

    @Indexed(expireAfterSeconds = 2592000)
    private Instant placedAt;         // TTL index — MongoDB auto-deletes this document 30 days after placedAt

    private String customerId;        // no @Indexed here — only queried through the compound index above
    private OrderStatus status;
}
🔎

In plain English: an index is just a lookup shortcut so MongoDB doesn't have to scan every document to answer a query. @Indexed builds one on a single field — add unique = true and Mongo will also reject duplicate values outright, like orderNumber above. @CompoundIndex is for queries that always filter on the combination of two or more fields together (customer + status) — a single-field index on each wouldn't be as efficient. @TextIndexed is specifically for free-text search (like a search box), and Mongo only allows one per collection, across however many fields you mark. @Indexed(expireAfterSeconds=) is the odd one out — it's not really about lookup speed at all, it's a TTL (time-to-live) index that has MongoDB silently delete the document once that many seconds have passed since the indexed timestamp.

⚠️

These annotations alone don't guarantee the index exists. spring.data.mongodb.auto-index-creation defaults to false in current Spring Boot — annotated indexes are only created automatically if you turn that on, otherwise they're purely documentation until you create the indexes yourself (migration script, mongosh, or an IndexOperations call on startup).

03Embedding & references

Mongo has no @OneToMany/@ManyToOne — modeling a relationship is a design choice between embedding (nest the data, no annotation needed) and referencing (store a pointer to another collection).

ApproachHowTrade-off
EmbedA plain POJO or List<Pojo> field — no annotation at all, it's the default.One read gets everything; the embedded data can't sensibly be queried/updated on its own or shared across parents.
@DBRefStores a reference (collection + _id) instead of embedding.lazy = true defers the load. Each reference resolves as a separate query — an N+1 risk — and there's no built-in cascading delete.
@DocumentReferenceNewer, more flexible replacement for @DBRef (Spring Data MongoDB 4+).Can reference by any field (not just _id), supports a custom lookup query, and plays better with reactive repositories.
Manual id fieldJust store the related document's id as a plain String/ObjectId field, resolve it yourself in the service layer.Most explicit and most common in practice — full control over when/how the second document is fetched.
Java — three ways to model "customer has orders"
// (a) embed — orders live INSIDE the customer document, as a nested array of JSON objects
private List<Order> orders;
// -> one read gets the customer AND all their orders in a single round trip
// -> but you can't query/update ONE order without loading the whole customer document

// (b) @DBRef — orders stay in their OWN "orders" collection; this field stores a pointer to them
@DBRef(lazy = true)
private List<Order> orders;
// -> lazy=true: don't resolve the referenced Order documents until this field is actually accessed
// -> each Order in the list = a separate query to resolve — an N+1 risk if you loop over many customers

// (c) @DocumentReference — the modern equivalent, more control over the lookup
@DocumentReference(lazy = true)
private List<Order> orders;
// -> same idea as @DBRef, but can reference by any field (not just _id) and works with reactive repos

// (d) manual reference — just an id, resolved explicitly in the service
private List<String> orderIds;
// -> Spring does nothing automatically here; YOU call orderRepository.findAllById(orderIds) when needed
// -> most explicit option — full control over when the second query actually happens
🔎

In plain English: Mongo has no foreign keys, so "how does a Customer relate to their Orders" is a design decision you make yourself, not something an annotation enforces. Option (a), embedding, is the Mongo-native default — no annotation at all, the order data is physically nested inside the customer's JSON document. That's fast to read but means the orders can't be queried on their own or shared with anything else. Options (b) and (c) keep orders in their own collection and just store a reference (like a foreign key) — @DBRef is the older, built-in way; @DocumentReference is the newer, more flexible replacement. Option (d) skips Spring's automatic resolution entirely and just stores plain ids you look up yourself — more code, but no hidden queries and no surprises about when data gets fetched.

💡

Rule of thumb: embed data that's always read together and rarely updated independently (an Address, line items on an order at the moment it was placed). Reference data that has its own lifecycle, grows unbounded, or is shared across many parents (a Customer's full order history).

@Configuration
@EnableMongoAuditing // turns auditing ON for every @Document — no per-class listener needed, unlike JPA
public class MongoAuditingConfig {
    @Bean
    public AuditorAware<String> auditorProvider() {
        return () -> Optional.of(SecurityContextHolder.getContext().getAuthentication().getName());
    }
}

@Document(collection = "orders") // no @EntityListeners here — Mongo's mapping converter applies auditing automatically
public class Order {
    @Id
    private String id;

    @Version
    private Long version;           // same idea as JPA's @Version — checked before overwriting the document

    @CreatedDate
    private Instant createdAt;     // set once, automatically, on first insert

    @LastModifiedDate
    private Instant updatedAt;     // re-set automatically on every save() after that

    @CreatedBy
    private String createdBy;      // from the SAME AuditorAware bean type used on the JPA side

    @LastModifiedBy
    private String lastModifiedBy;
}
🔎

In plain English: this is functionally identical to the JPA auditing example — same four field annotations, same AuditorAware bean for "who is the current user." The one real difference is ceremony: JPA needs @EntityListeners(AuditingEntityListener.class) stamped on every single entity you want audited, or the fields silently stay null. Mongo doesn't — once @EnableMongoAuditing is set up globally, every @Document class gets audited automatically, no per-class annotation required.

💡

Unlike JPA, Mongo documents don't need an @EntityListeners-style annotation for auditing to work — once @EnableMongoAuditing is present, the mapping converter applies it to every document automatically.

05Repository & query annotations

AnnotationPurposeKey attributes / notes
@QuerySupplies a raw MongoDB JSON query for a repository method.value, fields — a projection document.

Java — repository
public interface OrderRepository extends MongoRepository<Order, String> {
    // extending MongoRepository already gives you save(), findById(), findAll(), delete() for free

    @Query("{ 'customerId': ?0, 'status': ?1 }")
    // ^ raw MongoDB JSON filter — ?0/?1 are positional placeholders for the method's arguments, in order
    List<Order> findByCustomerAndStatus(String customerId, String status);

    @Aggregation(pipeline = {
        "{ $match: { status: 'COMPLETED' } }",                              // stage 1: keep only completed orders
        "{ $group: { _id: '$customerId', total: { $sum: '$amount' } } }"  // stage 2: sum amount per customer
    })
    // ^ a real MongoDB aggregation pipeline — for reporting/analytics queries a simple filter can't express
    List<CustomerSpend> totalSpendPerCustomer();
}
🔎

In plain English: just like JpaRepository, extending MongoRepository<Order, String> gives you basic CRUD for free, and Spring can also auto-generate simple finders from method names alone (no annotation needed) — these two annotations are for when that's not enough. @Query here takes literal MongoDB JSON syntax instead of JPQL, since there's no SQL-like query language on the Mongo side; the ?0/?1 placeholders just mean "first argument," "second argument." @Aggregation is for genuinely different kinds of questions — not "find these documents" but "compute something across many of them," like totaling spend per customer, which is what MongoDB's aggregation pipeline (a sequence of `$match`/`$group`/etc. stages) is built for.

06Full example, put together

Java — Customer / Order model
@Document(collection = "customers")                // this class -> the "customers" collection
public class Customer {

    @Id
    private String id; // maps to _id; null on save() -> Spring generates an ObjectId hex string

    @Field("full_name")                              // stored as "full_name" in the document, not "fullName"
    private String fullName;

    @Indexed(unique = true)                             // fast lookups by email + DB-enforced no-duplicates rule
    private String email;

    private Address billingAddress; // embedded automatically — plain POJO, no annotation, nested right in this document

    @Field(targetType = FieldType.STRING)               // stored as e.g. "ACTIVE" rather than a number
    private CustomerStatus status;

    @DBRef(lazy = true)
    private List<Order> orders; // referenced — lives in its own "orders" collection, resolved on access

    @Version                                           // optimistic locking, same idea as JPA
    private Long version;

    @CreatedDate                                       // requires @EnableMongoAuditing — no listener annotation needed here
    private Instant createdAt;
}

@Document(collection = "orders")
@CompoundIndex(name = "customer_status_idx", def = "{'customerId': 1, 'status': 1}")
// ^ speeds up queries filtering by BOTH customerId and status together (e.g. this customer's pending orders)
public class Order {

    @Id
    private String id;

    private String customerId;             // plain field — no @Indexed, only queried via the compound index above
    private List<OrderItem> items; // embedded — line items belong to this order alone, never shared

    @Indexed(expireAfterSeconds = 2592000) // TTL index — this document is auto-deleted 30 days after placedAt
    private Instant placedAt;
}
🔎

In plain English: same idea as the SQL full example — every Mongo annotation you've now seen, combined onto one realistic pair of documents. Notice the design choice baked in: Customer.orders is referenced via @DBRef (because a customer's order history grows without bound and shouldn't bloat every customer read), while Order.items is embedded as a plain list (because line items are only ever meaningful attached to their one order, and are read together with it). That's the embed-vs-reference rule of thumb from §03 applied in practice, sitting right next to indexing, auditing, and enum storage on the same two classes.

Same annotation name, different import — the classic mistake. JPA's @Id, @Version, and @Transient come from jakarta.persistence. Mongo's come from org.springframework.data.annotation. @CreatedDate/@LastModifiedDate/@CreatedBy/@LastModifiedBy are the one genuine exception — those are always org.springframework.data.annotation.* and work identically on both sides, since they live in the shared spring-data-commons module both projects build on.

Bonus: what usually sits right next to these

not persistence, but always nearby

Two annotation families that show up on almost every model class but aren't actually about persistence — worth knowing where the line is.

AnnotationFromPurpose
@NotNull / @NotBlank / @NotEmptyJakarta Bean ValidationRejects null / blank / empty values — enforced at the API/service boundary via @Valid, not by the database.
@Size / @Min / @MaxJakarta Bean ValidationBounds a string length or numeric range before it ever reaches persistence code.
@Email / @PatternJakarta Bean ValidationFormat validation via a built-in check or a custom regex.
@Data / @Getter / @SetterLombokGenerates accessors (and equals/hashCode/toString for @Data) so entities don't carry hand-written boilerplate.
@NoArgsConstructor / @AllArgsConstructorLombokJPA specifically requires a no-args constructor on every entity — easy to forget without Lombok generating it.
@BuilderLombokFluent construction for entities/documents with many optional fields.
Java — validation + Lombok, on top of persistence annotations
@Entity
@Data                        // Lombok: generates getters, setters, equals/hashCode, toString at compile time
@NoArgsConstructor          // Lombok: empty constructor — JPA REQUIRES this to exist on every entity
@AllArgsConstructor         // Lombok: constructor taking every field, handy for tests/builders
@Builder                     // Lombok: enables Customer.builder().fullName("...").email("...").build()
public class Customer {

    @Id @GeneratedValue
    private Long id;

    @NotBlank(message = "Full name is required")
    @Size(max = 120)     // enforced by @Valid at the controller/service boundary — NOT by the database
    private String fullName;

    @Email                // checks it looks like a real email address BEFORE it ever reaches persistence code
    @NotBlank
    private String email;

    @Min(0) @Max(100)  // keeps a percentage-style field inside a sane range
    private int loyaltyDiscountPercent;
}

// elsewhere, in a controller:
@PostMapping("/customers")
public Customer create(@Valid @RequestBody Customer customer) {
    // @Valid triggers the @NotBlank/@Size/@Email/@Min/@Max checks above — invalid requests
    // never even reach this method body, Spring returns a 400 automatically
    return customerRepository.save(customer);
}
🔎

In plain English: these two families sit right next to persistence annotations on the same class but do a completely different job. Bean Validation (@NotBlank, @Size, @Email, @Min/@Max) checks that incoming data is sensible before it's ever saved — it's enforced in application code when something calls @Valid (typically a REST controller), and a bad request never reaches the database at all. It's a different layer from a database constraint like @Column(nullable=false), which only fires when Hibernate actually tries to write the row. Lombok, meanwhile, isn't about correctness at all — @Data/@NoArgsConstructor/@AllArgsConstructor/@Builder just generate boilerplate code (getters, setters, constructors) at compile time so you don't hand-write it. The one Lombok annotation that actually matters functionally for JPA is @NoArgsConstructor — Hibernate needs a no-args constructor to instantiate entities via reflection when loading rows from the database, and forgetting one is a classic runtime error.
