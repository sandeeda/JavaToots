01
Basic The Throwable Hierarchy
Everything throwable in Java extends Throwable. It splits into Error (JVM-level disasters you can't recover from) and Exception (problems your code can reasonably handle). Exception splits again into checked (compiler forces you to handle it) and RuntimeException (unchecked — compiler says nothing).
🏥

Hospital triage: Error = the building is on fire, evacuate, don't try to "handle" it. Exception = a patient with a treatable condition — checked exceptions are conditions the hospital's protocol *requires* a treatment plan for before discharge; unchecked are conditions you're trusted to notice yourself.

Java
public class Main {
  public static void main(String[] args) {
    // Error — extends Error, NOT Exception. Don't catch these.
    try {
      recurse(0);
    } catch (StackOverflowError e) {
      System.out.println("Caught an Error (you usually shouldn't): " + e);
    }

    // RuntimeException — unchecked, compiler doesn't force a catch
    try {
      int[] arr = new int[3];
      System.out.println(arr[10]);
    } catch (ArrayIndexOutOfBoundsException e) {
      System.out.println("Caught unchecked: " + e.getMessage());
    }

    // Checked exception — compiler FORCES a try/catch or throws
    try {
      throw new java.io.IOException("disk full");
    } catch (java.io.IOException e) {
      System.out.println("Caught checked: " + e.getMessage());
    }
  }

  static void recurse(int depth) { recurse(depth + 1); } // blows the stack on purpose
}
Output
Caught an Error (you usually shouldn't): java.lang.StackOverflowError Caught unchecked: Index 10 out of bounds for length 3 Caught checked: disk full
💡

Throwable → Error | Exception → RuntimeException (unchecked) | everything else under Exception is checked. Catch Exception, never Error or bare Throwable, in application code.

02
Basic try / catch / finally
finally always runs — even if try returns, even if catch throws. The one gotcha: a return inside finally silently overrides a return from try, swallowing the original value with no warning.
Java
public class Main {
  public static void main(String[] args) {
    System.out.println(trap());      // 99 — NOT 1!
    System.out.println(normal());     // 1, as expected
  }

  static int trap() {
    try {
      return 1;
    } finally {
      return 99; // ⚠️ overrides the try's return — almost always a bug
    }
  }

  static int normal() {
    try {
      return 1;
    } finally {
      System.out.println("cleanup runs, but doesn't return anything");
    }
  }
}
Output
cleanup runs, but doesn't return anything 99 1
💡

Never put a return (or throw) inside finally unless you mean to discard whatever the try/catch was about to return. Use finally only for cleanup — closing streams, releasing locks.

03
Basic Checked vs Unchecked
Checked exceptions (extend Exception directly) must be caught or declared with throws — the compiler enforces it. Unchecked (extend RuntimeException) need no such declaration. Modern Java APIs (Spring, most new libraries) lean heavily unchecked — it's controversial, but the argument is that checked exceptions leak implementation details into every caller's signature.
Java
import java.io.IOException;

public class Main {

  // Checked — caller is FORCED to handle or declare this
  static void readFile() throws IOException {
    throw new IOException("file not found");
  }

  // Unchecked — caller is NOT forced to do anything
  static void validate(int age) {
    if (age < 0) throw new IllegalArgumentException("age can't be negative: " + age);
  }

  public static void main(String[] args) {
    try { readFile(); } catch (IOException e) { System.out.println("Handled checked: " + e.getMessage()); }

    try { validate(-5); } catch (IllegalArgumentException e) { System.out.println("Handled unchecked: " + e.getMessage()); }
  }
}
💡

Checked = "the compiler makes you prove you thought about this." Unchecked = "trust the developer." For new public APIs, prefer unchecked unless the caller genuinely has a recovery action to take.

04
Basic Custom Exceptions
Extend RuntimeException for an unchecked custom exception, or Exception for checked. Always provide a constructor that accepts a message and, ideally, a cause — you'll need both in production.
Java
public class Main {

  // Unchecked custom exception — most common choice today
  static class InsufficientFundsException extends RuntimeException {
    private final double shortfall;

    public InsufficientFundsException(String message, double shortfall) {
      super(message);
      this.shortfall = shortfall;
    }

    public double getShortfall() { return shortfall; }
  }

  static void withdraw(double balance, double amount) {
    if (amount > balance)
      throw new InsufficientFundsException("Cannot withdraw $" + amount, amount - balance);
    System.out.println("Withdrew $" + amount);
  }

  public static void main(String[] args) {
    try {
      withdraw(100.0, 250.0);
    } catch (InsufficientFundsException e) {
      System.out.println(e.getMessage() + " — short by $" + e.getShortfall());
    }
  }
}
Output
Cannot withdraw $250.0 — short by $150.0
💡

Add fields to your custom exception (like shortfall) when the catcher needs structured data, not just a string. Name it for what went wrong, not for the layer it happened in.

05
Basic try-with-resources
Anything implementing AutoCloseable can go in the parentheses after try — Java calls .close() automatically, even if an exception is thrown, in reverse declaration order. No more forgetting to close a stream in finally.
Java
public class Main {

  static class Resource implements AutoCloseable {
    private final String name;
    Resource(String name) { this.name = name; System.out.println("opened " + name); }
    void use() { System.out.println("using " + name); }
    @Override
    public void close() { System.out.println("closed " + name); } // called automatically
  }

  public static void main(String[] args) {
    try (Resource a = new Resource("A"); Resource b = new Resource("B")) {
      a.use();
      b.use();
      throw new RuntimeException("boom"); // both still get closed!
    } catch (RuntimeException e) {
      System.out.println("caught: " + e.getMessage());
    }
  }
}
Output
opened A opened B using A using B closed B ← reverse order! closed A caught: boom
💡

Resources close in reverse order of declaration (B before A) — same idea as unwinding a stack. If close() itself throws while the body is already throwing, the close's exception becomes a suppressed exception, retrievable via e.getSuppressed().

06
Intermediate Multi-catch
Catch several unrelated exception types in one block with |, instead of duplicating the same handler body. Catch blocks must be ordered subclass before superclass — catching the superclass first makes the subclass catch unreachable and is a compile error.
Java
import java.io.IOException;
import java.sql.SQLException;

public class Main {

  static void doWork(int mode) throws IOException, SQLException {
    if (mode == 1) throw new IOException("disk error");
    if (mode == 2) throw new SQLException("db error");
  }

  public static void main(String[] args) {
    for (int mode = 1; mode <= 2; mode++) {
      try {
        doWork(mode);
      } catch (IOException | SQLException e) { // one handler, two unrelated types
        System.out.println(e.getClass().getSimpleName() + ": " + e.getMessage());
      }
    }
  }
}
Output
IOException: disk error SQLException: db error
💡

In a multi-catch, the exception variable (e) is implicitly final and typed as the nearest common supertype — you can't reassign it, and you only get the methods both types share.

07
Intermediate Exception Chaining
When you catch a low-level exception and throw a higher-level one, pass the original as the cause: new MyException("msg", originalException). Skip this and you've thrown away the root cause forever — a production debugging nightmare.
🔗

Police report: "Car crashed" is the new exception. "Because the brakes failed, because a hose burst" is the chained cause. Drop the cause and all you're left with is "car crashed" — true, but useless for fixing anything.

Java
import java.sql.SQLException;

public class Main {

  static class OrderServiceException extends RuntimeException {
    public OrderServiceException(String message, Throwable cause) {
      super(message, cause); // 🔗 preserves the original stack trace
    }
  }

  static void saveOrder() throws SQLException {
    throw new SQLException("connection timed out");
  }

  static void placeOrder() {
    try {
      saveOrder();
    } catch (SQLException e) {
      throw new OrderServiceException("Could not place order", e); // chain it!
    }
  }

  public static void main(String[] args) {
    try {
      placeOrder();
    } catch (OrderServiceException e) {
      System.out.println("Top-level: " + e.getMessage());
      System.out.println("Root cause: " + e.getCause());
    }
  }
}
Output
Top-level: Could not place order Root cause: java.sql.SQLException: connection timed out
💡

Never write catch (SQLException e) { throw new RuntimeException("failed"); } without passing e as the cause — that's throwing away the one piece of information that explains why.

08
Intermediate Anti-Patterns
The four classics: swallowing (empty catch block, error vanishes silently), catching too broad (catch (Exception e) hides bugs you didn't mean to catch), double-logging (log it AND rethrow it — now it's logged 3 times up the stack), and exceptions as control flow (using throw/catch instead of a normal if/return).
Java
public class Main {

  public static void main(String[] args) {

    // ❌ ANTI-PATTERN 1: swallowed — caller has NO idea this failed
    try {
      risky();
    } catch (Exception e) { /* nothing — the bug just disappears */ }

    // ❌ ANTI-PATTERN 2: catching too broad — also catches NullPointerException,
    // ClassCastException, bugs you actually wanted to crash loudly on
    try {
      risky();
    } catch (Exception e) {
      System.out.println("something failed, who knows what");
    }

    // ✅ FIX: catch the SPECIFIC exception, log with context, decide: handle or rethrow
    try {
      risky();
    } catch (IllegalStateException e) {
      System.out.println("Order processing failed: " + e.getMessage()); // log ONCE, here
      throw e; // rethrow — don't ALSO log it again at the next catch up the stack
    }
  }

  static void risky() { throw new IllegalStateException("order already shipped"); }
}
💡

An empty catch block is the single most dangerous line you can write — it converts a loud failure into silent data corruption. If you genuinely have nothing to do, at minimum log it.

09
Intermediate Exceptions in Lambdas & Streams
Functional interfaces like Function<T,R> don't declare throws — so a lambda that calls a method which throws a checked exception won't even compile. You either wrap it in a try/catch inside the lambda, or wrap the checked exception in an unchecked one.
Java
import java.net.MalformedURLException;
import java.net.URI;
import java.util.List;
import java.util.stream.Collectors;

public class Main {

  public static void main(String[] args) {
    List<String> urls = List.of("https://a.com", "https://b.com");

    List<URI> parsed = urls.stream()
        .map(Main::toUriUnchecked) // the checked exception is wrapped INSIDE this method
        .collect(Collectors.toList());

    parsed.forEach(System.out::println);
  }

  // URI.create() actually throws unchecked already, but imagine it threw checked —
  // this is the standard wrapping pattern for that case:
  static URI toUriUnchecked(String s) {
    try {
      return new URI(s);
    } catch (Exception e) {
      throw new RuntimeException("bad URL: " + s, e); // checked → unchecked, with cause preserved
    }
  }
}
Output
https://a.com https://b.com
💡

This is the most common reason teams move away from checked exceptions entirely: they're painful to use inside streams, and the standard workaround (wrap-and-rethrow-unchecked) just reintroduces the unchecked behaviour anyway.

10
Intermediate Reading a Stack Trace
Read a stack trace top to bottom: the first line is the exception that was thrown; each "at" line below is a stack frame, with the deepest call (where it actually broke) at the top. "Caused by:" sections show chained exceptions, oldest cause at the bottom.
Java
public class Main {
  public static void main(String[] args) {
    a();
  }
  static void a() { b(); }
  static void b() { c(); }
  static void c() { throw new IllegalStateException("something broke in c()"); }
}
Output (uncaught — printed by the JVM)
Exception in thread "main" java.lang.IllegalStateException: something broke in c() at Main.c(Main.java:7) ← READ FROM HERE — deepest frame, where it threw at Main.b(Main.java:6) at Main.a(Main.java:5) at Main.main(Main.java:3) ← entry point, at the bottom
💡

Never use e.printStackTrace() in production code — it writes to stderr with no log level, no timestamp, no correlation ID. Use a logging framework (logger.error("...", e)) so it's captured, searchable, and routed properly.

11
Advanced @ControllerAdvice / @ExceptionHandler
Without this, an uncaught exception in a Spring Boot controller returns a raw stack-trace-laden 500 page to the client. @ControllerAdvice + @ExceptionHandler centralizes "what HTTP response does each exception type map to" in one place, instead of try/catch in every controller method. Notice the controller and service below have zero try/catch — that's the whole point.
Java
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.stereotype.Service;
import org.springframework.web.bind.annotation.*;

import java.util.Map;

// Controller — thin. No try/catch: it calls the service and lets exceptions bubble up.
@RestController
@RequestMapping("/accounts")
public class AccountController {

  private final AccountService accountService;

  public AccountController(AccountService accountService) {
    this.accountService = accountService;
  }

  @PostMapping("/{id}/withdraw")
  public ResponseEntity<Void> withdraw(@PathVariable String id, @RequestParam double amount) {
    accountService.withdraw(id, amount); // may throw — nothing catches it here, on purpose
    return ResponseEntity.ok().build();
  }
}

// Service — owns the business rule, throws when it's violated
@Service
public class AccountService {

  public void withdraw(String accountId, double amount) {
    double balance = 100.0; // pretend this came from a repository
    if (amount > balance) {
      throw new InsufficientFundsException("Cannot withdraw $" + amount, amount - balance);
    }
    // ...withdraw
  }
}

@RestControllerAdvice
// @RestControllerAdvice = @ControllerAdvice + @ResponseBody — applies across ALL controllers
public class GlobalExceptionHandler {

  @ExceptionHandler(InsufficientFundsException.class)
  public ResponseEntity<Map<String, String>> handleInsufficientFunds(InsufficientFundsException e) {
    return ResponseEntity.status(HttpStatus.UNPROCESSABLE_ENTITY)
        .body(Map.of("error", e.getMessage()));
  }

  @ExceptionHandler(IllegalArgumentException.class)
  public ResponseEntity<Map<String, String>> handleBadInput(IllegalArgumentException e) {
    return ResponseEntity.badRequest().body(Map.of("error", e.getMessage()));
  }

  // catch-all — never let an unmapped exception leak a raw stack trace to the client
  @ExceptionHandler(Exception.class)
  public ResponseEntity<Map<String, String>> handleAnythingElse(Exception e) {
    return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
        .body(Map.of("error", "Something went wrong")); // never leak e.getMessage() to clients here
  }
}
💡

Trace the flow: AccountController calls AccountService.withdraw() with no try/catch → the service throws InsufficientFundsException → it propagates all the way up, past the controller, to GlobalExceptionHandler. Order also matters: Spring picks the most specific matching @ExceptionHandler, so a generic Exception.class catch-all is safe to include — it only fires when nothing more specific matched.

Advanced Exception Performance
Throwing an exception is expensive mainly because of fillInStackTrace() — capturing the entire call stack at the moment of construction. A try/catch block that never throws costs almost nothing; the cost is entirely in the throw, not the try. Never use exceptions for routine, expected control flow in a hot loop.
Java
public class Main {

  public static void main(String[] args) {
    int iterations = 200_000;

    // ❌ using exceptions as control flow — fillInStackTrace() runs 200,000 times
    long start1 = System.nanoTime();
    for (int i = 0; i < iterations; i++) {
      try {
        throw new RuntimeException("not really exceptional");
      } catch (RuntimeException e) { /* ignored */ }
    }
    long exceptionMs = (System.nanoTime() - start1) / 1_000_000;

    // ✅ same outcome with a plain boolean check — no stack capture at all
    long start2 = System.nanoTime();
    for (int i = 0; i < iterations; i++) {
      boolean failed = true;
      if (failed) { /* handle normally */ }
    }
    long normalMs = (System.nanoTime() - start2) / 1_000_000;

    System.out.println("Exception-based: " + exceptionMs + "ms");
    System.out.println("Boolean-based:    " + normalMs + "ms");
  }
}
Output (typical — your numbers will vary)
Exception-based: 180ms Boolean-based: 2ms
💡

Exceptions are for the exceptional: things that shouldn't normally happen. "User not found" in a lookup that's called constantly is normal, expected, and should be an Optional or a null check — not a thrown exception.

Advanced Custom Exception Hierarchies
Real systems build a small hierarchy: one base exception with shared fields (an error code, HTTP status hint), and specific subclasses for each failure type. Callers can catch broadly (the base) or narrowly (a specific subclass) depending on what they need.
Java
public class Main {

  // Base — every domain exception carries an error code
  static abstract class ApplicationException extends RuntimeException {
    private final String errorCode;
    protected ApplicationException(String errorCode, String message) {
      super(message);
      this.errorCode = errorCode;
    }
    public String getErrorCode() { return errorCode; }
  }

  static class ResourceNotFoundException extends ApplicationException {
    public ResourceNotFoundException(String resource, String id) {
      super("NOT_FOUND", resource + " " + id + " was not found");
    }
  }

  static class ValidationException extends ApplicationException {
    public ValidationException(String field, String reason) {
      super("VALIDATION_FAILED", field + ": " + reason);
    }
  }

  public static void main(String[] args) {
    ApplicationException[] failures = {
      new ResourceNotFoundException("Order", "#1001"),
      new ValidationException("email", "must not be blank")
    };

    for (ApplicationException e : failures) { // caught generically, handled by code
      System.out.println("[" + e.getErrorCode() + "] " + e.getMessage());
    }
  }
}
Output
[NOT_FOUND] Order #1001 was not found [VALIDATION_FAILED] email: must not be blank
💡

A shared base means a single @ExceptionHandler(ApplicationException.class) can build a consistent { "errorCode": ..., "message": ... } JSON shape for every domain error, while still letting you catch a specific subtype where you need to react differently.

Advanced Senior Interview FAQ
Five questions interviewers love, with the answer a senior candidate is expected to give.
Java
// Q: "Checked vs unchecked — what would you pick for a new public API, and why?"
// A: Default to unchecked. Checked exceptions force every caller up the stack to either
//    handle or re-declare them, which leaks your implementation details into call signatures
//    several layers away that have no way to actually recover. Reserve checked exceptions
//    for cases where the immediate caller has a real, specific recovery action available.

// Q: "What happens if an exception is thrown inside a finally block?"
// A: It propagates and SUPPRESSES whatever the try/catch was about to throw or return —
//    silently. This is exactly why finally should only contain cleanup, never logic that
//    can itself fail and change control flow (concept 2).

// Q: "Difference between 'throw' and 'throws'?"
// A: 'throw' is a statement — it actually raises an exception instance, right now, at this
//    line. 'throws' is part of a method SIGNATURE — it declares that this method might
//    propagate a checked exception, so callers know to handle it.

// Q: "Difference between Error and Exception — should you ever catch Error?"
// A: Error signals a problem the JVM itself is in trouble over (OutOfMemoryError,
//    StackOverflowError) — almost never recoverable. Catching Exception is normal;
//    catching Error is a code smell outside of very specific cases (e.g. a test harness
//    that needs to report a StackOverflowError as a test failure rather than crashing).

// Q: "Why is an empty catch block worse than not catching at all?"
// A: An uncaught exception fails LOUDLY — it crashes the thread/request and shows up in
//    logs/monitoring immediately. An empty catch block fails SILENTLY — the program keeps
//    running with corrupted or missing state, and you find out days later when the
//    downstream damage is much harder to trace back to the root cause.
💡

Senior interviews aren't testing whether you can recite the hierarchy — they're testing whether you've been burned by a swallowed exception in production and changed how you write code because of it.
