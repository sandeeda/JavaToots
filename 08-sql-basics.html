01
Basic The Relational Model
A relational database stores data in tables (rows & columns). Each row is one record. Each column is one attribute. A primary key uniquely identifies every row — no two rows can share one.
📒

Spreadsheet analogy: A table is a sheet. Each row is one entry. The primary key is like a row number that's guaranteed never to repeat or change.

PostgreSQL
-- A "users" table: each row = one person
-- id is the PRIMARY KEY — unique, never reused
SELECT * FROM users;

-- id | username  | email                | created_at
-- ---+-----------+----------------------+------------
-- 1  | sandeep   | sandeep@email.com    | 2026-01-04
-- 2  | priya     | priya@email.com      | 2026-02-11

-- A "orders" table: each row = one order, LINKED to a user via user_id
SELECT * FROM orders;

-- id | user_id | total  | status
-- ---+---------+--------+--------
-- 101| 1       | 49.99  | SHIPPED
-- 102| 1       | 12.50  | PENDING
-- 103| 2       | 99.00  | SHIPPED
💡

Tables are connected by shared key values — orders.user_id matches users.id. This relationship is the entire point of "relational" databases, and is what JOINs (concept 5) exploit.

02
Basic CREATE TABLE
Before you can store anything, you declare the table's shape: column names, data types, and constraints (rules the database enforces for you, always, on every write).
PostgreSQL
CREATE TABLE users (
  id         SERIAL PRIMARY KEY,           -- auto-incrementing integer
  username   VARCHAR(50) NOT NULL UNIQUE,  -- required, no duplicates
  email      VARCHAR(255) NOT NULL UNIQUE,
  created_at TIMESTAMP NOT NULL DEFAULT NOW()  -- auto-filled if omitted
);

CREATE TABLE orders (
  id      SERIAL PRIMARY KEY,
  user_id INTEGER NOT NULL REFERENCES users(id), -- foreign key, see concept 4
  total   NUMERIC(10,2) NOT NULL DEFAULT 0.00,
  status  VARCHAR(20) NOT NULL DEFAULT 'PENDING'
);

-- inserting a row that violates NOT NULL UNIQUE fails immediately —
-- the database is enforcing the rule for you, every single time
INSERT INTO users (username, email) VALUES ('sandeep', 'sandeep@email.com');
INSERT INTO users (username, email) VALUES ('sandeep', 'x@email.com');
-- ERROR: duplicate key value violates unique constraint "users_username_key"
💡

Constraints (NOT NULL, UNIQUE, REFERENCES) are not "nice to have" documentation — the database physically refuses any write that breaks them, even from buggy application code.

03
Basic INSERT, SELECT, WHERE, ORDER BY, LIMIT
The four verbs you'll type 1000 times a day: write a row in, then read rows back out, filtered and sorted exactly how you want.
PostgreSQL
CREATE TABLE products (
  id    SERIAL PRIMARY KEY,
  name  VARCHAR(100) NOT NULL,
  price NUMERIC(10,2) NOT NULL,
  stock INTEGER NOT NULL DEFAULT 0
);

INSERT INTO products (name, price, stock) VALUES
  ('Keyboard', 49.99, 120),
  ('Monitor',  219.00, 35),
  ('Mouse',    19.99, 300),
  ('Webcam',   59.50, 0);

-- filter + sort + limit, all in one query
SELECT name, price, stock
FROM products
WHERE stock > 0
ORDER BY price DESC
LIMIT 2;
Output
name | price | stock ----------+--------+------- Monitor | 219.00 | 35 Webcam | 59.50 | 0 -- wait, stock=0 so this is EXCLUDED Keyboard | 49.99 | 120
💡

WHERE filters rows before sorting/limiting. The Webcam (stock 0) never makes it into the result — WHERE stock > 0 excluded it before ORDER BY even ran.

04
Basic Foreign Keys & Referential Integrity
A foreign key says "this column must match a real row in another table." It stops orphaned data — an order pointing at a user that doesn't exist — before it can ever be written.
🔗

Coat-check ticket: Your ticket number is meaningless unless a coat with that exact number is hanging on the rack. A foreign key is the database refusing to hand you a ticket for a coat that was never checked in.

PostgreSQL
CREATE TABLE users (
  id       SERIAL PRIMARY KEY,
  username VARCHAR(50) NOT NULL
);

CREATE TABLE orders (
  id      SERIAL PRIMARY KEY,
  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  total   NUMERIC(10,2) NOT NULL
);

INSERT INTO users (username) VALUES ('sandeep'); -- id = 1
INSERT INTO orders (user_id, total) VALUES (1, 49.99); -- fine, user 1 exists

INSERT INTO orders (user_id, total) VALUES (999, 10.00);
-- ERROR: insert or update on table "orders" violates foreign key constraint
-- DETAIL: Key (user_id)=(999) is not present in table "users".

-- ON DELETE CASCADE: deleting the user auto-deletes their orders too
DELETE FROM users WHERE id = 1;
SELECT * FROM orders; -- empty — the order for user 1 is gone too
💡

ON DELETE CASCADE auto-deletes children. ON DELETE RESTRICT (often the default) instead blocks the delete while children exist — pick CASCADE only when "delete the parent, delete everything under it" is genuinely what you want.

05
Basic INNER JOIN
A JOIN stitches rows from two tables together where a key matches. INNER JOIN keeps only rows that have a match on both sides.
INNER JOIN — only the overlap
PostgreSQL
CREATE TABLE users (id SERIAL PRIMARY KEY, username VARCHAR(50));
CREATE TABLE orders (
  id SERIAL PRIMARY KEY, user_id INTEGER REFERENCES users(id), total NUMERIC(10,2)
);

INSERT INTO users (username) VALUES ('sandeep'), ('priya'), ('amir'); -- ids 1,2,3 — amir has NO orders
INSERT INTO orders (user_id, total) VALUES (1, 49.99), (1, 12.50), (2, 99.00);

SELECT u.username, o.total
FROM users u
INNER JOIN orders o ON o.user_id = u.id;
Output — amir is MISSING entirely
username | total ----------+------- sandeep | 49.99 sandeep | 12.50 priya | 99.00
💡

INNER JOIN = "give me rows that exist on BOTH sides." amir has zero orders, so he produces zero output rows — not a row with NULLs, no row at all. For that you need LEFT JOIN (concept 6).

06
Basic LEFT JOIN / RIGHT JOIN
LEFT JOIN keeps every row from the left table, even with no match on the right — filling the right side's columns with NULL when there's nothing to join.
👥

Attendance sheet: Every registered student appears on the sheet (left table) whether or not they showed up to class (right table). A no-show isn't omitted — they're listed with a blank attendance column.

LEFT JOIN — all of users
RIGHT JOIN — all of orders
PostgreSQL
-- same users/orders tables as concept 5 — amir (id 3) still has zero orders

SELECT u.username, o.total
FROM users u
LEFT JOIN orders o ON o.user_id = u.id;

-- "find users with NO orders" — the classic LEFT JOIN use case
SELECT u.username
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;
First query output — amir now appears, with NULLs
username | total ----------+------- sandeep | 49.99 sandeep | 12.50 priya | 99.00 amir | NULL
💡

WHERE o.id IS NULL after a LEFT JOIN is the standard trick for "find left-side rows with no match" — exactly the opposite of what INNER JOIN gives you. RIGHT JOIN is identical but flips which side is kept in full.

07
Intermediate FULL OUTER, CROSS, and Self Joins
Three less-common joins worth knowing cold: FULL OUTER JOIN keeps unmatched rows from both sides, CROSS JOIN pairs every row with every row, and a self join joins a table to itself.
FULL OUTER JOIN — everything, both sides
🔀

CROSS JOIN and a self join aren't about matching at all, so there's no Venn diagram for them — CROSS JOIN is every row of A paired with every row of B (a Cartesian product, no overlap concept), and a self join is just an ordinary join where circle A and circle B happen to be the same table.

PostgreSQL
-- FULL OUTER JOIN: every user (even with no orders) AND every order
-- (even one with a bad/missing user_id) all appear, NULLs where unmatched
SELECT u.username, o.total
FROM users u
FULL OUTER JOIN orders o ON o.user_id = u.id;

-- CROSS JOIN: every size paired with every color — 3 x 2 = 6 combinations
SELECT s.size, c.color
FROM (VALUES ('S'),('M'),('L')) s(size)
CROSS JOIN (VALUES ('Red'),('Blue')) c(color);

-- SELF JOIN: employees table referencing its own manager_id
CREATE TABLE employees (
  id         SERIAL PRIMARY KEY,
  name       VARCHAR(50),
  manager_id INTEGER REFERENCES employees(id) -- points back at THIS table
);
INSERT INTO employees (name, manager_id) VALUES
  ('Aisha', NULL),     -- id 1, the CEO, no manager
  ('Bilal', 1),       -- id 2, reports to Aisha
  ('Chen',  1);       -- id 3, reports to Aisha

SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;
Self join output
employee | manager ----------+--------- Aisha | NULL Bilal | Aisha Chen | Aisha
💡

A self join is just a normal join where both "tables" happen to be the same table given two different aliases (e and m) — that's the whole trick.

08
Intermediate GROUP BY & Aggregates
GROUP BY collapses many rows into one row per group, so you can run COUNT/SUM/AVG/MAX/MIN per group. HAVING filters groups after aggregation — WHERE filters rows before it.
PostgreSQL
-- orders(id, user_id, total) — same data as concept 5
SELECT user_id,
       COUNT(*)       AS order_count,
       SUM(total)    AS total_spent,
       AVG(total)    AS avg_order
FROM orders
GROUP BY user_id
HAVING SUM(total) > 50          -- only groups whose TOTAL exceeds 50
ORDER BY total_spent DESC;

-- the classic interview trap — this is INVALID SQL and will not run:
-- SELECT user_id, SUM(total) FROM orders WHERE SUM(total) > 50 GROUP BY user_id;
-- ERROR: aggregate functions are not allowed in WHERE
-- WHERE runs BEFORE grouping happens, so SUM() doesn't exist yet — use HAVING
Output (user 1 = sandeep: orders 49.99 + 12.50 = 62.49)
user_id | order_count | total_spent | avg_order ---------+-------------+-------------+----------- 1 | 2 | 62.49 | 31.25
💡

Order of operations: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. WHERE can't see aggregates because they don't exist yet at that stage — that's exactly why HAVING exists.

09
Intermediate Subqueries
A query nested inside another query. Can sit in WHERE (filter by a computed value), in SELECT (a scalar per-row value), or be correlated — re-run once per outer row, referencing the outer row's columns.
PostgreSQL
-- 1. Subquery in WHERE — users who spent above the overall average order
SELECT DISTINCT u.username
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE o.total > (SELECT AVG(total) FROM orders);

-- 2. Scalar subquery in SELECT — each user's order count, inline
SELECT u.username,
       (SELECT COUNT(*) FROM orders o WHERE o.user_id = u.id) AS order_count
FROM users u;

-- 3. CORRELATED subquery — re-evaluated per outer row (slow if unindexed!)
-- "users whose most recent order was over $50"
SELECT u.username
FROM users u
WHERE 50 < (
  SELECT o.total FROM orders o
  WHERE o.user_id = u.id   -- references the OUTER row "u"
  ORDER BY o.id DESC LIMIT 1
);
💡

Most subqueries CAN be rewritten as a JOIN, and a JOIN is often faster because the optimizer plans it as one pass — but a correlated subquery is sometimes clearer to read, and the optimizer is usually smart enough to flatten simple ones anyway.

10
Intermediate Common Table Expressions (WITH)
A WITH clause names a subquery so you can reference it like a temporary table — turning deeply nested subqueries into a readable, top-to-bottom sequence of steps. WITH RECURSIVE lets a CTE reference itself, perfect for tree traversal.
PostgreSQL
-- plain CTE — readable alternative to nesting concept 9's avg subquery
WITH order_stats AS (
  SELECT user_id, SUM(total) AS total_spent
  FROM orders
  GROUP BY user_id
)
SELECT u.username, os.total_spent
FROM users u
JOIN order_stats os ON os.user_id = u.id
WHERE os.total_spent > 50;

-- RECURSIVE CTE — walk the whole org chart from employees (concept 7)
WITH RECURSIVE org_chart AS (
  -- base case: the CEO (no manager)
  SELECT id, name, manager_id, 0 AS depth
  FROM employees
  WHERE manager_id IS NULL

  UNION ALL

  -- recursive case: join the NEXT level down using the CTE itself
  SELECT e.id, e.name, e.manager_id, oc.depth + 1
  FROM employees e
  JOIN org_chart oc ON e.manager_id = oc.id
)
SELECT name, depth FROM org_chart ORDER BY depth;
Recursive CTE output
name | depth -------+------- Aisha | 0 Bilal | 1 Chen | 1
💡

A recursive CTE has exactly two halves joined by UNION ALL: a base case (where to start) and a recursive case (how to step to the next level), referencing the CTE's own name. It stops automatically once a step produces zero new rows.

11
Advanced Indexes
An index is a separate, sorted data structure (a B-tree by default) that lets the database jump straight to matching rows instead of scanning the whole table. The cost: every INSERT/UPDATE must also update the index.
📖

Book index: Finding "foreign keys" via the index at the back takes seconds. Reading every page until you stumble on it (a sequential scan) takes forever. The index itself costs a few extra pages — and updating it every time the book changes.

PostgreSQL
-- single-column index — speeds up lookups/joins/sorts on this column
CREATE INDEX idx_orders_user_id ON orders (user_id);

-- composite index — column ORDER matters!
-- this index helps "WHERE user_id = ? AND status = ?"
-- and "WHERE user_id = ?" alone (leftmost prefix)
-- but does NOT help "WHERE status = ?" alone
CREATE INDEX idx_orders_user_status ON orders (user_id, status);

-- UNIQUE index — enforces uniqueness AND speeds up lookups
CREATE UNIQUE INDEX idx_users_email ON users (email);

-- removing an index — every write to this table just got slightly cheaper,
-- and every read filtering on user_id just got slightly more expensive
DROP INDEX idx_orders_user_id;
💡

Index the columns you actually filter/join/sort by — not every column. Each extra index makes every INSERT/UPDATE/DELETE on that table slightly slower, since the index has to be kept in sync too.

Advanced EXPLAIN / EXPLAIN ANALYZE
EXPLAIN shows the query plan the optimizer chose, without running it. EXPLAIN ANALYZE actually runs the query and reports real timings — this is how you confirm an index is actually being used.
PostgreSQL
EXPLAIN ANALYZE
SELECT * FROM orders WHERE user_id = 42;

-- WITHOUT an index on user_id:
-- Seq Scan on orders  (cost=0.00..2334.00 rows=12 width=24)
--                     (actual time=8.220..8.225 rows=12 loops=1)
--   Filter: (user_id = 42)
--   Rows Removed by Filter: 99988      <-- scanned EVERY row, kept 12
-- Planning Time: 0.082 ms
-- Execution Time: 8.241 ms

CREATE INDEX idx_orders_user_id ON orders (user_id);

-- run the SAME query again — WITH the index:
-- Index Scan using idx_orders_user_id on orders  (cost=0.29..8.31 rows=12)
--                     (actual time=0.015..0.018 rows=12 loops=1)
--   Index Cond: (user_id = 42)         <-- jumped straight to the rows
-- Planning Time: 0.110 ms
-- Execution Time: 0.034 ms          <-- ~240x faster on this dataset
💡

Seq Scan = read every row, filter in memory. Index Scan = jump straight to matches via the B-tree. If a query feels slow, EXPLAIN ANALYZE it first — never guess at the fix.

Advanced Transactions & ACID
A transaction groups multiple statements so they all succeed together (COMMIT) or all fail together (ROLLBACK) — never half-applied. Isolation level controls what one transaction is allowed to see of another transaction's in-flight changes.
PostgreSQL
-- transfer $50 from account 1 to account 2 — must be all-or-nothing
BEGIN;

UPDATE accounts SET balance = balance - 50 WHERE id = 1;
UPDATE accounts SET balance = balance + 50 WHERE id = 2;

-- if account 1's balance would go negative, abort BEFORE committing:
-- SELECT balance FROM accounts WHERE id = 1;  -- check it's >= 0
-- if bad: ROLLBACK;   -- undoes BOTH updates, as if neither ran

COMMIT; -- both updates become permanent together, atomically
Isolation levels — what each PREVENTS
Level | Dirty Read | Non-Repeatable Read | Phantom Read ------------------+------------+---------------------+-------------- READ UNCOMMITTED | possible | possible | possible READ COMMITTED | prevented | possible | possible (Postgres default) REPEATABLE READ | prevented | prevented | possible* SERIALIZABLE | prevented | prevented | prevented * Postgres's REPEATABLE READ actually also prevents phantoms via snapshot isolation
💡

ACID = Atomicity (all-or-nothing), Consistency (constraints always hold), Isolation (concurrent transactions don't corrupt each other), Durability (once committed, survives a crash). For a money transfer, use at least REPEATABLE READ — losing money to a race condition is not an acceptable tradeoff for speed.

Advanced Normalization (1NF / 2NF / 3NF)
Normalization removes redundant data by splitting one messy table into several clean, linked ones — so updating a fact in one place doesn't require hunting down every duplicate copy of it.
PostgreSQL
-- ❌ BEFORE — one denormalized table, customer info repeated per order
CREATE TABLE orders_denormalized (
  order_id       SERIAL PRIMARY KEY,
  customer_name  VARCHAR(100),   -- repeated on EVERY order by this customer
  customer_email VARCHAR(255),  -- if it changes, must UPDATE every single row
  product_name   VARCHAR(100),
  product_price  NUMERIC(10,2)   -- stale if the real price changes later
);

-- ✅ AFTER — normalized into 3 tables, each fact lives in exactly ONE place
CREATE TABLE customers (id SERIAL PRIMARY KEY, name VARCHAR(100), email VARCHAR(255));
CREATE TABLE products  (id SERIAL PRIMARY KEY, name VARCHAR(100), price NUMERIC(10,2));
CREATE TABLE orders (
  id          SERIAL PRIMARY KEY,
  customer_id INTEGER REFERENCES customers(id),
  product_id  INTEGER REFERENCES products(id),
  price_paid  NUMERIC(10,2) -- snapshot of price AT TIME of order, intentionally kept
);
💡

1NF = no repeating groups in a cell (atomic values). 2NF = every column depends on the whole primary key, not part of it. 3NF = no column depends on another non-key column. In practice: "one fact, one place" — that's the whole spirit of all three.

Advanced The N+1 Query Problem
An ORM (Hibernate, JPA) silently runs 1 query to fetch a list, then 1 more query PER ROW to fetch each row's related data. 100 users = 101 round trips to the database, when 1 JOIN would have done it.
PostgreSQL
-- ❌ What a lazy-loading ORM actually sends for "list users with their orders":
SELECT * FROM users;                          -- query #1 — gets 100 users
SELECT * FROM orders WHERE user_id = 1;    -- query #2  ← one per user!
SELECT * FROM orders WHERE user_id = 2;    -- query #3
-- ... 97 more identical-shaped queries ...
SELECT * FROM orders WHERE user_id = 100;  -- query #101 — 101 total round trips!

-- ✅ FIX — one JOIN instead of 101 round trips
SELECT u.*, o.*
FROM users u
LEFT JOIN orders o ON o.user_id = u.id;
-- ONE query, ONE round trip — the app groups rows by user in memory

-- In JPA/Hibernate, this is the actual fix:
-- @Query("SELECT u FROM User u LEFT JOIN FETCH u.orders")  -- JOIN FETCH
-- forces eager loading of the association IN the same query
💡

N+1 is invisible in dev with 5 test rows and brutal in production with 10,000. Always check the actual SQL your ORM generates (enable query logging) — don't assume lazy loading is free.

Advanced Senior Interview FAQ
Four questions that come up constantly in senior backend interviews, with the one-line answer interviewers are actually listening for.
PostgreSQL
// Q: "What's the difference between WHERE and HAVING?"
// A: WHERE filters individual ROWS before grouping happens. HAVING filters
//    GROUPS after aggregation — it's the only place you can reference
//    SUM()/COUNT()/AVG() in a filter condition (concept 8).

// Q: "Difference between a clustered and non-clustered index?"
// A: A clustered index determines the PHYSICAL order rows are stored on
//    disk — a table can have at most one (it usually IS the primary key).
//    A non-clustered index is a separate structure that points BACK at the
//    table's rows — you can have many of these (concept 11).

// Q: "How would you find duplicate rows in a table?"
SELECT email, COUNT(*)
FROM users
GROUP BY email
HAVING COUNT(*) > 1;  -- any email appearing more than once

// Q: "Explain isolation levels — which would you pick for a bank transfer?"
// A: At least REPEATABLE READ, often paired with SELECT ... FOR UPDATE to
//    lock the specific account rows — losing money to a race condition is
//    never an acceptable tradeoff for the small extra latency (concept 13).
💡

Senior interviews rarely test SQL syntax recall — they test whether you can explain why the database behaves a certain way (ordering of clauses, what an index physically is, what a transaction guarantees) and connect it to a real production tradeoff.
