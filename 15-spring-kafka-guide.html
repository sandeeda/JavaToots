Chapter 1

Core Concepts

Topics, partitions, offsets, brokers — how Kafka stores and routes messages.

📦
Topic

A topic is a named channel where messages are sent and received.

Think of it like a YouTube channel — producers upload videos (messages), consumers subscribe and watch.
Producer → [Topic: "payments"] → Consumer
🔀
Partitions

Each topic is split into partitions — ordered, append-only logs.

Think of a highway with multiple lanes. More lanes = more throughput in parallel.
Topic: "payments" ├── Partition 0: [msg1, msg4, msg7] ├── Partition 1: [msg2, msg5, msg8] └── Partition 2: [msg3, msg6, msg9]
RuleDetail
Within a partitionMessages are ordered
Across partitionsNo ordering guarantee
More partitionsHigher throughput, more consumers can work in parallel
📍
Offset

An offset is the position of a message within a partition — like a line number. Starts at 0.

Partition 0: [0: msg1] [1: msg4] [2: msg7] ↑ consumer is here (offset 2)

Kafka never deletes messages when consumed — consumers track their own offset. This lets you replay messages by resetting the offset.

🏢
Brokers & Replication

A broker is a Kafka server. A cluster = multiple brokers working together.

Kafka Cluster ├── Broker 1 (warehouse 1) ├── Broker 2 (warehouse 2) └── Broker 3 (warehouse 3)

Each partition is replicated across brokers. One broker is the leader — producers always write to the leader. Replicas copy from it.

Partition 0 (replication-factor: 3) ├── Broker 1 — LEADER ← producer writes here ├── Broker 2 — replica ← copies from leader └── Broker 3 — replica ← copies from leader Partition 1 ├── Broker 2 — LEADER ├── Broker 1 — replica └── Broker 3 — replica
Rule: Replication factor cannot exceed number of brokers. 2 brokers → max replication factor = 2.

5 Partitions, 3 Brokers

Partition 0 → Leader: Broker 1, Replicas: Broker 2, Broker 3 Partition 1 → Leader: Broker 2, Replicas: Broker 1, Broker 3 Partition 2 → Leader: Broker 3, Replicas: Broker 1, Broker 2 Partition 3 → Leader: Broker 1, Replicas: Broker 2, Broker 3 Partition 4 → Leader: Broker 2, Replicas: Broker 1, Broker 3 Broker 1 leads → P0, P3 Broker 2 leads → P1, P4 Broker 3 leads → P2 ← not perfectly even, Kafka distributes best it can
🔑
Keys & Partition Routing

When a producer sends a message with a key, Kafka routes it to the same partition every time — guaranteeing ordering per key.

// All messages for userId-123 always go to same partition
kafkaTemplate.send("payments", "userId-123", payload);

Producer Config

Sending messages, acks, batching, timeouts — and how they wire together.

⚙️
application.yml
spring:
  kafka:
    bootstrap-servers: localhost:9092
    producer:
      key-serializer: org.apache.kafka.common.serialization.StringSerializer
      value-serializer: org.springframework.kafka.support.serializer.JsonSerializer
      acks: all
      retries: 3
      batch-size: 16384        # 16KB
      properties:
        retry.backoff.ms: 1000
        delivery.timeout.ms: 120000
        linger.ms: 5
        enable.idempotence: true
📤
KafkaTemplate — Sending
@Service
public class PaymentProducer {

    private final KafkaTemplate<String, PaymentEvent> kafkaTemplate;

    // Fire and forget
    public void send(PaymentEvent event) {
        kafkaTemplate.send("payments", event.getUserId(), event);
    }

    // With callback
    public void sendWithCallback(PaymentEvent event) {
        kafkaTemplate.send("payments", event.getUserId(), event)
            .whenComplete((result, ex) -> {
                if (ex != null) {
                    log.error("Failed: {}", ex.getMessage());
                } else {
                    log.info("Sent → partition={} offset={}",
                        result.getRecordMetadata().partition(),
                        result.getRecordMetadata().offset());
                }
            });
    }
}
⚠️
acks — What They Mean
acks valueWaits forRisk
0Nothing — fire and forgetmessage can be lost
1Leader broker onlylost if leader crashes before replication
allLeader + all in-sync replicassafest
acks=0 + whenComplete: callback still fires but ex is always null and offset returns -1. You never know if the broker actually got the message.
📦
Batching — batch.size & linger.ms
Message created → sits in buffer (buffer.memory) ↓ Wait for batch to fill (batch.size = 16KB) OR Wait linger.ms timer (e.g. 5ms) ↓ Whichever hits first → flush batch to broker

linger.ms = 0

Send immediately. Best latency, lower throughput.

linger.ms = 5–10

Sweet spot — lets batch fill up, improves throughput.

⏱️
Timeouts — How They Wire Together
delivery.timeout.ms = total time budget for EVERYTHING └── request.timeout.ms = time per single broker attempt └── retry.backoff.ms = wait between retries How many retries fit? delivery.timeout.ms / (request.timeout.ms + retry.backoff.ms) Example: delivery = 120000ms request = 30000ms backoff = 1000ms → each cycle = 31000ms → max ~3 retries (even if retries=10)
Gotcha: delivery.timeout.ms always wins. If it expires, retries stop even if you haven't hit the retries count yet.
📋
All Producer Properties
PropertyDefaultWhat it does
delivery.timeout.ms120000Total time budget for send + all retries
request.timeout.ms30000Wait per broker attempt
retry.backoff.ms100Wait between retries
linger.ms0Wait to fill batch before sending
batch.size16384Max bytes per batch per partition
buffer.memory33554432Total producer memory for unsent batches
max.block.ms60000Block send() if buffer full, then fail
max.request.size1048576Max size of full request to broker
message.max.bytes1000012Max size of a single message/payload
max.in.flight.requests5Unacked requests in parallel
max.request.size vs message.max.bytes: message.max.bytes = one JSON payload. max.request.size = the whole request (can contain a batch). Both must agree with the broker-side config or the broker rejects the request.
Chapter 3

Idempotence

Prevent duplicate messages when retries cause the broker to receive the same message twice.

💥
The Problem Without Idempotence
Producer sends msg (offset unknown to broker) ↓ Broker receives & writes it ✅ ↓ Broker crashes before sending ack ❌ ↓ Producer thinks it failed → retries ↓ Broker recovers → receives it AGAIN ↓ Duplicate message in partition 💥
✅
How Idempotence Fixes It

Kafka assigns every producer a unique Producer ID (PID) and a sequence number per partition.

Producer (PID: 42) sends to Partition 0: → msg1 (seq: 0) → msg2 (seq: 1) → msg3 (seq: 2) ← broker crashes before ack Producer retries msg3 (PID: 42, seq: 2) Broker recovers → seq 2 already written → ignores duplicate ✅
spring:
  kafka:
    producer:
      properties:
        enable.idempotence: true  # auto-sets acks=all, retries=MAX, in-flight=5
Low retries + idempotence = startup error. Kafka enforces retries must be effectively unlimited when idempotence is on.
🧠
Idempotence vs Exactly-Once
What it solvesScope
IdempotenceNo duplicates from producer retriesProducer side only
Exactly-once (EOS)No duplicates across producer + consumer + DBFull pipeline

If your consumer crashes and reprocesses the same message — idempotence won't help. That's where Kafka transactions come in.

Chapter 4

Exactly-Once Semantics (EOS)

Making "consume → transform → produce" succeed or fail as a single atomic unit — not just retry-safe on the producer.

💥
What Idempotence Still Doesn't Cover

A typical service doesn't just produce — it reads a message, does something with it, and writes a result. Idempotence only protects the write. The read-then-write pair is still two separate, uncoordinated operations.

Consumer reads msg (offset 5) from orders-raw ↓ Service processes it, calls kafkaTemplate.send() to orders-enriched ↓ Producer send SUCCEEDS ✅ — but consumer crashes before committing offset 5 ↓ Consumer restarts → re-reads offset 5 (nobody told it the send already happened) ↓ Same enriched order produced AGAIN → duplicate in orders-enriched 💥
The gap: idempotence guarantees msg2 written twice by a retrying producer only lands once. It says nothing about the consumer offset commit and the downstream produce being two independent operations that can succeed/fail independently of each other.
✅
What EOS Actually Guarantees

Exactly-once wraps the consumed offset and the produced record(s) into one Kafka transaction. Either both become visible, or neither does.

Input topic ──▶ consume (offset 5) │ ▼ process / transform │ ▼ Output topic ◀── produce (as part of the SAME transaction) │ ▼ commit offset 5 + commit produced record ── ONE atomic Kafka transaction ── │ success: both visible together failure: NEITHER is — offset 5 gets redelivered, nothing downstream leaked
GuaranteesFails to cover
IdempotenceA retried produce never double-writesConsumer offset vs. downstream produce staying in sync
EOSOffset commit + downstream produce succeed or fail togetherAnything outside Kafka — a DB write is not automatically part of the same transaction (see gotcha below)
🔒
The Building Block — transactional.id & Fencing

Every transactional producer registers a stable transactional.id. The broker uses it to track a producer epoch — the mechanism that stops a stalled ("zombie") instance from committing after a replacement has already taken over.

Instance A starts, transactional.id = "order-svc-tx-0", broker assigns epoch 5 Instance A stalls (long GC pause / network partition) — broker assumes it's dead Instance A's replacement starts with the SAME transactional.id → broker bumps epoch to 6 Stalled Instance A wakes up, tries to commit under epoch 5 ↓ Broker REJECTS it — epoch 5 is fenced, only epoch 6 may commit ✅
Practical rule: derive transactional.id from something stable per logical producer instance — e.g. prefix + "-" + partition — so a restarted instance reuses the same id and gets fenced protection, instead of a random id that gives every restart a clean slate (and no zombie protection).
⚙️
Spring Boot Config
spring:
  kafka:
    producer:
      properties:
        enable.idempotence: true          # EOS requires this — implied once transactional
      transaction-id-prefix: order-svc-tx-  # presence of this alone switches on a transactional producer factory
    consumer:
      group-id: order-enrichment
      properties:
        isolation.level: read_committed  # hide records from aborted/in-flight transactions
Don't skip isolation.level. Without read_committed on every downstream consumer, they default to read_uncommitted — meaning they can still see records from a transaction that later gets aborted, which defeats the entire point of EOS.
💻
Code — Consume, Transform, Produce, Atomically

Once transaction-id-prefix is set, Spring Kafka's listener container automatically opens a Kafka transaction before invoking the listener, and — if the method returns normally — sends the consumed offset into that same transaction and commits it. No extra annotation required for the basic case.

@Service
public class OrderEnrichmentListener {

    private final KafkaTemplate<String, EnrichedOrder> kafkaTemplate;

    @KafkaListener(topics = "orders-raw", groupId = "order-enrichment")
    public void enrich(ConsumerRecord<String, Order> record) {

        EnrichedOrder enriched = enrichmentService.enrich(record.value());

        // container already opened a Kafka transaction before this method ran
        kafkaTemplate.send("orders-enriched", record.key(), enriched);

        // method returns normally →
        // container sends offset 5 into the SAME transaction, then commits
        // throws instead → container aborts the transaction, offset is redelivered
    }
}

To make the transaction boundary explicit — or to combine it with other transactional Spring beans — wire a KafkaTransactionManager and reference it directly:

@Bean
public KafkaTransactionManager<String, Object> kafkaTransactionManager(ProducerFactory<String, Object> pf) {
    return new KafkaTransactionManager<>(pf);
}

@KafkaListener(topics = "orders-raw", groupId = "order-enrichment")
@Transactional("kafkaTransactionManager")
public void enrich(ConsumerRecord<String, Order> record) {
    kafkaTemplate.send("orders-enriched", record.key(), enrichmentService.enrich(record.value()));
}
⚠️
Gotcha — EOS Doesn't Reach Your Database

A Kafka transaction only spans Kafka records. Writing to a database inside the same listener is a separate resource — Kafka's transaction coordinator has no idea it exists.

@Bean
public ChainedKafkaTransactionManager<String, Object> chainedTransactionManager(
        KafkaTransactionManager<String, Object> kafkaTm,
        JpaTransactionManager jpaTm) {
    return new ChainedKafkaTransactionManager<>(kafkaTm, jpaTm);
}
Not a real 2PC: ChainedKafkaTransactionManager starts and commits both transaction managers in sequence — it is not an atomic XA commit. A crash between the two commits can still leave Kafka committed and the DB not (or vice versa). Treat it as "best effort ordering," and keep a DB-side idempotency key (e.g. a unique constraint on the message's business id) as the real safety net if a DB write has to stay consistent with a Kafka produce.

Consumer Groups

Multiple consumers with the same group-id share the work. Each partition goes to exactly one consumer in the group.

Topic: "payments" — 3 partitions Consumer Group: "payment-service" — 3 consumers Consumer 1 → Partition 0 Consumer 2 → Partition 1 Consumer 3 → Partition 2
ScenarioResult
consumers < partitionsEach consumer handles multiple partitions
consumers = partitionsPerfect 1-1 mapping
consumers > partitionsExtra consumers sit idle
Same group-id, 1 partition, 2 service instances: One instance will always be idle. Fix → increase partition count OR use different group-id per service.

Two services, different group-id

Service A → group-id: "payment-service-a" → reads ALL partitions ✅ Service B → group-id: "payment-service-b" → reads ALL partitions ✅ Use when: two different services both need every message (e.g. payment-service + audit-service)
📍
auto-offset-reset

Only applies when a consumer group reads a topic for the first time (no committed offset yet).

ValueBehaviour

latestStart from new messages only — skip existing
noneThrow exception if no offset found

Chapter 6

Acknowledgment Modes

When does Kafka move the offset forward? You control it.

🤔
Why It Matters
Consumer reads msg at offset 5 → processes it → crashes before committing ❌ Kafka still thinks consumer is at offset 4 → consumer restarts → reads offset 5 AGAIN → duplicate processing

Ack mode controls when the offset is committed — which determines what gets redelivered on restart.

🗂️
All Ack Modes
ModeWhen offset commitsControl
RECORDAfter every single messageAuto — slowest but safest auto
BATCHAfter entire batch (default)Auto — efficient
TIMEEvery n millisecondsAuto
COUNTEvery n messagesAuto
COUNT_TIMEWhichever hits firstAuto
MANUALWhen you call ack.acknowledge()Full control
MANUAL_IMMEDIATEInstantly on ack callFull control + immediate
⚠️
Risk with BATCH mode
batch: [msg1, msg2, msg3] msg1 ✅ msg2 ✅ msg3 ❌ crashes → batch never committed → all 3 redelivered → msg1 and msg2 processed TWICE 💥
For critical data like payments — use MANUAL. Commit only after you know processing succeeded.
🔧
TIME & COUNT Config
spring:
  kafka:
    listener:
      ack-mode: COUNT_TIME
      ack-count: 10      # commit every 10 messages
      ack-time: 5000    # OR every 5s — whichever first
Chapter 7

Manual Ack & Nack

Full control over offset commits — and what to do when processing fails.

✅
acknowledge()
@KafkaListener(topics = "payments", groupId = "payment-service")
public void consume(@Payload PaymentEvent event, Acknowledgment ack) {
    process(event);
    ack.acknowledge(); // offset committed — won't be redelivered
}
❌
nack(sleep)
@KafkaListener(topics = "payments", groupId = "payment-service")
public void consume(@Payload PaymentEvent event, Acknowledgment ack) {
    try {
        process(event);
        ack.acknowledge();
    } catch (Exception e) {
        ack.nack(5000); // wait 5s then seek back and redeliver
    }
}
nack doesn't tell the broker anything. The consumer seeks back to the failed offset client-side, then redelivers after the sleep.
📦
nack(index, sleep) — Batch Listeners
@KafkaListener(topics = "payments")
public void consume(@Payload List<PaymentEvent> events, Acknowledgment ack) {
    for (int i = 0; i < events.size(); i++) {
        try {
            process(events.get(i));
        } catch (Exception e) {
            ack.nack(i, 5000); // commit 0..i-1, redeliver i onwards
            return;
        }
    }
    ack.acknowledge();
}
batch: [msg0, msg1, msg2, msg3] msg0 ✅ msg1 ✅ msg2 ❌ ack.nack(2, 5000) → msg0, msg1 committed ✅ → msg2, msg3 redelivered after 5s
⚠️
Infinite Loop — Poison Pill
msg5 always fails → nack → redeliver → fail → nack → forever 💥
private Map<String, Integer> retryCount = new ConcurrentHashMap<>();

@KafkaListener(topics = "payments")
public void consume(@Payload PaymentEvent event, Acknowledgment ack) {
    String key = event.getId();
    int attempts = retryCount.getOrDefault(key, 0);
    try {
        process(event);
        retryCount.remove(key);
        ack.acknowledge();
    } catch (Exception e) {
        if (attempts >= 3) {
            sendToDLQ(event);         // give up → dead letter queue
            retryCount.remove(key);
            ack.acknowledge();        // commit so we don't loop forever
        } else {
            retryCount.put(key, attempts + 1);
            ack.nack(5000);
        }
    }
}
🧠
Summary
MethodWhat happensUse when
ack.acknowledge()Offset committed, no redeliverProcessing succeeded
ack.nack(sleep)Seeks back, redelivers after sleepTransient error, want to retry
ack.nack(index, sleep)Commits up to index, redelivers restBatch — partial failure
Chapter 8

Kafka Headers

Metadata attached to messages — separate from the payload.

📬
What Are Headers?
Think of it like an envelope — the payload is the letter inside, headers are what's written on the outside (to, from, tracking ID, priority).
Message ├── Key: "userId-123" ├── Value: { "amount": 500, "currency": "CAD" } ← payload └── Headers: ├── x-correlation-id: "abc-123" ├── x-source-service: "order-service" └── x-event-type: "PAYMENT_INITIATED"

Headers are always byte arrays at the Kafka level — you convert to/from String manually.

📤
Setting Headers — Producer Side
ProducerRecord<String, PaymentEvent> record = new ProducerRecord<>(
    "payments", null, event.getUserId(), event
);

record.headers().add("x-correlation-id",
    "abc-123".getBytes(StandardCharsets.UTF_8));
record.headers().add("x-source-service",
    "order-service".getBytes(StandardCharsets.UTF_8));

kafkaTemplate.send(record);
📥
Reading Headers — Consumer Side

Option 1 — Specific header with @Header

@KafkaListener(topics = "payments")
public void consume(
    @Payload PaymentEvent event,
    @Header("x-correlation-id") byte[] correlationIdBytes,
    @Header("x-source-service") String source  // Spring auto-converts
) {
    String correlationId = new String(correlationIdBytes, StandardCharsets.UTF_8);
}

Option 2 — All headers as map

@KafkaListener(topics = "payments")
public void consume(@Payload PaymentEvent event, @Headers MessageHeaders headers) {
    headers.forEach((key, value) -> {
        if (value instanceof byte[]) {
            log.info("{} = {}", key, new String((byte[]) value, StandardCharsets.UTF_8));
        }
    });
}

Option 3 — Via ConsumerRecord (full control)

@KafkaListener(topics = "payments")
public void consume(ConsumerRecord<String, PaymentEvent> record) {
    record.headers().forEach(header -> {
        log.info("{} = {}", header.key(),
            new String(header.value(), StandardCharsets.UTF_8));
    });
}
🔁
Forwarding Headers Across Services
// Forward ALL headers from incoming record to outbound record
record.headers().forEach(header ->
    outbound.headers().add(header.key(), header.value())
);
Always forward headers when chaining services — especially x-correlation-id. It's how you trace a message across Service A → B → C.

Chapter 9

Multi-Service Reply Pattern

Service A → B → C → A using plain KafkaTemplate and header forwarding.

🗺️
The Flow
Service A → topic: "payments" → Service B Service B → topic: "payments.processed" → Service C Service C → topic: "payments.final" → Service A Headers flow through every hop: x-correlation-id preserved end-to-end ✅
📤
Service A — Send & Listen for Final
@Service
public class ServiceA {

    public void send(PaymentEvent event) {
        ProducerRecord<String, Object> record =
            new ProducerRecord<>("payments", event.getUserId(), event);

        record.headers().add("x-correlation-id",
            UUID.randomUUID().toString().getBytes(StandardCharsets.UTF_8));
        record.headers().add("x-source-service",
            "service-a".getBytes(StandardCharsets.UTF_8));

        kafkaTemplate.send(record);
    }

    @KafkaListener(topics = "payments.final", groupId = "service-a")
    public void receiveFinal(
        @Payload PaymentFinalEvent event,
        @Header("x-correlation-id") byte[] correlationId,
        Acknowledgment ack
    ) {
        log.info("Final response. correlationId={}", new String(correlationId));
        ack.acknowledge();
    }
}
⚙️
Service B — Transform & Forward
@KafkaListener(topics = "payments", groupId = "service-b")
public void consume(ConsumerRecord<String, PaymentEvent> record, Acknowledgment ack) {
    PaymentProcessedEvent processed = transform(record.value());

    ProducerRecord<String, Object> outbound =
        new ProducerRecord<>("payments.processed", record.key(), processed);

    // forward ALL headers
    record.headers().forEach(h -> outbound.headers().add(h.key(), h.value()));
    outbound.headers().add("x-processed-by", "service-b".getBytes(StandardCharsets.UTF_8));

    kafkaTemplate.send(outbound)
        .whenComplete((result, ex) -> {
            if (ex == null) ack.acknowledge();  // ack AFTER forward confirmed
            else ack.nack(5000);
        });
}
Always ack AFTER the forward succeeds. If you ack before forwarding and the forward fails — the message is permanently lost.
⚙️
Service C — Final Processing & Reply to A
@KafkaListener(topics = "payments.processed", groupId = "service-c")
public void consume(ConsumerRecord<String, PaymentProcessedEvent> record, Acknowledgment ack) {
    PaymentFinalEvent finalEvent = finalize(record.value());

    ProducerRecord<String, Object> outbound =
        new ProducerRecord<>("payments.final", record.key(), finalEvent);

    // forward all headers so A can match correlation id
    record.headers().forEach(h -> outbound.headers().add(h.key(), h.value()));
    outbound.headers().add("x-processed-by", "service-c".getBytes(StandardCharsets.UTF_8));

    kafkaTemplate.send(outbound)
        .whenComplete((result, ex) -> {
            if (ex == null) ack.acknowledge();
            else ack.nack(5000);
        });
}
🧠
Header Trace
Service A sends: x-correlation-id: "abc-123" x-source-service: "service-a" Service B forwards + adds: x-correlation-id: "abc-123" ← preserved x-source-service: "service-a" ← preserved x-processed-by: "service-b" ← added Service C forwards + adds: x-correlation-id: "abc-123" ← preserved x-processed-by: "service-c" ← added Service A receives: x-correlation-id: "abc-123" ← matches original ✅

Spring Kafka Beans

ProducerFactory, ConsumerFactory, KafkaTemplate, ReplyingKafkaTemplate — how they wire together.

🏭
ProducerFactory

Creates Kafka producer instances with a fixed config. Think of it as the factory that manufactures delivery trucks.

@Bean
public ProducerFactory<String, Object> producerFactory() {
    Map<String, Object> config = new HashMap<>();
    config.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
    config.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
    config.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, JsonSerializer.class);
    config.put(ProducerConfig.ACKS_CONFIG, "all");
    config.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, true);
    return new DefaultKafkaProducerFactory<>(config);
}
📬

Built on top of ProducerFactory — this is what you use to send messages.

@Bean

ReplyingKafkaTemplate

Send a message and block until a response comes back — like HTTP over Kafka.

@Bean
public KafkaMessageListenerContainer<String, Object> replyContainer() {
    ContainerProperties props = new ContainerProperties("payments.reply");
    return new KafkaMessageListenerContainer<>(consumerFactory(), props);
}

@Bean
public ReplyingKafkaTemplate<String, Object, Object> replyingKafkaTemplate() {
    ReplyingKafkaTemplate<String, Object, Object> template =
        new ReplyingKafkaTemplate<>(producerFactory(), replyContainer());
    template.setDefaultReplyTimeout(Duration.ofSeconds(10));
    return template;
}
