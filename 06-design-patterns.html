PATTERN 01 · CREATIONAL
Singleton
One instance. Shared everywhere. No duplicates allowed.
Creational Spring beans Interview favourite

🏠 The Analogy

Your house has one main electricity meter. It doesn't matter how many rooms you have, how many appliances are running — there is only one meter for the whole house. You can't create a second one. Everyone shares the same single meter.

That's Singleton — one instance, shared everywhere.

⚠️ The Problem Without It

Every class creates its own DB connection — expensive, wasteful, and unnecessary. UserService → new DBConnection() 💸, PaymentService → new DBConnection() 💸, OrderService → new DBConnection() 💸. All doing the same expensive work.

"Singleton ensures only one instance of a class exists, with a global access point — useful for shared resources like DB connections, config, or thread pools."
Java✅ Singleton
public class DatabaseConnection {

    // The one and only instance
    private static final DatabaseConnection instance
        = new DatabaseConnection(); // eager — thread safe ✅

    // Nobody can call new DatabaseConnection()
    private DatabaseConnection() {
        System.out.println("Connecting to DB... (expensive!)");
    }

    public static DatabaseConnection getInstance() {
        return instance;
    }

    public void query(String sql) {
        System.out.println("Running: " + sql);
    }
}

// Usage — run it yourself, this is a complete, compilable file
public class Main {
    public static void main(String[] args) {
        DatabaseConnection c1 = DatabaseConnection.getInstance();
        DatabaseConnection c2 = DatabaseConnection.getInstance();

        System.out.println(c1 == c2); // true — exact same object!
        c1.query("SELECT * FROM users"); // "Connecting..." only printed ONCE, ever
    }
}
⚠️ Gotcha — Thread Safety: The lazy version (checking if instance == null) has a race condition — two threads can both create an instance simultaneously. Always prefer eager initialization (shown above) or use synchronized.

🌱 You Already Use This Every Day

Every @Service, @Repository, @Component in Spring is a Singleton by default. Spring creates one instance and reuses it for every request.

This is why instance variables in Spring beans are dangerous — they're shared across all threads simultaneously.

JavaSpring Singleton
@Service // Spring creates ONE instance — Singleton!
public class PaymentService {

    // ✅ Safe — no state, just methods
    public void processPayment(PaymentRequest req) { ... }

    // ❌ DANGER — shared across ALL threads
    private String currentUser; // race condition!
}
PATTERN 02 · CREATIONAL
Builder
Construct complex objects step by step. Only finalize at the end.
Creational ResponseEntity · Lombok Interview favourite

🥖 The Subway Analogy

You go to Subway to order a sandwich. You don't just say "give me a sandwich" and get a random one. You build it step by step — bread, protein, veggies, sauce, toasted or not?

The guy behind the counter builds it step by step, exactly how you want. You only get the final sandwich when you say "that's it."

⚠️ The Problem Without It — Telescoping Constructor

new User("Sandeep", "Das", 32, "Toronto", "email", true, false, null, "en-CA") — What is the 4th argument? What does true, false mean? Unreadable and error-prone.

"Builder constructs a complex object step by step using a fluent chain — and only creates the final object when you call build()."
Java✅ Builder Pattern
public class User {
    private String firstName, lastName, email, city;
    private boolean isVerified;

    private User(Builder builder) {
        this.firstName  = builder.firstName;
        this.lastName   = builder.lastName;
        this.email      = builder.email;
        this.city       = builder.city;
        this.isVerified = builder.isVerified;
    }

    public static class Builder {
        private String firstName, lastName, email, city;
        private boolean isVerified;

        public Builder firstName(String v) { this.firstName = v; return this; }
        public Builder lastName(String v)  { this.lastName = v;  return this; }
        public Builder email(String v)     { this.email = v;     return this; }
        public Builder city(String v)      { this.city = v;      return this; }
        public Builder isVerified(boolean v){ this.isVerified = v; return this; }

        public User build() {
            if (firstName == null || email == null)
                throw new IllegalStateException("firstName and email required");
            return new User(this);
        }
    }

    @Override
    public String toString() {
        return firstName + " " + lastName + " <" + email + "> (" + city + ")";
    }
}

// Usage — clean, readable, obvious. Run it: this is a complete file.
public class Main {
    public static void main(String[] args) {
        User user = new User.Builder()
            .firstName("Sandeep")
            .lastName("Das")
            .email("sandeep@email.com")
            .city("Toronto")
            .isVerified(true)
            .build(); // sandwich is ready 🥪

        System.out.println(user); // Sandeep Das <sandeep@email.com> (Toronto)
    }
}

🌱 You Use This Every Day

Builder is baked into Spring and Lombok. You're already using it without thinking about it.

JavaSpring + Lombok Builder
// ResponseEntity — classic Spring builder
return ResponseEntity
    .ok()
    .header("X-Custom", "value")
    .body(responseDto);

// Lombok @Builder — generates all the boilerplate for you
@Builder
public class User {
    private String firstName, lastName, email, city;
}

User user = User.builder()
    .firstName("Sandeep")
    .city("Toronto")
    .build();
PATTERN 03 · BEHAVIOURAL
Strategy
Swap algorithms at runtime. Eliminate if-else chains forever.
Behavioural Payment providers · Comparator

🗺️ Google Maps Analogy

You're travelling from Toronto to downtown. Google Maps asks: 🚗 Drive (25 mins), 🚌 Transit (40 mins), 🚴 Cycle (35 mins), 🚶 Walk (1hr 20 mins).

You pick a strategy at runtime. The destination is the same. The goal is the same. Only the algorithm changes. Tomorrow you might pick differently based on weather or mood.

⚠️ The Problem Without It

One giant if-else block that you must edit every time you add a new payment provider. Adding Razorpay? Find every copy of this block across your codebase. Add a case. Hope you didn't miss any.

"Strategy defines a family of algorithms behind a common interface, and lets you swap them at runtime — eliminating if-else chains and making it easy to add new behaviours without touching existing code."
Java✅ Strategy Pattern
// 1. The contract
public interface PaymentStrategy {
    void pay(double amount);
}

// 2. Concrete strategies
public class StripeStrategy implements PaymentStrategy {
    public void pay(double amount) {
        System.out.println("Stripe: charging $" + amount);
    }
}
public class PayPalStrategy implements PaymentStrategy {
    public void pay(double amount) {
        System.out.println("PayPal: processing $" + amount);
    }
}

// 3. Context — uses whichever strategy is injected
public class PaymentService {
    private PaymentStrategy strategy;

    public void setStrategy(PaymentStrategy s) { this.strategy = s; }

    public void checkout(double amount) {
        strategy.pay(amount); // doesn't know or care which one
    }
}

// Usage — run it: this is a complete file
public class Main {
    public static void main(String[] args) {
        PaymentService service = new PaymentService();

        // Swap at runtime!
        service.setStrategy(new StripeStrategy());
        service.checkout(99.99); // Stripe: charging $99.99

        service.setStrategy(new PayPalStrategy());
        service.checkout(49.99); // PayPal: processing $49.99
    }
}

🌱 Spring DI + Strategy = Zero If-Else

Register each strategy as a bean. Spring automatically injects all implementations into a Map keyed by bean name. Pick by key at runtime — no if-else anywhere.

JavaSpring Strategy Magic
@Service("stripe")
public class StripeStrategy implements PaymentStrategy { ... }

@Service("paypal")
public class PayPalStrategy implements PaymentStrategy { ... }

@Service
public class CheckoutService {

    @Autowired
    Map<String, PaymentStrategy> strategies;
    // Spring injects ALL implementations, keyed by bean name

    public void checkout(String provider, double amount) {
        strategies.get(provider).pay(amount); // zero if-else 🎉
    }
}
PATTERN 04 · STRUCTURAL
Proxy
Wrap an object to control access. The engine behind Spring annotations.
Structural @Transactional · @Cacheable · @Async Must know

📞 Bank IVR Analogy

You call your bank. You don't reach the agent directly. You reach an IVR system first — "Press 1 for balance", "Enter your PIN", "Verifying identity..." — only after all that does it connect you to the real agent.

The IVR is the Proxy. It sits in front of the real thing and does extra work before letting you through.

📐 Visually

Without Proxy: You → Real Object

With Proxy: You → Proxy (does extra stuff) → Real Object

The caller doesn't know there's a proxy. It just calls normally.

"Proxy wraps a real object and controls access to it — adding security, logging, caching, or transactions transparently without touching the real class."
Java✅ Proxy Pattern
interface BankService {
    void getBalance();
}

// Real object — the celebrity
class RealBankService implements BankService {
    public void getBalance() {
        System.out.println("Balance: $5000");
    }
}

// Proxy — the manager. Same interface!
class BankServiceProxy implements BankService {
    private RealBankService real = new RealBankService();

    public void getBalance() {
        System.out.println("🔐 Checking PIN...");  // BEFORE
        real.getBalance();                          // real call
        System.out.println("📋 Call logged.");      // AFTER
    }
}

// Usage — run it: this is a complete file
public class Main {
    public static void main(String[] args) {
        // Caller has no idea it's a proxy
        BankService service = new BankServiceProxy();
        service.getBalance();
        // 🔐 Checking PIN...
        // Balance: $5000
        // 📋 Call logged.
    }
}

🌱 How @Transactional, @Cacheable, @Async Work

Spring secretly replaces your bean with a proxy on startup. You never see it — but it's always there intercepting your method calls.

JavaWhat Spring does behind the scenes
// What you write
@Transactional
public void placeOrder(Order order) {
    orderRepo.save(order);       // step 1
    inventoryRepo.reduce(...);   // step 2
    paymentRepo.charge(...);     // step 3 — if this throws...
}                                 // steps 1 & 2 ROLL BACK ✅

// What Spring's proxy does
// open transaction
// → calls your real placeOrder()
// success  → COMMIT
// exception → ROLLBACK

// ❌ THE GOTCHA — self-invocation bypasses proxy!
public void doSomething() {
    placeOrder(order); // 😱 @Transactional WON'T work here
}                      // calls real method, skips proxy
Java@Cacheable — proxy checks the cache first
// What you write
@Cacheable("users")
public User getUserById(Long id) {
    System.out.println("Hitting DB for user " + id); // only runs on a MISS
    return userRepo.findById(id);
}

// What Spring's proxy does before calling your real method
// call 1: getUserById(1) → cache MISS → runs real method → stores result under key "1"
// call 2: getUserById(1) → cache HIT  → returns stored value, "Hitting DB..." never prints

// Usage
userService.getUserById(1L); // prints "Hitting DB for user 1"
userService.getUserById(1L); // prints nothing — served from cache
Java@Async — proxy hands the call to another thread
// What you write
@Async
public CompletableFuture<String> sendEmail(String to) {
    System.out.println("Sending on thread: " + Thread.currentThread().getName());
    return CompletableFuture.completedFuture("sent");
}

// What Spring's proxy does
// intercepts the call → submits it to a TaskExecutor thread pool
// → returns control to the caller immediately, doesn't wait

// Usage
public void onSignup(User user) {
    emailService.sendEmail(user.getEmail()); // returns instantly, runs in background
    System.out.println("Signup flow continues without waiting");
}
⚠️ Applies to all three: Each needs its own switch turned on at config level — @EnableTransactionManagement, @EnableCaching, @EnableAsync (Spring Boot autoconfigures these once it sees the annotation in use, but plain Spring doesn't). And the self-invocation gotcha above isn't unique to @Transactional — calling a @Cacheable or @Async method from another method in the same class calls the real object directly, skipping the proxy entirely, so the caching/async behaviour silently does nothing.
PATTERN 05 · BEHAVIOURAL
Template Method
Fixed skeleton. Subclasses fill in specific steps.
Behavioural JdbcTemplate · RestTemplate

⏰ Morning Routine Analogy

Every morning: 1. Wake up ⏰ 2. Brush teeth 🪥 3. Get ready ← this changes 4. Breakfast 🍳 5. Leave 🚪

Steps 1, 2, 4, 5 are always the same. Only step 3 changes — suit on workdays, casual on weekends. Your routine is the template. "Get ready" is left blank for you to fill in.

⚠️ The Problem Without It

PDF report, Excel report, Email report all repeat the same "fetch data" and "save report" steps. Copy-paste across 3 classes. If fetching logic changes — update it in 3 places and hope you don't miss one.

"Template Method defines the skeleton of an algorithm in a base class and lets subclasses fill in specific steps — without changing the overall structure."
Java✅ Template Method
public abstract class ReportGenerator {

    // THE SKELETON — final so nobody breaks the order
    public final void generateReport() {
        fetchData();    // same for everyone
        formatData();   // ← subclass fills in
        renderOutput(); // ← subclass fills in
        saveReport();   // same for everyone
    }

    private void fetchData()  { System.out.println("📦 Fetching..."); }
    private void saveReport() { System.out.println("💾 Saving..."); }

    protected abstract void formatData();
    protected abstract void renderOutput();
}

public class PdfReportGenerator extends ReportGenerator {
    protected void formatData()  { System.out.println("📄 PDF format"); }
    protected void renderOutput(){ System.out.println("🖨️ PDF render"); }
}

public class ExcelReportGenerator extends ReportGenerator {
    protected void formatData()  { System.out.println("📊 Excel format"); }
    protected void renderOutput(){ System.out.println("📈 Excel render"); }
}

// Usage — run it: this is a complete file
public class Main {
    public static void main(String[] args) {
        // Same skeleton — different filling
        new PdfReportGenerator().generateReport();
        System.out.println();
        new ExcelReportGenerator().generateReport();
    }
}

🌱 It's Literally in the Name

JdbcTemplate, RestTemplate, KafkaTemplate — Spring writes the skeleton (open connection, handle errors, close connection). You fill in your specific step (the SQL or URL).

JavaSpring Templates
// JdbcTemplate — Spring handles connection/cleanup
// You fill in: the SQL and how to map a row
jdbcTemplate.query("SELECT * FROM orders", (rs, row) -> {
    return new Order(rs.getString("id")); // 👈 your step
});

// RestTemplate — Spring handles HTTP lifecycle
// You fill in: the URL and response type
Order order = restTemplate.getForObject(
    "https://api.example.com/orders/1",
    Order.class  // 👈 your step
);
PATTERN 06 · BEHAVIOURAL
Observer
One changes. Many get notified. The foundation of event-driven systems.
Behavioural @EventListener · Kafka Must know

▶️ YouTube Analogy

You subscribe to a YouTube channel. You don't check every 5 minutes — you subscribe once. When the creator uploads → YouTube notifies all subscribers automatically.

The creator doesn't know who you are. They just upload. YouTube handles telling everyone. That's Observer.

⚠️ The Problem Without It — Polling

Checking in a while loop every second: "hasNewOrder? hasNewOrder? hasNewOrder?" — wasteful, tightly coupled. Every new service that cares about orders means editing that loop.

"Observer defines a one-to-many relationship — when one object changes, all dependents are notified automatically. Foundation of event-driven architecture and Kafka."
Java✅ Observer Pattern
import java.util.ArrayList;
import java.util.List;

// Minimal Order — just enough state for the demo
class Order {
    private final String id;
    public Order(String id) { this.id = id; }
    public String getId() { return id; }
}

// Subscriber contract
public interface OrderObserver {
    void onOrderPlaced(Order order);
}

// The Subject (YouTube channel)
public class OrderService {
    private List<OrderObserver> observers = new ArrayList<>();

    public void addObserver(OrderObserver o) { observers.add(o); }

    public void placeOrder(Order order) {
        System.out.println("💾 Order saved: " + order.getId()); // stand-in for orderRepo.save(order)
        for (OrderObserver o : observers)
            o.onOrderPlaced(order); // notify ALL
    }
}

// Subscribers — each does its own thing
class EmailObserver implements OrderObserver {
    public void onOrderPlaced(Order o) {
        System.out.println("📧 Email sent for: " + o.getId());
    }
}
class InventoryObserver implements OrderObserver {
    public void onOrderPlaced(Order o) {
        System.out.println("📦 Stock reduced for: " + o.getId());
    }
}

// Usage — run it: this is a complete file
public class Main {
    public static void main(String[] args) {
        OrderService orderService = new OrderService();

        // Add new observer = zero changes to OrderService
        orderService.addObserver(new EmailObserver());
        orderService.addObserver(new InventoryObserver());

        orderService.placeOrder(new Order("ORD-1001"));
        // 💾 Order saved: ORD-1001
        // 📧 Email sent for: ORD-1001
        // 📦 Stock reduced for: ORD-1001
    }
}

🌱 Spring Events + Kafka = Observer at Scale

Spring's @EventListener is Observer within one app. Kafka is Observer across distributed microservices. Same concept — different scale.

JavaSpring @EventListener
// Publisher (the subject)
@Service
public class OrderService {
    @Autowired ApplicationEventPublisher publisher;

    @Transactional
    public void placeOrder(Order order) {
        orderRepo.save(order);
        publisher.publishEvent(new OrderPlacedEvent(this, order));
    }
}

// Listeners — completely decoupled
@Component
public class EmailListener {
    @EventListener
    @Async // run in background — one failure won't block others
    public void onOrder(OrderPlacedEvent e) { /* send email */ }
}

// Kafka — Observer across microservices
// OrderService (Producer) → Kafka Topic → EmailService (Consumer)
//                                       → InventoryService (Consumer)
// Your @KafkaListener IS the Observer pattern 🔥
PATTERN 07 · CREATIONAL
Factory
Ask what you want. Factory decides how to create it.
Creational ApplicationContext · BeanFactory

🚗 Car Dealership Analogy

You walk into a dealership. You don't go to the back and build the car yourself — welding, wiring, painting. You just say "I want an SUV."

The dealership figures out which car to build and hands it to you. You don't care how it was made. You just drive it away.

⚠️ The Problem Without It

The same if-else block deciding which processor to create gets copy-pasted everywhere in your codebase. Add Razorpay — hunt down every copy. Update all of them. Hope you didn't miss one.

"Factory centralises object creation — the caller says what it wants, the factory decides how to create and return it. Removes tight coupling between caller and concrete classes."
Java✅ Simple Factory
// The contract + concrete implementations the factory hands back
interface PaymentProcessor {
    void pay(double amount);
}
class StripeProcessor implements PaymentProcessor {
    public void pay(double amount) { System.out.println("Stripe: charging $" + amount); }
}
class PayPalProcessor implements PaymentProcessor {
    public void pay(double amount) { System.out.println("PayPal: charging $" + amount); }
}
class RazorpayProcessor implements PaymentProcessor {
    public void pay(double amount) { System.out.println("Razorpay: charging $" + amount); }
}

public class PaymentProcessorFactory {

    public static PaymentProcessor create(String type) {
        switch (type) {
            case "STRIPE":   return new StripeProcessor();
            case "PAYPAL":   return new PayPalProcessor();
            case "RAZORPAY": return new RazorpayProcessor();
            default: throw new IllegalArgumentException("Unknown: " + type);
        }
    }
}

// Usage — run it: this is a complete file
public class Main {
    public static void main(String[] args) {
        // Caller just asks — factory decides
        PaymentProcessor p1 = PaymentProcessorFactory.create("STRIPE");
        p1.pay(99.99);

        // Switch provider — zero other code changes, just a different variable
        PaymentProcessor p2 = PaymentProcessorFactory.create("PAYPAL");
        p2.pay(49.99);
    }
}
⚠️ Factory vs Builder: Factory = which type of object? Builder = how do I assemble this one object? Factory returns different types. Builder configures one type differently.

🌱 Spring's Entire Core IS a Factory

You never call new PaymentService(). Spring's ApplicationContext is the factory — you ask for a bean, it creates and returns it.

JavaSpring as Factory
// ApplicationContext IS a factory
ApplicationContext ctx = new AnnotationConfigApplicationContext(...);

// You ask for a bean — Spring creates and returns it
PaymentService service = ctx.getBean(PaymentService.class);

// Factory + Strategy combined — the ultimate pattern 🔥
@Autowired
Map<String, PaymentStrategy> strategies;
// Spring injects all implementations, keyed by bean name
// strategies.get("stripe") → StripeProcessor
// strategies.get("paypal") → PayPalProcessor
// Zero if-else. Just ask by name.
PATTERN 08 · STRUCTURAL
Decorator
Layer behaviour on top without changing the original object.
Structural Security FilterChain · Java IO

☕ Starbucks Analogy

You order a plain coffee ☕. Then — "add milk" → latte. "Add caramel" → caramel latte. "Add whipped cream" → caramel latte with whip.

Each addition wraps the previous drink. You never threw away the original coffee — you kept layering on top. Price adds up with each layer.

⚠️ The Problem Without It

CoffeeWithMilk, CoffeeWithCaramel, CoffeeWithMilkAndCaramel, CoffeeWithMilkAndCaramelAndWhip... 10 add-ons = hundreds of class combinations. Combinatorial explosion. 💥

"Decorator wraps an object to add new behaviour layer by layer at runtime — without changing the original class or creating an explosion of subclass combinations."
Java✅ Decorator Pattern
interface Coffee {
    String getDescription();
    double getCost();
}

class PlainCoffee implements Coffee {
    public String getDescription() { return "Plain coffee"; }
    public double getCost() { return 2.00; }
}

// Base decorator — wraps any Coffee
abstract class CoffeeDecorator implements Coffee {
    protected Coffee coffee;
    CoffeeDecorator(Coffee c) { this.coffee = c; }
    public String getDescription() { return coffee.getDescription(); }
    public double getCost() { return coffee.getCost(); }
}

class MilkDecorator extends CoffeeDecorator {
    MilkDecorator(Coffee c) { super(c); }
    public String getDescription() { return coffee.getDescription() + ", Milk"; }
    public double getCost() { return coffee.getCost() + 0.50; }
}

class CaramelDecorator extends CoffeeDecorator {
    CaramelDecorator(Coffee c) { super(c); }
    public String getDescription() { return coffee.getDescription() + ", Caramel"; }
    public double getCost() { return coffee.getCost() + 0.75; }
}

// Usage — run it: this is a complete file
public class Main {
    public static void main(String[] args) {
        // Stack layers at runtime
        Coffee order = new CaramelDecorator(
                          new MilkDecorator(
                            new PlainCoffee()));

        System.out.println(order.getDescription()); // Plain coffee, Milk, Caramel
        System.out.println(order.getCost());        // 3.25
    }
}

🌱 Spring Security Filter Chain

Each filter wraps the next one. Each adds its own behaviour. Your controller stays completely clean — it never knows any of this happened.

JavaDecorator in the wild
// Spring Security — each filter decorates the next
// Request comes in
//   → CorsFilter        (adds CORS headers)
//   → LoggingFilter     (logs the request)
//   → AuthTokenFilter   (validates JWT)
//   → RateLimitFilter   (checks rate limit)
//   → Your Controller   (the real object — stays clean)

// Java IO — the classic Decorator example
BufferedReader reader = new BufferedReader(     // adds buffering
                          new InputStreamReader(   // adds charset
                            new FileInputStream("f.txt") // base
                          )
                        );
// FileInputStream = plain coffee ☕
// Each wrapper = an add-on layer
⚠️ Decorator vs Proxy: Both wrap an object. Decorator adds features (stacked by caller). Proxy controls access (created by framework). Decorator = coffee add-ons. Proxy = bank IVR.
