01
Basic What @LoadBalanced Does
@LoadBalanced is a qualifier annotation you drop on a RestTemplate (or WebClient.Builder) @Bean. It tells Spring Cloud LoadBalancer to intercept every outgoing HTTP call made through that client and resolve a logical service name — like http://inventory-service/... — into a real host:port picked from the service registry, instead of doing a literal DNS lookup that would fail.
🚕

Hotel concierge: you say "get me a taxi" and the concierge picks one from a rotating pool of cars out front — you never need a specific driver's phone number, and if that driver is busy, the concierge just picks the next one.

Java
import org.springframework.cloud.client.loadbalancer.LoadBalanced;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.client.RestTemplate;

@Configuration
public class ClientConfig {

  @Bean
  @LoadBalanced // marks this RestTemplate for service-discovery-aware calls
  public RestTemplate restTemplate() {
    return new RestTemplate();
  }
}

@Service
public class StockService {

  private final RestTemplate restTemplate;

  public StockService(RestTemplate restTemplate) {
    this.restTemplate = restTemplate;
  }

  public Integer getStock(String sku) {
    // "inventory-service" isn't a DNS name — it's the app's spring.application.name,
    // resolved to a real instance by the LoadBalancerInterceptor before the call goes out
    return restTemplate.getForObject(
        "http://inventory-service/api/stock/{sku}", Integer.class, sku);
  }
}
Output (log)
DEBUG LoadBalancerInterceptor : Resolved 'inventory-service' -> 10.0.4.12:8082 DEBUG RestTemplate : GET http://10.0.4.12:8082/api/stock/SKU-8841
💡

Without @LoadBalanced, that exact same call throws UnknownHostException: inventory-service — because "inventory-service" isn't a real DNS name, it's just the identity the app registered itself under.

02
Basic The Service Registry — Where inventory-service Actually Lives
inventory-service is not a class, a package, or anything inside your codebase — it's the spring.application.name of a completely separate, independently running Spring Boot application, its own JVM process on its own port. For @LoadBalanced to turn that name into a real host:port, a fourth process has to exist and be running: a service registry (Eureka, Consul, etc.) that every other service explicitly points at. Nothing here is auto-discovered — each service is told the registry's address in plain config.
📞

Company front desk: when Priya joins Accounting, she calls the front desk — a fixed, known number everyone already has — and says "I'm Priya, extension 4471." Later, when you want to reach "Priya in Accounting," you don't know her extension either — you call the same front desk and ask. If Priya changes desks, she just re-registers; you never need to learn her new extension, because you never call it directly.

Java + YAML — the registry itself
// THIS is a fourth, separate Spring Boot app — it IS the registry, nothing else
@SpringBootApplication
@EnableEurekaServer
public class RegistryServerApplication {
  public static void main(String[] args) {
    SpringApplication.run(RegistryServerApplication.class, args);
  }
}

server:
  port: 8082   # the APP decides this — the registry has no say in it

spring:
  application:
    name: inventory-service   # the logical name THIS app registers itself under

eureka:
  client:
    service-url:
      defaultZone: http://localhost:8761/eureka/   # the ONE hardcoded address in the whole system
☎️

Doesn't the registry hand out the port? No — it's the reverse. inventory-service binds its own embedded server to server.port: 8082 (or, if you set server.port: 0, the OS hands it a random free port instead — common when running several instances of the same service on one machine so they don't collide). Only after it's actually bound and knows its real port does the Eureka client read that port back and include it in the registration payload it POSTs to the registry. The registry just stores whatever port it was told — it never assigns, reserves, or manages a port for anyone. Every app, including the registry itself, needs its own server.port; leaving it unset defaults to 8080 for all of them, which is exactly why running several services locally without distinct ports fails with "port already in use."

What happens on startup (logs, conceptually)
inventory-service : binds embedded server to 8082 (from server.port, or a random free port if server.port=0) inventory-service : POST http://localhost:8761/eureka/apps/INVENTORY-SERVICE {host, port: 8082, ...} -> registered inventory-service : PUT http://localhost:8761/eureka/apps/INVENTORY-SERVICE/i1 -> heartbeat (every 30s) order-service : GET http://localhost:8761/eureka/apps -> pulls + caches the full registry locally (every 30s)
💡

The registry's address (defaultZone) is the one hardcoded host:port in the entire architecture — it has to be fixed, because you can't use service discovery to find the service that does service discovery. Every other address — inventory-service's real IP and port, order-service's real IP and port — is decided by each app itself and merely reported to, never assigned by, that registry, which is exactly what @LoadBalanced reads back out on every call.

Without a discovery client on the classpath, @LoadBalanced has nothing to balance across.

04
Intermediate How It Works Under the Hood
@LoadBalanced RestTemplate gets a LoadBalancerInterceptor added to its interceptor chain by Spring Cloud's auto-configuration. On every request, the interceptor asks the LoadBalancerClient for a ServiceInstance matching the host portion of the URI, then rewrites the URI with that instance's real host:port before the actual HTTP call goes out.
Java
// Roughly what Spring Cloud does for you behind @LoadBalanced — NOT code you write yourself
public class LoadBalancerInterceptor implements ClientHttpRequestInterceptor {

  private final LoadBalancerClient loadBalancerClient;

  @Override
  public ClientHttpResponse intercept(HttpRequest request, byte[] body,
                                       ClientHttpRequestExecution execution) throws IOException {
    URI original = request.getURI();
    String serviceId = original.getHost();              // e.g. "inventory-service"

    ServiceInstance instance = loadBalancerClient.choose(serviceId); // picks one, load-balanced
    URI resolved = loadBalancerClient.reconstructURI(instance, original);

    HttpRequest wrapped = new HttpRequestWrapper(request) {
      @Override public URI getURI() { return resolved; }  // now points at 10.0.4.12:8082
    };
    return execution.execute(wrapped, body);
  }
}
💡

This is why @LoadBalanced is a marker/qualifier, not a class with load-balancing logic in it — the actual work happens in this auto-configured interceptor, invisible to your code.

05
Intermediate Load Balancing Strategies
Spring Cloud LoadBalancer picks instances via a pluggable ReactorLoadBalancer: RoundRobinLoadBalancer is the default, RandomLoadBalancer is built in, and you can register your own (weighted, zone-aware) via a @LoadBalancerClient-scoped configuration class.
🔄

Does Eureka hand back a different URL on every single call? No — that would mean a network round-trip to the registry per HTTP request, which would defeat the point. Instead, the caller's Eureka client polls the registry on a timer (every 30s by default) and pulls the entire list of currently-registered instances for a service name in one shot, caching it locally in memory. Every actual call after that reads from this local cache — the ReactorLoadBalancer just advances an in-memory counter through it. Zero network calls to Eureka happen per request; that's exactly what makes client-side load balancing fast.

10 order-service instances — cached once, round-robinned locally over 12 calls
// notification-service's local cache after one 30s sync (10 entries, one call to Eureka): [10.0.4.1:8081, 10.0.4.2:8081, 10.0.4.3:8081, ... , 10.0.4.10:8081] call 1 -> 10.0.4.1:8081 call 7 -> 10.0.4.7:8081 call 2 -> 10.0.4.2:8081 call 8 -> 10.0.4.8:8081 call 3 -> 10.0.4.3:8081 call 9 -> 10.0.4.9:8081 call 4 -> 10.0.4.4:8081 call 10 -> 10.0.4.10:8081 call 5 -> 10.0.4.5:8081 call 11 -> 10.0.4.1:8081 (wraps around) call 6 -> 10.0.4.6:8081 call 12 -> 10.0.4.2:8081
💡

The staleness gotcha: if instance 10.0.4.4:8081 crashes mid-window, it stays in the cached list until the next 30s refresh — round robin will still route a call to it in the meantime, and that call fails. The load balancer itself has no idea the instance is dead; catching that failure and retrying against a different instance is the job of a retry policy / circuit breaker sitting around the call, not the load balancer.

Java — customizing which strategy is used
@Configuration
public class RandomLoadBalancerConfig {

  @Bean
  public ReactorLoadBalancer<ServiceInstance> randomLoadBalancer(
      Environment environment, LoadBalancerClientFactory factory) {
    String name = environment.getProperty(LoadBalancerClientFactory.PROPERTY_NAME);
    return new RandomLoadBalancer(
        factory.getLazyProvider(name, ServiceInstanceListSupplier.class), name);
  }
}

// Scope the custom strategy to ONE named client — everything else stays round robin
@Configuration
@LoadBalancerClient(name = "inventory-service", configuration = RandomLoadBalancerConfig.class)
public class LoadBalancerClientConfig {
}
Requests to pricing-service (default RoundRobinLoadBalancer)
1 -> instance-A 2 -> instance-B 3 -> instance-C 4 -> instance-A 5 -> instance-B 6 -> instance-C
💡

Round robin is the sane default for stateless services. Reach for a custom strategy only when you have a specific traffic-shaping need — e.g. weighting a bigger instance, or keeping a client sticky to one zone.

Intermediate @LoadBalanced vs Feign Clients
Declarative Spring Cloud OpenFeign gives you load balancing for free — a @FeignClient(name = "...") interface resolves the logical name and balances across instances automatically, using the exact same LoadBalancer machinery under the hood, with none of the RestTemplate boilerplate.
❓

"Is a discovery service not needed here?" It absolutely still is — nothing about Feign removes that requirement. @FeignClient(name = "inventory-service") resolves that name through the exact same DiscoveryClient / LoadBalancerClient machinery as a @LoadBalanced RestTemplate does. Feign only removes the boilerplate of building the request by hand — it changes nothing about needing a running registry, both apps registered with it, and the eureka-client dependency on both classpaths. Skip any of that and Feign fails the exact same way RestTemplate would (see the error trace near the bottom of this card).

Java — the shape of it, imperative vs declarative
// Imperative — @LoadBalanced RestTemplate
public Integer getStockImperative(String sku) {
  return restTemplate.getForObject(
      "http://inventory-service/api/stock/{sku}", Integer.class, sku);
}

// Declarative — Feign, load-balanced automatically, no @LoadBalanced needed
@FeignClient(name = "inventory-service")
public interface InventoryClient {

  @GetMapping("/api/stock/{sku}")
  Integer getStock(@PathVariable("sku") String sku);
}

Advanced Common Pitfalls
Four classics: forgetting @LoadBalanced (a confusing UnknownHostException in prod for what looks like a valid URL), pointing that same RestTemplate at a real external hostname (the interceptor tries to resolve it against the service registry too, and fails), skipping retry/timeout config so one flaky instance cascades into failures for every caller, and — the sneaky one — two genuinely different services accidentally registering under the same spring.application.name.
Java
@Configuration
public class RestTemplateConfig {

  @Bean
  @LoadBalanced
  public RestTemplate internalRestTemplate() {
    return new RestTemplate(); // for calls to OTHER services in the registry, by logical name
  }

  @Bean
  @Qualifier("external")
  public RestTemplate externalRestTemplate() {
    return new RestTemplate(); // for real DNS hosts — Stripe, S3, anything outside the registry
  }
}

@Service
public class PaymentService {

  private final RestTemplate internalRestTemplate;
  private final RestTemplate externalRestTemplate;

  public PaymentService(RestTemplate internalRestTemplate,
                         @Qualifier("external") RestTemplate externalRestTemplate) {
    this.internalRestTemplate = internalRestTemplate;
    this.externalRestTemplate = externalRestTemplate;
  }

  public void charge(String orderId, double amount) {
    // real external host — MUST use the non-load-balanced client
    externalRestTemplate.postForObject("https://api.stripe.com/v1/charges", request, String.class);
    // internal microservice — MUST use the load-balanced client
    internalRestTemplate.postForObject("http://order-service/api/orders/{id}/paid", request, Void.class, orderId);
  }
}
💡

@LoadBalanced is an all-or-nothing switch per RestTemplate instance. Never mix service-discovery calls and raw external calls on the same bean — split them and disambiguate with @Qualifier.

👥

The fourth pitfall — name collisions: Eureka only ever sees the string in spring.application.name. It has no idea that "inventory-service" is supposed to mean one specific codebase. If a brand-new shipping-service is bootstrapped by copy-pasting inventory-service's application.yml and someone forgets to change that one line, both apps register under INVENTORY-SERVICE and Eureka merges them into a single list, as if they were interchangeable peers.

Registry entry for "INVENTORY-SERVICE" after the mistake
INVENTORY-SERVICE: 10.0.4.20:8082 // real inventory-service — /api/stock/{sku} 10.0.4.21:8082 // real inventory-service — /api/stock/{sku} 10.0.5.30:8090 // actually shipping-service, misconfigured — no /api/stock endpoint at all // ~1 in 3 calls to http://inventory-service/api/stock/{sku} silently lands on shipping-service // -> 404, or worse: a same-shaped endpoint on shipping-service returns the WRONG data, no error at all
💡

Eureka provides zero protection against this — no uniqueness check, no warning, no error. It's purely a naming-discipline problem, usually caught only by code review or a team convention, which is exactly why it's dangerous: the failure mode isn't a loud crash, it's silently-wrong data on a fraction of calls that's very hard to correlate back to "two services share a name."

Advanced Senior Interview FAQ
Five questions interviewers love, with the answer a senior candidate is expected to give.
Java
// Q: "What problem does @LoadBalanced solve that plain DNS/hostnames can't?"
// A: Microservice instances are ephemeral — they scale up/down and get rescheduled with new
//    IPs constantly. DNS can't keep up with that churn cheaply. @LoadBalanced resolves a
//    stable LOGICAL name against a live service registry on every call, so routing always
//    reflects which instances are actually up right now.

// Q: "What actually intercepts the HTTP call — where does the load balancing logic live?"
// A: A LoadBalancerInterceptor added to the RestTemplate's interceptor chain by Spring Cloud's
//    auto-configuration. It's the interceptor that calls the LoadBalancerClient and rewrites
//    the request URI — @LoadBalanced itself is just a marker annotation with no logic in it.

// Q: "Client-side load balancing (this) vs server-side load balancing (a gateway) — what's
//     the difference?"
// A: Client-side: the calling service itself knows about all instances and picks one directly
//    (what @LoadBalanced does) — no extra network hop, but every client needs registry access.
//    Server-side: callers hit one stable address (a reverse proxy / API gateway / hardware LB)
//    which does the instance selection for them — simpler clients, but an extra hop and a
//    potential bottleneck/single point of failure at the proxy.

// Q: "What breaks if you call a public third-party API through a @LoadBalanced RestTemplate?"
// A: The interceptor tries to resolve the real hostname (e.g. api.stripe.com) against your
//    service registry instead of doing a normal DNS lookup — since no such service is
//    registered, you get "No instances available" or a similar load-balancer error, not a
//    real HTTP response.

// Q: "Why might a team choose Feign over @LoadBalanced RestTemplate for new services?"
// A: Feign gives you a type-safe interface instead of hand-built URL strings, less boilerplate
//    per call, and load balancing "for free" with no annotation to remember — while using the
//    exact same LoadBalancerClient machinery underneath.

// Q: "How does inventory-service even know the registry exists — is that auto-discovered too?"
// A: No — that's the one piece that ISN'T dynamic. The registry's address is set explicitly,
//    as plain config (eureka.client.service-url.defaultZone), on every service including the
//    registry's own clients. You can't discover the discovery service via discovery — something
//    has to be the fixed starting point, and that's it. On startup the client POSTs a
//    registration to that fixed address, then PUTs a heartbeat every ~30s to stay listed;
//    miss enough heartbeats and the registry evicts the instance automatically.
💡

Interviewers aren't testing whether you memorized the annotation name — they're testing whether you understand client-side vs server-side load balancing, and whether you've been bitten by pointing a load-balanced client at the wrong kind of host.
