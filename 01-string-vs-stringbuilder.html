01
Basic String Immutability
A String object can never be changed after it's created. Every method that looks like it "modifies" a String — concat(), toUpperCase(), replace() — actually returns a brand new String object.
🖼️

Printed photograph: You can't edit a printed photo. To "change" it you print a new photo. The old one still exists exactly as it was, until nobody references it anymore.

Java
public class Main {
  public static void main(String[] args) {

    String name = "sandeep";
    String upper = name.toUpperCase(); // does NOT change "name"

    System.out.println(name);  // sandeep — unchanged
    System.out.println(upper); // SANDEEP — a brand new object

    name.toUpperCase(); // return value thrown away — common beginner bug!
    System.out.println(name);  // still sandeep — nothing happened
  }
}
Output
sandeep SANDEEP sandeep
💡

Every "mutating" String method actually returns a new String. If you don't capture the return value, your change is silently lost.

02
Basic The String Constant Pool
Because Strings are immutable, the JVM can safely reuse identical literals. "hi" written twice in your code points to the same object in a special memory area called the string pool. new String(...) bypasses the pool and forces a fresh object.
🏛️

Library book: The pool is like a public library — everyone who asks for "hi" gets handed the SAME copy. new String("hi") is like buying your own personal copy instead of borrowing the shared one.

Java
public class Main {
  public static void main(String[] args) {

    String a = "hello";             // goes into the string pool
    String b = "hello";             // reuses the SAME pooled object
    String c = new String("hello"); // forces a NEW object on the heap

    System.out.println(a == b);          // true  — same pooled object
    System.out.println(a == c);          // false — different objects
    System.out.println(a.equals(c));     // true  — same characters

    String d = c.intern();           // manually pulls "hello" from the pool
    System.out.println(a == d);          // true  — now pointing at the pooled object
  }
}
Output
true false true true
💡

== compares identity (same object?). .equals() compares value (same characters?). For Strings, always use .equals() unless you specifically need identity.

03
Basic Why Immutability Matters
Immutability isn't just a quirk — it's a deliberate design choice that buys three big wins: free thread-safety, safe use as HashMap keys (hash code never changes), and protection against tampering after a value is handed to security-sensitive code.
Java
import java.util.HashMap;
import java.util.Map;

public class Main {
  public static void main(String[] args) {

    Map<String, Integer> ages = new HashMap<>();
    ages.put("sandeep", 32);
    // HashMap caches "sandeep".hashCode() the moment it's inserted.
    // If String were mutable and someone changed the key's characters
    // AFTER insertion, the cached hash code would no longer match —
    // the entry would become permanently unreachable. Immutability
    // guarantees that can never happen.

    System.out.println(ages.get("sandeep")); // 32 — always findable

    // Multiple threads can read the same String with zero locking —
    // there is no "in progress" state to see, because it can never change.
    String shared = "config-value";
    Runnable reader = () -> System.out.println(Thread.currentThread().getName() + ": " + shared);
    new Thread(reader).start();
    new Thread(reader).start();
  }
}
💡

Immutable objects are inherently thread-safe (nothing to corrupt) and make safe, stable hash keys (hash code can't drift after insertion).

04
Basic Concatenation Under the Hood
A single + between strings compiles to a hidden StringBuilder — fine. But += inside a loop creates a brand-new StringBuilder AND a brand-new String on every single iteration. That's O(n²) work to build one string.
📝

Rewriting the whole essay: Each loop iteration is like re-copying your entire essay onto a new page just to add one more word at the end. Word 1000 means you've copied the first 999 words 999 times.

Java
public class Main {
  public static void main(String[] args) {

    // fine — compiler turns this into ONE StringBuilder chain
    String greeting = "Hello, " + "Sandeep" + "!";
    System.out.println(greeting);

    // ❌ O(n²) — a NEW String object is allocated every iteration
    String result = "";
    for (int i = 0; i < 5; i++) {
      result += i + ","; // builds a new String each time, copying everything before it
    }
    System.out.println(result); // 0,1,2,3,4,
  }
}
Output
Hello, Sandeep! 0,1,2,3,4,
💡

A handful of + concatenations is fine. A loop that concatenates is a red flag — reach for StringBuilder instead.

05
Intermediate Introducing StringBuilder
StringBuilder wraps a mutable, resizable character array internally. append() just writes into free space at the end — no copying of existing characters, no new object per call. When the array fills up, it grows (usually doubles) and copies once, not every append.
📒

Growing notebook: Instead of rewriting the whole essay per word, you write into the next blank line of a notebook. When you run out of pages, you get a bigger notebook and copy over once — not after every single word.

Java
public class Main {
  public static void main(String[] args) {

    StringBuilder sb = new StringBuilder(); // default capacity: 16 chars
    System.out.println("capacity: " + sb.capacity()); // 16

    for (int i = 0; i < 5; i++) {
      sb.append(i).append(","); // writes into the SAME underlying array
    }

    String result = sb.toString(); // ONE final copy into an immutable String
    System.out.println(result);            // 0,1,2,3,4,
    System.out.println("length: " + sb.length()); // 10
  }
}
Output
capacity: 16 0,1,2,3,4, length: 10
💡

StringBuilder only converts to an immutable String once, when you call .toString(). Until then, everything mutates in place.

06
Intermediate StringBuilder vs StringBuffer
They have an identical API. The only difference: every method on StringBuffer is synchronized — safe to share across threads, but slower. StringBuilder (added in Java 5) has no locking. Almost all code is single-threaded inside one method, so StringBuilder is the modern default.
Java
public class Main {
  public static void main(String[] args) {

    // 99% of the time: local variable, one thread, one method — use this
    StringBuilder sb = new StringBuilder();
    sb.append("fast, ").append("unsynchronized");
    System.out.println(sb); // fast, unsynchronized

    // rare: the SAME buffer instance genuinely shared & mutated by multiple threads
    StringBuffer buf = new StringBuffer();
    Runnable appender = () -> buf.append("x"); // each append() call is synchronized
    Thread t1 = new Thread(appender);
    Thread t2 = new Thread(appender);
    t1.start(); t2.start();
  }
}
💡

Default to StringBuilder. Only reach for StringBuffer if the exact same instance is genuinely mutated by multiple threads — and even then, consider redesigning so each thread builds its own StringBuilder instead.

07
Intermediate StringBuilder Method Tour
Beyond append(), StringBuilder has a full editing toolkit: insert in the middle, delete a range, replace a range, reverse, and set a single character — all in place, no new objects until you call toString().
Java
public class Main {
  public static void main(String[] args) {

    StringBuilder sb = new StringBuilder("Hello World");

    sb.insert(5, ",");              // "Hello, World"
    System.out.println(sb);

    sb.delete(0, 6);               // removes "Hello,"  → " World"
    System.out.println(sb);

    sb.deleteCharAt(0);            // removes the leading space → "World"
    System.out.println(sb);

    sb.setCharAt(0, 'w');          // "world"
    System.out.println(sb);

    sb.replace(0, 5, "galaxy");  // "galaxy"
    System.out.println(sb);

    sb.reverse();                  // "yxalag"
    System.out.println(sb);
  }
}
Output
Hello, World World World world galaxy yxalag
💡

Every method here mutates sb directly and returns this, which is why you can chain calls: sb.append(a).insert(0,b).reverse().

08
Intermediate Prove It: A Real Benchmark
Talk is cheap — this program builds the same 100,000-character string two ways and times each with System.nanoTime(). The gap is not subtle: += is roughly 100×–1000× slower at this size, and the gap widens as the string grows.
Java
public class Main {
  public static void main(String[] args) {

    int n = 100_000;

    // ❌ String += in a loop — O(n²)
    long start1 = System.nanoTime();
    String slow = "";
    for (int i = 0; i < n; i++) {
      slow += "x";
    }
    long slowMs = (System.nanoTime() - start1) / 1_000_000;

    // ✅ StringBuilder.append() in a loop — O(n)
    long start2 = System.nanoTime();
    StringBuilder fast = new StringBuilder(n); // pre-size to avoid resizing entirely
    for (int i = 0; i < n; i++) {
      fast.append("x");
    }
    String result = fast.toString();
    long fastMs = (System.nanoTime() - start2) / 1_000_000;

    System.out.println("String +=      : " + slowMs + " ms");
    System.out.println("StringBuilder   : " + fastMs + " ms");
  }
}
Sample output (varies by machine)
String += : 4280 ms StringBuilder : 6 ms
💡

Pre-sizing the StringBuilder (new StringBuilder(n)) when you know roughly how big the result will be avoids resize-copies entirely — squeezing out even more performance.

09
Intermediate String.format & Text Blocks
Neither concatenation nor StringBuilder is the most readable choice for templated output. String.format() (or "%s".formatted(...) since Java 15) handles placeholders cleanly. Text blocks (""", Java 15+) make multi-line strings readable without escape-character soup.
Java
public class Main {
  public static void main(String[] args) {

    String name = "Sandeep";
    int age = 32;

    // readable templating instead of "Name: " + name + ", Age: " + age
    String formatted = String.format("Name: %s, Age: %d", name, age);
    System.out.println(formatted);

    // Java 15+ text block — no \n or string concatenation needed
    String json = """
        {
          "name": "%s",
          "age": %d
        }""".formatted(name, age);
    System.out.println(json);
  }
}
Output
Name: Sandeep, Age: 32 { "name": "Sandeep", "age": 32 }
💡

Use StringBuilder for loops, String.format/text blocks for one-shot readable templates. Neither replaces the other — they solve different problems.

Basic equals() vs ==
This is the single most asked Java interview question about Strings. == asks "is this the exact same object in memory?" .equals() asks "do these have the same characters?" Because of the string pool, == can accidentally "work" for literals — until it doesn't.
Java
public class Main {
  public static void main(String[] args) {

    String input = new Scanner(System.in).nextLine(); // imagine user typed "admin"
    String expected = "admin";

    if (input == expected) { // ❌ DANGEROUS — input is never pool-interned automatically
      System.out.println("Access granted (lucky, not correct)");
    } else {
      System.out.println("Access denied — even if input WAS \"admin\"!");
    }

    if (input.equals(expected)) { // ✅ CORRECT — compares actual characters
      System.out.println("Access granted (correctly!)");
    }
  }
}
// note: requires "import java.util.Scanner;" to actually compile and run
💡

Never use == to compare String values. It might pass by accident with literals and silently fail with anything read from user input, a file, or a network call.

Basic Core String Methods Cold
A handful of String methods come up constantly in interviews and real code: compareTo (lexicographic order), equalsIgnoreCase, contains, indexOf, substring, and isBlank() vs isEmpty().
Java
public class Main {
  public static void main(String[] args) {

    System.out.println("apple".compareTo("banana"));     // negative — "apple" < "banana"
    System.out.println("Admin".equalsIgnoreCase("admin")); // true
    System.out.println("hello world".contains("wor"));    // true
    System.out.println("hello world".indexOf("wor"));     // 6
    System.out.println("hello world".substring(6));     // world
    System.out.println("hello world".substring(0, 5)); // hello
    System.out.println("   ".isEmpty());          // false — has 3 spaces
    System.out.println("   ".isBlank());          // true  — only whitespace (Java 11+)
  }
}
Output
-1 true true 6 world hello false true
💡

isEmpty() only checks length 0. isBlank() (Java 11+) also treats whitespace-only strings as empty — usually the one you actually want for validating user input.

Intermediate split, join & StringJoiner
Going from String to pieces: split(regex). Going from pieces back to a delimited String: String.join(...) for simple cases, or StringJoiner when you need a custom prefix/suffix too (it's what powers Collectors.joining() internally).
Java
import java.util.Arrays;
import java.util.List;
import java.util.StringJoiner;

public class Main {
  public static void main(String[] args) {

    String[] parts = "sandeep,toronto,32".split(","); // ["sandeep","toronto","32"]
    System.out.println(Arrays.toString(parts));

    List<String> names = List.of("a", "b", "c");
    String joined = String.join(" - ", names); // "a - b - c"
    System.out.println(joined);

    StringJoiner sj = new StringJoiner(", ", "[", "]"); // delimiter, prefix, suffix
    sj.add("a").add("b").add("c");
    System.out.println(sj.toString()); // [a, b, c]
  }
}
Output
[sandeep, toronto, 32] a - b - c [a, b, c]
💡

split() takes a regex, not a literal — splitting on "." needs "\\." because . means "any character" in regex.

Advanced When Immutability Backfires
Immutability is the right default everywhere — except hot loops doing lots of small mutations, where it becomes a measurable cost. The fix is never "make String mutable," it's "use a mutable builder for the lifetime of the loop, then freeze the result."
Java
public class Main {

  // ❌ called 1 million times in a hot path — each call allocates 2 new Strings
  static String badNormalize(String s) {
    return s.trim().toLowerCase(); // 2 intermediate Strings per call — fine occasionally, costly at scale
  }

  // ✅ same intent, but the caller decides whether to batch it through one builder
  static String buildReport(String[] lines) {
    StringBuilder sb = new StringBuilder(lines.length * 32); // pre-size: rough capacity estimate
    for (String line : lines) {
      sb.append(line.trim()).append('\n'); // one builder for the WHOLE loop, not one per line
    }
    return sb.toString(); // freeze to an immutable String exactly once, at the end
  }

  public static void main(String[] args) {
    String[] lines = { "  hello  ", "  world  " };
    System.out.print(buildReport(lines)); // hello\nworld\n
  }
}
💡

The rule of thumb: one mutation → String is fine and clearer. A loop of mutations → one shared StringBuilder for the whole loop, frozen to a String once at the end.

Advanced Senior Interview FAQ
The questions that come up again and again at the senior level — short, confident answers beat long, vague ones.
🎤

Q: Why is String immutable in Java?
Security, thread-safety with zero locking, safe hashCode caching for use as HashMap/HashSet keys, and it enables the string pool to safely share objects.

🎤

Q: What is the string pool, and is there a memory leak risk with intern()?
It's a special area (part of the heap since Java 7, previously PermGen) where literal Strings are cached and reused. Pre-Java 7, calling .intern() on many unique dynamic strings could fill a fixed-size PermGen and cause OutOfMemoryError. Since Java 7+ the pool lives in the regular garbage-collected heap, so that specific leak risk is gone — but interning huge numbers of unique strings can still bloat memory unnecessarily.

🎤

Q: StringBuilder vs StringBuffer — when would you actually pick StringBuffer?
Almost never in new code. Only if the exact same builder instance is mutated directly by multiple threads without any other synchronization — and even then, redesigning to build per-thread and merge results is usually better.

🎤

Q: How would you efficiently build a large CSV string from 1 million records?
One StringBuilder (pre-sized with an estimate of total characters) reused across the whole loop, appending each row, calling .toString() once at the end — or even better, stream directly to a BufferedWriter so you never hold the whole 1M-row string in memory at once.

💡

Interviewers care less about memorized definitions and more about whether you immediately reach for the right tool — StringBuilder for loops, immutable String everywhere else.
