01
Basic ACID Properties Overview
Atomicity — all statements in a transaction succeed or none do. Consistency — a transaction moves the database from one valid state to another, never violating constraints. Isolation — concurrent transactions don't see each other's half-finished work. Durability — once committed, a crash a millisecond later can't undo it. These are database engine guarantees; Spring's @Transactional is just a convenient way to declare transaction boundaries around them.
🏦

Bank transfer: moving $50 from Account A to Account B is really two statements — debit A, credit B. Atomicity is the guarantee that you never end up in a world where A was debited but B was never credited (money vanishes) or B was credited twice (money appears from nowhere). It's both, or neither.

Java
public class TransferExample {

  // ❌ NO transaction wrapper — a crash between the two UPDATEs leaves money vanished
  static void unsafeTransfer(Connection conn, int fromId, int toId, double amount) throws SQLException {
    try (Statement st = conn.createStatement()) {
      st.executeUpdate("UPDATE accounts SET balance = balance - " + amount + " WHERE id = " + fromId);
      // ⚡ if the JVM crashes / network drops right here, A lost money but B never gained it
      st.executeUpdate("UPDATE accounts SET balance = balance + " + amount + " WHERE id = " + toId);
    }
  }

  // ✅ wrapped in a transaction — atomic: both happen, or the rollback undoes the first
  static void safeTransfer(Connection conn, int fromId, int toId, double amount) throws SQLException {
    conn.setAutoCommit(false); // 🔒 open a transaction — nothing commits until we say so
    try (Statement st = conn.createStatement()) {
      st.executeUpdate("UPDATE accounts SET balance = balance - " + amount + " WHERE id = " + fromId);
      if (amount > 1_000_000) throw new IllegalStateException("suspiciously large transfer");
      st.executeUpdate("UPDATE accounts SET balance = balance + " + amount + " WHERE id = " + toId);
      conn.commit(); // both statements become permanent together
    } catch (Exception e) {
      conn.rollback(); // undo the debit too — DB is exactly as if nothing happened
      throw new RuntimeException("transfer failed, rolled back", e);
    }
  }
}
Output
before: A=100.0 B=50.0 unsafeTransfer crashes after debit → A=50.0 B=50.0 ← $50 vanished! safeTransfer throws on oversized amount → rollback() runs → A=100.0 B=50.0 ← unchanged
💡

@Transactional in Spring primarily targets Atomicity and, via its isolation attribute, Isolation. Consistency is enforced by DB constraints (foreign keys, checks) and your application logic; Durability is the storage engine's job (write-ahead logs, fsync) once a commit succeeds.

02
Basic @Transactional Basics
Spring wraps a @Transactional bean in a proxy. Calling the method opens a transaction; a normal return commits it; an unchecked exception rolls it back — all the boilerplate from concept 1 collapses into one annotation.
Java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class AccountService {

  private final AccountRepository accountRepository;

  public AccountService(AccountRepository accountRepository) {
    this.accountRepository = accountRepository;
  }

  @Transactional // 🔒 proxy opens a tx on entry, commits on return, rolls back on RuntimeException
  public void transfer(long fromId, long toId, BigDecimal amount) {
    accountRepository.debit(fromId, amount);

    if (amount.compareTo(BigDecimal.valueOf(1_000_000)) > 0) {
      throw new IllegalStateException("suspiciously large transfer"); // triggers rollback
    }

    accountRepository.credit(toId, amount); // never reached if the check above throws
  }
}
Output
before: A=100.00 B=50.00 transfer(A, B, 2_000_000) throws IllegalStateException after (rolled back): A=100.00 B=50.00 ← debit() was undone automatically
💡

By default, Spring only rolls back on unchecked exceptions (RuntimeException/Error). A checked exception thrown from inside a @Transactional method commits unless you override that — see concept 5.

03
Intermediate Propagation Types
Propagation decides what happens when a @Transactional method is called while another transaction is already open. REQUIRED (default) joins the existing one, or starts a new one if there isn't one. REQUIRES_NEW always suspends the caller's transaction and starts a brand-new, independent one. NESTED creates a savepoint inside the same physical transaction — a rollback only unwinds to that savepoint. SUPPORTS joins if one exists, otherwise runs non-transactionally. MANDATORY throws if no transaction exists. NOT_SUPPORTED suspends any existing transaction and runs without one. NEVER throws if a transaction exists.
Java
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Propagation;
import org.springframework.transaction.annotation.Transactional;

@Service
public class AuditService {

  @Transactional(propagation = Propagation.REQUIRES_NEW) // 🆕 always its own transaction
  public void logAttempt(long accountId, String action) {
    auditRepository.save(new AuditEntry(accountId, action, Instant.now()));
  }
}

@Service
public class AccountService {

  private final AuditService auditService; // separate bean — needed so the proxy is honored, see concept 6

  @Transactional // default REQUIRED — this is the "outer" transaction
  public void withdraw(long accountId, BigDecimal amount) {
    auditService.logAttempt(accountId, "WITHDRAW_ATTEMPT"); // commits in its OWN transaction, right now

    throw new InsufficientFundsException("balance too low"); // rolls back the OUTER tx only
  }
}
Output
audit_log table: 1 row inserted ("WITHDRAW_ATTEMPT") ← committed independently withdraw() throws InsufficientFundsException → outer transaction rolled back accounts table: unchanged ← but the audit row from above SURVIVES
💡

REQUIRES_NEW is the standard pattern for "this must be recorded no matter what the caller does next" — audit trails, outbound notifications you don't want silently rolled back with the business transaction that triggered them.

Intermediate Isolation Levels & Read Phenomena
Isolation controls what one transaction is allowed to see of another transaction's uncommitted or concurrently changing work. The SQL standard defines four levels, each preventing more read anomalies than the last — at the cost of more locking and lower concurrency.
Isolation LevelDirty ReadNon-Repeatable ReadPhantom Read
READ_UNCOMMITTEDpossiblepossiblepossible
READ_COMMITTEDpreventedpossiblepossible
REPEATABLE_READpreventedpreventedpossible*
SERIALIZABLEpreventedpreventedprevented
Java
import org.springframework.transaction.annotation.Isolation;
import org.springframework.transaction.annotation.Transactional;

@Service
public class ReportingService {

  @Transactional(isolation = Isolation.READ_COMMITTED) // explicit override
  public BigDecimal currentBalance(long accountId) {
    return accountRepository.findBalance(accountId);
  }

  // Spring's default is Isolation.DEFAULT — it just delegates to the DB's own default,
  // which is REPEATABLE_READ on MySQL/InnoDB but READ_COMMITTED on PostgreSQL and Oracle.
  // Know your database — "the default" silently means different things on different engines.
  @Transactional
  public void defaultIsolationExample() { /* uses whatever the DB engine defaults to */ }
}
💡

Higher isolation buys more consistency but costs more locking and lower throughput under concurrent load. Pick the lowest level that still keeps your invariants safe — most CRUD services never need anything above READ_COMMITTED or the DB's default.

05
Intermediate rollbackFor / noRollbackFor
Spring's default rollback rule is inherited from EJB conventions: roll back on unchecked exceptions (RuntimeException, Error), but commit anyway on checked exceptions. This surprises almost everyone the first time it bites them in production.
Java
@Service
public class OrderService {

  // ❌ BUG: IOException is checked — Spring commits the DB writes despite the failure!
  @Transactional
  public void placeOrder(Order order) throws IOException {
    orderRepository.save(order);
    receiptPrinter.print(order); // throws checked IOException — printer offline
    // ➔ transaction still COMMITS: order.save() is now permanent even though printing failed
  }

  // ✅ FIX: tell Spring to treat this checked exception as rollback-worthy too
  @Transactional(rollbackFor = Exception.class)
  public void placeOrderFixed(Order order) throws IOException {
    orderRepository.save(order);
    receiptPrinter.print(order); // same IOException — this time it DOES roll back
  }
}
Output
placeOrder(): IOException thrown → orders table STILL HAS the row ← silent bug placeOrderFixed(): IOException thrown → orders table has NO row ← correctly rolled back
💡

If any code inside a @Transactional method can throw a checked exception, you almost always want rollbackFor = Exception.class — otherwise you'll silently commit partial work every time that checked path fires. The inverse, noRollbackFor, exists for the rarer case where you want an unchecked exception to not trigger a rollback.

06
Advanced The Self-Invocation Pitfall
@Transactional works because Spring wraps your bean in a proxy (JDK dynamic proxy or CGLIB subclass) that intercepts the method call to open/commit/rollback a transaction around it. Calling an annotated method from another method in the same class via this.method() calls the real object directly — the proxy is never involved, so no transaction is ever opened. This is one of the most common real-world Spring bugs, and it applies equally to @Async, @Cacheable, and any other proxy-based annotation.
Java
@Service
public class BrokenAccountService {

  public void callSelf() {
    this.updateData(); // ❌ calls the REAL object, bypassing the transactional proxy entirely
  }

  @Transactional
  public void updateData() {
    boolean active = TransactionSynchronizationManager.isActualTransactionActive();
    System.out.println("transaction active? " + active); // prints false when called via this.updateData()
    accountRepository.save(new Account(...)); // runs with NO transaction, NO rollback safety net
  }
}

// ✅ FIX: split into two beans so the caller invokes the PROXY, not the raw object
@Service
public class CallerService {
  private final AccountUpdater accountUpdater; // injected proxy

  public void callSelf() {
    accountUpdater.updateData(); // ✅ goes through the proxy — transaction opens correctly
  }
}

@Service
public class AccountUpdater {
  @Transactional
  public void updateData() { accountRepository.save(new Account(...)); }
}
Output
BrokenAccountService.callSelf() → transaction active? false ← the annotation was silently ignored CallerService.callSelf() → transaction active? true ← proxy invoked correctly
💡

Annotate-and-forget doesn't work across internal calls. This is the exact same pitfall as @Async's self-invocation problem (covered in the @Async guide) — both rely on the same proxy mechanism, so both silently no-op the same way when called via this.

07
Advanced readOnly, Timeout & Performance
readOnly = true is a hint: Hibernate skips dirty-checking and flushing for the session, and some drivers/routing layers use it to send the query to a read replica. timeout sets a hard ceiling (in seconds) after which Spring force-rolls-back a still-open transaction. Both matter because every open transaction holds a real connection (and often row locks) from your pool — a slow one starves everyone else.
Java
@Service
public class AccountQueryService {

  @Transactional(readOnly = true, timeout = 5) // no dirty-checking + force-rollback after 5s
  public List<Account> findHighValueAccounts(BigDecimal threshold) {
    return accountRepository.findByBalanceGreaterThan(threshold);
  }

  // ❌ ANTI-PATTERN: slow I/O inside a transactional method holds a DB connection idle
  @Transactional
  public void syncAccount(long id) {
    Account account = accountRepository.findById(id);
    externalBankApi.notify(account); // ⚠️ HTTP call while holding a pooled connection — do this OUTSIDE the tx
    account.setLastSynced(Instant.now());
  }
}
💡

Mark every pure-read service method readOnly = true — it's nearly free and meaningfully reduces ORM overhead at scale. Never perform slow I/O (HTTP calls, file access, messaging) inside a @Transactional method: it holds a pooled DB connection idle for the whole call, and under load that exhausts the connection pool for everyone.

08
Advanced Senior Interview FAQ
Five questions interviewers love, with the answer a senior candidate is expected to give.
Java
// Q: "What does @Transactional actually do under the hood?"
// A: Spring wraps the bean in a proxy (JDK dynamic proxy if it implements an interface,
//    CGLIB subclass otherwise). The proxy intercepts calls to annotated methods, asks a
//    PlatformTransactionManager to begin a transaction before the method runs, then commits
//    on a normal return or rolls back based on the exception thrown (see rollback rules).

// Q: "Why doesn't @Transactional work when called from within the same class?"
// A: Self-invocation (this.method()) calls the real, unproxied object directly — the proxy
//    that would open the transaction is never in the call path. The fix is to call through
//    another injected bean, or inject a self-reference obtained via AopContext.currentProxy()
//    (which requires exposeProxy=true) — but splitting into two beans is usually cleaner.

// Q: "Checked vs unchecked — which rolls back by default, and why does that surprise people?"
// A: Unchecked (RuntimeException/Error) rolls back by default; checked exceptions commit
//    unless you specify rollbackFor. It's an inherited EJB convention most developers never
//    read about until a checked IOException silently commits half-finished work in prod.

// Q: "REQUIRED vs REQUIRES_NEW — when would you pick REQUIRES_NEW?"
// A: REQUIRED (default) joins whatever transaction is already open, so a rollback anywhere
//    in the call chain rolls back everything together. REQUIRES_NEW suspends the caller's
//    transaction and starts an independent one — use it when a side effect (audit log,
//    outbound notification) must survive even if the surrounding business transaction fails.

// Q: "What's the danger of a long-running @Transactional method in a high-traffic service?"
// A: The transaction holds a real connection from the pool (and often row locks) for its
//    entire duration. A method doing slow I/O or heavy computation inside a transaction ties
//    up that connection the whole time — under load this exhausts the pool, and every other
//    request queues up waiting for a connection, turning one slow method into an outage.
💡

Senior interviews aren't testing whether you can recite the propagation table — they're testing whether you've been burned by a self-invocation bug or an exhausted connection pool in production and changed how you design services because of it.
