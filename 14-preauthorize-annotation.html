@PreAuthorize & Method Security
in Spring Boot

URL security protects an HTTP path. Method security protects a Java method — no matter how it gets called. Learn the full toolkit from "hasRole" to custom permission evaluators.

Two different layers of security

If you've done the JWT tutorial, you already built URL-based security: SecurityConfig decides which HTTP paths need a token, using authorizeHttpRequests(). That happens in a servlet Filter, before the request ever reaches a controller.

Method security is a second, independent layer. It protects an individual method call — whether that call comes from a REST controller, an internal service-to-service call, a scheduled @Scheduled job, or a Kafka listener. The HTTP layer doesn't even need to be involved.

URL security — authorizeHttpRequests()
Protects a PATH. "/admin/** needs ROLE_ADMIN." Runs in a servlet Filter, before any controller code executes.
vs
Method security — @PreAuthorize
Protects a METHOD. "This Java method needs ROLE_ADMIN." Runs via an AOP proxy, no matter who calls the method or how.

Why use both — defense in depth. Imagine someone refactors SecurityConfig and accidentally removes the rule that protected /admin/**. If AdminService.deleteEverything() also has @PreAuthorize("hasRole('ADMIN')") directly on it, the request still gets rejected — the method itself refuses to run for a non-admin caller, regardless of which URL led to it.

Enabling method security

Method security annotations are silently ignored until you turn them on. In Spring Security 6+ (Spring Boot 3+), that's a single annotation: @EnableMethodSecurity.

📄 src/main/java/com/example/demo/config/SecurityConfig.java
package com.example.demo.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.method.configuration.EnableMethodSecurity;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.web.SecurityFilterChain;

@Configuration
@EnableMethodSecurity
// @EnableMethodSecurity turns ON processing of @PreAuthorize, @PostAuthorize,
// @PreFilter and @PostFilter across the whole application context.
// Without this annotation the annotations compile fine but are NEVER checked —
// no error, no warning, just silently unprotected methods. This is one of the
// most common Spring Security misconfigurations in real codebases.
//
// (Spring Security 5 and earlier used @EnableGlobalMethodSecurity(prePostEnabled = true).
// @EnableMethodSecurity is the modern replacement and enables pre/post-style
// checks by default. @Secured and @RolesAllowed need to be turned on explicitly —
// see the "@Secured" section later in this tutorial.)
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http
            .csrf(csrf -> csrf.disable())
            .sessionManagement(session -> session
                .sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/auth/**").permitAll()
                .anyRequest().authenticated()
                // this is the URL layer — coarse, path-based
            );
        return http.build();
    }
}

Mental model: URL security is a bouncer at the front door checking IDs by neighborhood. Method security is a lock on every individual room's door, checked every time — no matter which hallway you walked down to reach it.

Step 1

@PreAuthorize — Check BEFORE the Method Runs

The workhorse annotation. Evaluates a SpEL (Spring Expression Language) boolean expression before the method body executes. If it's false, the method never runs.

The full SpEL vocabulary you'll actually use

ExpressionMeaning
hasRole('ADMIN')Authority must literally be ROLE_ADMIN — Spring prepends ROLE_ for you
hasAuthority('ORDERS_READ')Authority must literally be ORDERS_READ — no prefix added, use for fine-grained permissions
hasAnyRole('ADMIN','SUPPORT')True if the user has any one of the listed roles
isAuthenticated()Any logged-in user — no specific role needed
permitAll()Always true — used to document "intentionally open" methods
denyAll()Always false — useful while a method is still under construction
hasRole('ADMIN') or hasRole('SUPPORT')Full boolean logic — and, or, not all work
📄 src/main/java/com/example/demo/orders/OrderService.java
package com.example.demo.orders;

import org.springframework.security.access.prepost.PreAuthorize;
import org.springframework.stereotype.Service;

@Service
public class OrderService {

    @PreAuthorize("hasRole('ADMIN')")
    public void deleteAllOrders() {
        System.out.println("All orders deleted.");
    }

    @PreAuthorize("hasAuthority('ORDERS_READ')")
    public String viewOrder(String orderId) {
        return "Order " + orderId;
    }

    @PreAuthorize("isAuthenticated()")
    public String viewOwnProfile() {
        return "Profile data";
    }

    @PreAuthorize("hasRole('ADMIN') or hasRole('SUPPORT')")
    public void refundOrder(String orderId) {
        System.out.println("Refunding " + orderId);
    }
}
📄 src/main/java/com/example/demo/orders/OrderAdminController.java
package com.example.demo.orders;

import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/admin/orders")
public class OrderAdminController {

    private final OrderService orderService;

    public OrderAdminController(OrderService orderService) {
        this.orderService = orderService;
    }

    @DeleteMapping("/all")
    public ResponseEntity<String> deleteAll() {
        orderService.deleteAllOrders(); // @PreAuthorize check happens HERE, inside the proxy
        return ResponseEntity.ok("Deleted");
    }
}

What happens when the check fails

If the SpEL expression evaluates to false, the proxy throws AccessDeniedException before your method body ever runs — not a single line inside deleteAllOrders() executes. Spring Security's exception-handling filter catches it and turns it into an HTTP response.

curl -X DELETE http://localhost:8080/admin/orders/all \
  -H "Authorization: Bearer <token-for-a-non-admin-user>"

# Response: 403 Forbidden
# Body: {"error": "Forbidden", "message": "Access Denied"}
# The console NEVER prints "All orders deleted." — the method body didn't run.

Common gotcha: hasRole('ADMIN') checks for the authority string ROLE_ADMIN, not ADMIN. If your JWT/database stores the raw role as "ADMIN" without the prefix, hasRole('ADMIN') will always fail. Either store roles with the ROLE_ prefix, or switch to hasAuthority('ADMIN') which does no prefixing.

Step 2

@PostAuthorize — Check AFTER the Method Runs

Sometimes you can't decide if a caller is allowed until you've actually loaded the data and can inspect it. That's what @PostAuthorize is for.

Classic case: "you can view this order, but only if you own it." You don't know who owns ORD-1 until you've fetched it from storage — so the security check has to happen after the method runs, against the return value.

📄 src/main/java/com/example/demo/orders/OrderService.java
package com.example.demo.orders;

import org.springframework.security.access.prepost.PostAuthorize;
import org.springframework.stereotype.Service;

import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

@Service
public class OrderService {

    private final Map<String, Order> orders = new ConcurrentHashMap<>();

    public OrderService() {
        orders.put("ORD-1", new Order("ORD-1", "sandeep"));
        orders.put("ORD-2", new Order("ORD-2", "alex"));
    }

    @PostAuthorize("returnObject.ownerUsername == authentication.name or hasRole('ADMIN')")
    // "returnObject" is whatever this method returns. The method ALREADY RAN
    // by the time this check fires — it fetched the order from the map below.
    // If the check fails, AccessDeniedException is thrown and the caller
    // never sees the data, but the lookup itself already happened.
    public Order getOrder(String orderId) {
        return orders.get(orderId);
    }

    public static class Order {
        public final String id;
        public final String ownerUsername; // field name must match "returnObject.ownerUsername" above

        public Order(String id, String ownerUsername) {
            this.id = id;
            this.ownerUsername = ownerUsername;
        }
    }
}
# Logged in as "sandeep" — owns ORD-1
curl http://localhost:8080/orders/ORD-1 -H "Authorization: Bearer <sandeeps-token>"
# 200 OK — { "id": "ORD-1", "ownerUsername": "sandeep" }

# Logged in as "sandeep" — does NOT own ORD-2
curl http://localhost:8080/orders/ORD-2 -H "Authorization: Bearer <sandeeps-token>"
# 403 Forbidden — the order WAS fetched internally, then the response was blocked

Important caveat: because the method body runs first, never put anything irreversible inside a @PostAuthorize-protected method — like sending an email, charging a card, or writing an audit log entry. Those side effects already happened by the time the security check rejects the caller.

Step 3

Reaching Into Method Arguments With SpEL

You can reference any method parameter by name inside the SpEL expression using #paramName — this unlocks "only the owner can do this" checks.

📄 src/main/java/com/example/demo/users/UserService.java
package com.example.demo.users;

import org.springframework.security.access.prepost.PreAuthorize;
import org.springframework.stereotype.Service;

@Service
public class UserService {

    @PreAuthorize("#username == authentication.name or hasRole('ADMIN')")
    // #username refers to the METHOD PARAMETER named "username" below — Spring
    // Security binds parameter names via reflection at startup. This requires
    // the "-parameters" javac flag, which Spring Boot's Maven/Gradle plugin
    // enables automatically — you don't need to configure anything extra.
    //
    // "authentication.name" is the username of the currently logged-in caller
    // (taken from the SecurityContext that JwtFilter populated).
    public String getUserProfile(String username) {
        return "Profile for " + username;
    }
}
# Logged in as "sandeep", asking for OWN profile — allowed
curl http://localhost:8080/users/sandeep/profile -H "Authorization: Bearer <sandeeps-token>"
# 200 OK — "Profile for sandeep"

# Logged in as "sandeep", asking for SOMEONE ELSE's profile — denied
curl http://localhost:8080/users/alex/profile -H "Authorization: Bearer <sandeeps-token>"
# 403 Forbidden, unless sandeep has ROLE_ADMIN

You can also reach into object fields: if a method takes a DTO parameter, e.g. updateOrder(OrderUpdateRequest request), you can write @PreAuthorize("#request.ownerUsername == authentication.name") — SpEL property navigation works exactly like Java field/getter access.

Step 4

@PreFilter & @PostFilter — Trimming Collections

Instead of allowing or denying the WHOLE call, these two annotations silently remove individual elements from a List argument or a List return value.

📄 src/main/java/com/example/demo/orders/BatchOrderService.java
package com.example.demo.orders;

import org.springframework.security.access.prepost.PostFilter;
import org.springframework.security.access.prepost.PreFilter;
import org.springframework.stereotype.Service;

import java.util.List;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

@Service
public class BatchOrderService {

    private final Map<String, OrderService.Order> orders = new ConcurrentHashMap<>();

    public BatchOrderService() {
        orders.put("ORD-1", new OrderService.Order("ORD-1", "sandeep"));
        orders.put("ORD-2", new OrderService.Order("ORD-2", "alex"));
    }

    @PreFilter("filterObject.ownerUsername == authentication.name")
    // PreFilter runs BEFORE the method, removing any element of the List
    // argument where the SpEL expression is false. "filterObject" is the
    // current element while Spring iterates the list — like an implicit loop
    // variable. By the time the method body runs, the list has already
    // been trimmed down to only the caller's own orders.
    public void cancelOrders(List<OrderService.Order> ordersToCancel) {
        ordersToCancel.forEach(o -> System.out.println("Cancelled " + o.id));
    }

    @PostFilter("filterObject.ownerUsername == authentication.name or hasRole('ADMIN')")
    // PostFilter runs AFTER the method, removing elements from the RETURNED
    // list that fail the check. The method itself sees and returns
    // EVERYTHING — security trims the list afterward, before the caller
    // ever sees it.
    public List<OrderService.Order> getAllOrders() {
        return List.copyOf(orders.values()); // unfiltered — security trims the result
    }
}

Performance note: @PostFilter loads the FULL unfiltered dataset into memory before trimming it — it cannot push the filter down into a database query. For large datasets, prefer filtering in the repository query itself (e.g. findByOwnerUsername(username)) and reserve @PostFilter for small, already-in-memory collections.

Step 5

@Secured, @RolesAllowed & Custom Permissions

The simpler, SpEL-free alternatives — plus how to plug in your own business-logic-driven permission checks.

@Secured and @RolesAllowed (JSR-250)

Both predate the SpEL-based @PreAuthorize and only support a plain list of role names — no expressions, no and/or, no method arguments. You'll mostly see these in older codebases.

AnnotationSyntaxNotes
@PreAuthorizeFull SpEL — "hasRole('ADMIN') or #id == authentication.name"Spring-specific, most powerful, on by default with @EnableMethodSecurity
@SecuredPlain role list — {"ROLE_ADMIN", "ROLE_SUPPORT"}Spring-specific, needs securedEnabled = true explicitly
@RolesAllowedPlain role list — {"ADMIN", "SUPPORT"} (no prefix)JSR-250 standard, portable outside Spring, needs jsr250Enabled = true
📄 SecurityConfig.java — opt in to the legacy annotations
@Configuration
@EnableMethodSecurity(securedEnabled = true, jsr250Enabled = true)
// @PreAuthorize/@PostAuthorize/@PreFilter/@PostFilter are ON by default.
// @Secured and @RolesAllowed are OFF by default — you must opt in explicitly.
public class SecurityConfig { /* ...same filterChain() bean as before... */ }
@Secured("ROLE_ADMIN") // note the explicit ROLE_ prefix — @Secured does NOT add it for you
public void legacyAdminOnly() { System.out.println("Admin action"); }

@RolesAllowed("ADMIN") // no prefix — JSR-250 doesn't use the ROLE_ convention
public void jsr250AdminOnly() { System.out.println("Admin action"); }

Custom PermissionEvaluator — business-logic-driven checks

When "owns it" isn't as simple as comparing one field, write a PermissionEvaluator and call hasPermission(...) from SpEL.

📄 src/main/java/com/example/demo/security/OrderPermissionEvaluator.java
package com.example.demo.security;

import com.example.demo.orders.OrderService;
import org.springframework.security.access.PermissionEvaluator;
import org.springframework.security.core.Authentication;
import org.springframework.stereotype.Component;

import java.io.Serializable;

@Component
public class OrderPermissionEvaluator implements PermissionEvaluator {

    @Override
    public boolean hasPermission(Authentication auth, Object targetDomainObject, Object permission) {
        if (!(targetDomainObject instanceof OrderService.Order order)) return false;
        if ("EDIT".equals(permission)) {
            return order.ownerUsername.equals(auth.getName());
        }
        return false;
    }

    @Override
    public boolean hasPermission(Authentication auth, Serializable targetId, String targetType, Object permission) {
        return false; // not used in this example — required to satisfy the interface
    }
}
📄 SecurityConfig.java — wire the evaluator in
import org.springframework.security.access.expression.method.DefaultMethodSecurityExpressionHandler;
import org.springframework.security.access.expression.method.MethodSecurityExpressionHandler;

@Bean
static MethodSecurityExpressionHandler methodSecurityExpressionHandler(OrderPermissionEvaluator evaluator) {
    DefaultMethodSecurityExpressionHandler handler = new DefaultMethodSecurityExpressionHandler();
    handler.setPermissionEvaluator(evaluator);
    return handler;
}
@PreAuthorize("hasPermission(#order, 'EDIT')")
// #order is the method parameter — passed straight into your evaluator's
// "targetDomainObject" argument above.
public void editOrder(OrderService.Order order) {
    System.out.println("Editing " + order.id);
}
Step 6

The Self-Invocation Gotcha

The single most common way @PreAuthorize "mysteriously" doesn't work — and it's the exact same proxy mechanism behind @Transactional and @Cacheable.

Method security is implemented as an AOP proxy — Spring wraps your real bean in a proxy object at startup. When code calls orderService.deleteOrder(id) through that proxy, the proxy intercepts the call, runs the @PreAuthorize check, and only then forwards to the real method. This is the identical mechanism documented for the Proxy design pattern (see the Design Patterns tutorial's @Transactional example) — same proxy, same self-invocation bug.

Broken Calling through this bypasses the proxy entirely
@Service
public class OrderService {

    @PreAuthorize("hasRole('ADMIN')")
    public void deleteOrder(String id) {
        System.out.println("Deleting " + id);
    }

    public void bulkDelete(List<String> ids) {
        for (String id : ids) {
            this.deleteOrder(id); // 😱 @PreAuthorize is SILENTLY skipped here!
            // "this" refers to the RAW object, not the Spring-generated proxy
            // that wraps it. The proxy is what intercepts calls and runs the
            // @PreAuthorize check — going through "this" never touches the proxy.
        }
    }
}
Fixed Extract the secured method into a separate bean
@Service
public class OrderDeletionService {
    @PreAuthorize("hasRole('ADMIN')")
    public void deleteOrder(String id) {
        System.out.println("Deleting " + id);
    }
}

@Service
public class OrderBulkService {
    private final OrderDeletionService deletionService;

    public OrderBulkService(OrderDeletionService deletionService) {
        this.deletionService = deletionService; // injected — this IS the proxy
    }

    public void bulkDelete(List<String> ids) {
        for (String id : ids) deletionService.deleteOrder(id); // ✅ goes through the real proxy
    }
}

The other workaround — AopContext.currentProxy() with @EnableAspectJAutoProxy(exposeProxy = true) — lets you fetch the proxy from inside the same class and call through it. It works, but most teams consider it a code smell; extracting to a separate bean (shown above) is the cleaner, more testable fix.

Step 7

Testing Secured Methods

Use @WithMockUser to simulate a logged-in user with specific roles, without needing a real JWT.

📄 src/test/java/com/example/demo/orders/OrderServiceSecurityTest.java
package com.example.demo.orders;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.security.access.AccessDeniedException;
import org.springframework.security.test.context.support.WithMockUser;

import static org.junit.jupiter.api.Assertions.assertDoesNotThrow;
import static org.junit.jupiter.api.Assertions.assertThrows;

@SpringBootTest
class OrderServiceSecurityTest {

    @Autowired
    private OrderService orderService;

    @Test
    @WithMockUser(roles = "ADMIN")
    // @WithMockUser populates the SecurityContext for this test method only —
    // no real JWT, no real login flow needed.
    void adminCanDeleteAllOrders() {
        assertDoesNotThrow(() -> orderService.deleteAllOrders());
    }

    @Test
    @WithMockUser(roles = "USER")
    void nonAdminCannotDeleteAllOrders() {
        assertThrows(AccessDeniedException.class, () -> orderService.deleteAllOrders());
    }
}

Why this matters: these tests run against the REAL @PreAuthorize-protected proxy (because @SpringBootTest wires up the actual application context) — so they catch the exact self-invocation and "wrong role string" bugs covered earlier, not just whatever your test mocks assume.

Step 8

Senior Interview FAQ

The questions that come up once an interviewer knows you've actually used this in production.

Q: @PreAuthorize vs @Secured — why would you ever pick @Secured?
You usually wouldn't for new code — @PreAuthorize is a strict superset (SpEL includes plain role checks as a special case). @Secured shows up in legacy codebases predating Spring's SpEL-based method security, or in teams that want to forbid expressions entirely for auditability.
Q: How does method security actually work under the hood?
Spring AOP. At startup, any bean with a method-security annotation gets wrapped in a dynamic proxy (CGLIB by default for classes, JDK proxies for interfaces). The proxy registers a MethodInterceptor (AuthorizationManagerBeforeMethodInterceptor for @PreAuthorize) that evaluates the SpEL expression against the current SecurityContext before delegating to the real method. It's the same proxy infrastructure that powers @Transactional and @Cacheable.
Q: Why doesn't @PreAuthorize fire when you call a method from inside the same class?
Because this inside a class refers to the raw, unwrapped object — not the proxy Spring created around it. The check only runs when the call passes through the proxy, i.e. when some OTHER bean holds an injected reference and calls through it. See the Self-Invocation Gotcha section.
Q: @PreAuthorize vs URL-based security — which should you use?
Both, layered. URL security is fast, coarse, and catches most traffic before it reaches a controller. Method security is the precise, can't-be-bypassed-by-a-config-typo backstop, and it's the only option for code paths that don't go through HTTP at all (scheduled jobs, message listeners, internal service calls). Relying on only one layer is the actual anti-pattern.
Q: What's the practical difference between @PreFilter/@PostFilter and just filtering in your repository query?
@PostFilter loads the full unfiltered result set into memory first, then discards rows — it cannot push the condition into SQL/Mongo. For anything beyond small, already-in-memory lists, filter in the query (findByOwnerUsername) for performance; reserve @PreFilter/@PostFilter for cases where the filtering logic genuinely can't be expressed as a query predicate.

You now have the full toolkit: @PreAuthorize/@PostAuthorize for single-object checks, @PreFilter/@PostFilter for collections, @Secured/@RolesAllowed for simple legacy role checks, custom PermissionEvaluator for business-logic-driven permissions — and you know exactly why the self-invocation bug happens and how to avoid it.
