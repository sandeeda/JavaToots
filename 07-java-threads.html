01
Basic What is a Thread?
A thread is an independent worker that runs code. Normally Java runs one line at a time. With threads, multiple workers run simultaneously.
🍳

Kitchen analogy: One cook doing tasks one at a time = single thread. Hire two cooks working in parallel = two threads.

Java
public class Main {
  public static void main(String[] args) {

    Thread cook1 = new Thread(() -> {
      System.out.println("Cook 1: Chopping vegetables");
    });

    Thread cook2 = new Thread(() -> {
      System.out.println("Cook 2: Boiling water");
    });

    cook1.start(); // launches cook1 independently
    cook2.start(); // launches cook2 independently
  }
}
Output (order not guaranteed)
Cook 2: Boiling water Cook 1: Chopping vegetables
💡

A Thread is a separate worker that runs code independently. Call .start() — not .run() — to launch it in a new thread.

02
Basic Race Condition
When two threads read and write the same variable at the same time, updates get lost. count++ is secretly 3 steps: read → add → write. Two threads interleaving = corrupted data.
🔪

Shared knife: Both cooks grab it simultaneously. Both read count=5, both write 6. One increment silently lost.

Java
public class Main {

  // static field — shared by every thread in this JVM. DANGER zone.
  static int count = 0;

  public static void main(String[] args) throws InterruptedException {

    Thread t1 = new Thread(() -> {
      for (int i=0; i<1000; i++) count++; // read→add→write
    });
    Thread t2 = new Thread(() -> {
      for (int i=0; i<1000; i++) count++;
    });

    t1.start(); t2.start(); // both race immediately — no order guaranteed
    t1.join();  t2.join();  // main BLOCKS here until both threads finish

    System.out.println(count); // expected 2000 — rarely is
  }
}
Output (never 2000)
1743 1850 1991
💡

count++ is not atomic. Two threads doing it simultaneously = lost updates = wrong answer silently.

03
Basic synchronized
The fix for race conditions. Forces threads to take turns — only one can be inside the block at a time. Others wait at the door until the lock is released.
🔒

Lock on the knife drawer: Cook 1 grabs the lock, uses the knife, releases. Cook 2 was waiting — now they can go. One at a time. No overlap.

Java
public class Main {

  static int count = 0;
  static final Object lock = new Object(); // the shared lock — any Object works

  public static void main(String[] args) throws InterruptedException {

    Thread t1 = new Thread(() -> {
      for (int i=0; i<1000; i++) {
        synchronized (lock) { // 🔒 grab
          count++;             // safe
        }                      // 🔓 release
      }
    });

    Thread t2 = new Thread(() -> {
      for (int i=0; i<1000; i++) {
        synchronized (lock) { // same lock object as t1 — they take turns
          count++;
        }
      }
    });

    t1.start(); t2.start();
    t1.join();  t2.join();

    System.out.println(count); // always 2000
  }
}
Output — every single time
2000 ✅
💡

synchronized(lock): grab the lock, do the work, release it. Any other thread trying to enter waits until the lock is free.

04
Basic Wrong Lock Bug
Using synchronized on different lock objects = zero protection. Both threads enter simultaneously. False sense of safety with all the original bugs.
🚪

Two knife drawers: Cook 1 locks drawer A. Cook 2 locks drawer B. They don't block each other at all.

Java
// ❌ Broken.java — different lock objects = zero protection
public class Broken {

  static int count = 0;
  static final Object lockA = new Object();
  static final Object lockB = new Object(); // different object — this IS the bug

  public static void main(String[] args) throws InterruptedException {
    Thread t1 = new Thread(() -> {
      for (int i=0; i<100_000; i++)
        synchronized (lockA) { count++; }
    });
    Thread t2 = new Thread(() -> {
      for (int i=0; i<100_000; i++)
        synchronized (lockB) { count++; } // ⚠️ wrong lock!
    });

    t1.start(); t2.start();
    t1.join();  t2.join();

    System.out.println(count); // expected 200000 — almost never is
  }
}

// ✅ Fixed.java — one shared lock object = real mutual exclusion
public class Fixed {

  static int count = 0;
  static final Object lock = new Object(); // ONE lock, shared by both threads

  public static void main(String[] args) throws InterruptedException {
    Thread t1 = new Thread(() -> {
      for (int i=0; i<100_000; i++)
        synchronized (lock) { count++; }
    });
    Thread t2 = new Thread(() -> {
      for (int i=0; i<100_000; i++)
        synchronized (lock) { count++; }
    });

    t1.start(); t2.start();
    t1.join();  t2.join();

    System.out.println(count); // always 200000
  }
}
💡

synchronized only works when all threads use the exact same lock object. Different locks = no mutual exclusion.

05
Basic volatile
Each thread caches variables locally. One thread updates a value while another never sees the change. volatile forces all reads/writes to go directly to main memory.
📋

Whiteboard vs sticky notes: Without volatile, threads use their own sticky notes (cache). With it, everyone reads from the shared whiteboard.

Java
public class Main {

  // without volatile: worker may cache "running" and loop forever
  static volatile boolean running = true;

  public static void main(String[] args) throws InterruptedException {

    Thread worker = new Thread(() -> {
      long spins = 0;
      while (running) { // volatile forces a fresh read from main memory every loop
        spins++; // pretend work
      }
      System.out.println("Worker stopped! Spun " + spins + " times.");
    });

    worker.start();
    Thread.sleep(1000); // let the worker spin for 1 second
    running = false; // worker WILL see this on its very next loop check

    worker.join(); // wait for worker to actually exit before main exits
    System.out.println("Main done.");
  }
}
💡

volatile = visibility fix. Use for simple on/off flags. Does NOT protect count++ — that still needs synchronized.

06
Basic wait() and notify()
Threads sometimes need to communicate. wait() puts a thread to sleep and releases its lock. notify() wakes it up. Both must be inside synchronized.
🍽

Waiter and Cook: Waiter doesn't spin-check every second. Instead waiter sleeps (wait()). Cook finishes and shouts (notify()). Waiter wakes and serves.

Java
public class Main {

  static final Object lock = new Object();
  static boolean foodReady = false; // must be a FIELD — lambdas can't reassign local vars

  public static void main(String[] args) throws InterruptedException {

    Thread waiter = new Thread(() -> {
      synchronized (lock) {
        while (!foodReady) {      // always while, not if
          try {
            lock.wait();        // 😴 release lock + sleep until notified
          } catch (InterruptedException e) {
            Thread.currentThread().interrupt(); // restore interrupt status, don't swallow it
          }
        }
        System.out.println("Serving! ✅");
      }
    });

    Thread cook = new Thread(() -> {
      try {
        Thread.sleep(2000); // Runnable.run() has no throws clause — must catch here
      } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
      }
      synchronized (lock) {
        foodReady = true;
        lock.notify();           // 📢 wake the waiter
      }
    });

    waiter.start();
    cook.start();
    waiter.join();
    cook.join();
  }
}
💡

wait() = sleep and release lock. notify() = wake one waiter. Always use while not if to guard against spurious wakeups.

07
Basic notifyAll()
notify() wakes one random thread. notifyAll() wakes all waiting threads. When multiple threads should all react, use notifyAll() — the safer default.
Java
public class Main {

  static final Object lock = new Object();
  static boolean started = false;

  public static void main(String[] args) throws InterruptedException {

    Thread[] runners = new Thread[5];
    for (int i=1; i<=5; i++) {
      int id = i;
      runners[i-1] = new Thread(() -> {
        synchronized (lock) {
          while (!started) {
            try { lock.wait(); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
          }
        }
        System.out.println("Runner " + id + " started running! 🏃");
      });
      runners[i-1].start();
    }

    Thread starter = new Thread(() -> {
      try { Thread.sleep(2000); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
      synchronized (lock) {
        started = true;
        // lock.notify();    ⚠️  wakes 1 random runner — other 4 stay stuck forever
        lock.notifyAll();    // ✅  wakes ALL 5 runners at once
      }
    });
    starter.start();

    for (Thread r : runners) r.join();
    starter.join();
  }
}
💡

When in doubt, use notifyAll(). notify() can leave threads stuck waiting forever if the wrong one wakes up.

08
Intermediate ReentrantLock
More powerful than synchronized. Gives you try-without-waiting, timeouts, and lock inspection. Must manually call unlock() — always in a finally block.
Java
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;

public class Main {

  static int count = 0;
  static final ReentrantLock lock = new ReentrantLock();

  public static void main(String[] args) throws InterruptedException {

    // basic — blocks the calling thread until the lock is free
    lock.lock();
    try { count++; }
    finally { lock.unlock(); } // ALWAYS in finally!

    // try without waiting — returns immediately either way
    if (lock.tryLock()) {
      try { count++; } finally { lock.unlock(); }
    } else {
      System.out.println("Busy, skipping!");
    }

    // try with a timeout — waits up to 2s for the lock, then gives up
    if (lock.tryLock(2, TimeUnit.SECONDS)) {
      try { count++; } finally { lock.unlock(); }
    } else {
      System.out.println("Gave up after 2s");
    }

    System.out.println("count = " + count);
  }
}
💡

Use synchronized for simple cases. Use ReentrantLock for tryLock() and timeouts. Always unlock in finally.

09
Intermediate Thread Pool
Creating a new thread per task is expensive and doesn't scale. A pool keeps a fixed set of reusable threads. Tasks queue up, threads pick them when free.
👨‍🍳

Smart restaurant: Hire 3 cooks once. Customers queue. When a cook finishes, they take the next customer. Not hire/fire per customer.

Java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

public class Main {

  public static void main(String[] args) throws InterruptedException {

    ExecutorService pool = Executors.newFixedThreadPool(3); // 3 reusable worker threads

    for (int i=1; i<=10; i++) {
      int task = i;
      pool.submit(() ->
        System.out.println("Task "+task+" by "+Thread.currentThread().getName())
      );
    }

    pool.shutdown();                          // stop accepting NEW tasks; queued ones still run
    pool.awaitTermination(5, TimeUnit.SECONDS); // block here until all 10 tasks finish (max 5s)
    System.out.println("All tasks done — pool is shut down.");
  }
}
Output
Task 1 by pool-1-thread-1 Task 2 by pool-1-thread-2 Task 3 by pool-1-thread-3 Task 4 by pool-1-thread-1 ← reused!
💡

Never create new Thread() per request in production. Use ExecutorService. Always call shutdown().

10
Intermediate Callable & Future
Runnable returns nothing. Callable returns a value. Future is the promise of that value — call .get() when you need the result. It blocks like join().
📦

Order tracking: Order online → get order number immediately (Future). Do other things. Check when ready → package arrives (get()).

Java
import java.util.concurrent.ExecutionException;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class Main {

  public static void main(String[] args) throws InterruptedException, ExecutionException {

    ExecutorService pool = Executors.newFixedThreadPool(3);

    // 3 Callables submitted — all 3 start running immediately, in parallel
    Future<Integer> f1 = pool.submit(() -> { Thread.sleep(1000); return 10; });
    Future<Integer> f2 = pool.submit(() -> { Thread.sleep(2000); return 20; });
    Future<Integer> f3 = pool.submit(() -> { Thread.sleep(1500); return 30; });

    // .get() blocks until THAT task finishes — total wait ≈ 2s (the longest),
    // not 4.5s (1+2+1.5), because all 3 ran concurrently on the pool
    int total = f1.get() + f2.get() + f3.get();

    System.out.println(total); // 60
    pool.shutdown();
  }
}
💡

Callable = Runnable with a return value. Future.get() blocks and returns the result. Use get(timeout, unit) in APIs to avoid waiting forever.

11
Intermediate Deadlock
Two threads each hold a lock the other needs. Neither releases. Both wait forever. App freezes silently — no exception, no crash. The hardest thread bug.
🌉

Narrow bridge: A says "you go back first." B says "no, YOU go back." Neither moves. Forever.

Java
// ❌ Broken.java — opposite lock order 💀 this WILL hang forever
public class Broken {

  static final Object lockA = new Object();
  static final Object lockB = new Object();

  public static void main(String[] args) {
    Thread t1 = new Thread(() -> {
      synchronized (lockA) {
        System.out.println("t1: locked A, waiting for B...");
        sleep(500); // gives t2 time to grab B first — forces the interleaving
        synchronized (lockB) {
          System.out.println("t1: got both locks"); // never printed
        }
      }
    });

    Thread t2 = new Thread(() -> {
      synchronized (lockB) {
        System.out.println("t2: locked B, waiting for A...");
        sleep(500);
        synchronized (lockA) { // 💀 t1 holds A wants B, t2 holds B wants A
          System.out.println("t2: got both locks"); // never printed
        }
      }
    });

    t1.start();
    t2.start();
    System.out.println("Main launched both threads — the app is now frozen forever.");
    // no exception, no crash — jstack/VisualVM would show both threads BLOCKED
  }

  static void sleep(long ms) {
    try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
  }
}

// ✅ Fixed.java — BOTH threads acquire locks in the SAME order (A then B)
public class Fixed {

  static final Object lockA = new Object();
  static final Object lockB = new Object();

  public static void main(String[] args) throws InterruptedException {
    Thread t1 = new Thread(() -> {
      synchronized (lockA) {
        synchronized (lockB) {
          System.out.println("t1: got both locks");
        }
      }
    });

    Thread t2 = new Thread(() -> {
      synchronized (lockA) { // same order as t1 — no cycle possible
        synchronized (lockB) {
          System.out.println("t2: got both locks");
        }
      }
    });

    t1.start(); t2.start();
    t1.join();  t2.join();
    System.out.println("Both threads finished — no deadlock.");
  }
}
💡

Fix by ensuring all threads acquire locks in the same order. Or use tryLock(timeout) to give up instead of waiting forever.

12
Intermediate AtomicInteger
Thread-safe counter with no locks needed. Uses CPU-level CAS (Compare-And-Swap) — atomically read, compute, write in one hardware instruction. Faster than synchronized.
Java
import java.util.concurrent.atomic.AtomicInteger;

public class Main {

  static final AtomicInteger count = new AtomicInteger(0);

  public static void main(String[] args) throws InterruptedException {

    // quick API tour
    count.incrementAndGet(); // ++count, returns the NEW value
    count.getAndIncrement(); // count++, returns the OLD value
    count.addAndGet(5);      // count += 5, returns the NEW value
    count.get();             // just read, no change
    count.set(0);            // reset before the demo below

    // two threads, no lock anywhere — always ends at 2000
    Thread t1 = new Thread(() -> {
      for (int i=0;i<1000;i++) count.incrementAndGet();
    });
    Thread t2 = new Thread(() -> {
      for (int i=0;i<1000;i++) count.incrementAndGet();
    });

    t1.start(); t2.start();
    t1.join();  t2.join();

    System.out.println(count.get()); // always 2000
  }
}
💡

For single-variable operations — cleaner and faster than synchronized. For multi-step logic (check-then-act), still use synchronized.

13
Advanced ConcurrentHashMap
Regular HashMap is not thread-safe. ConcurrentHashMap locks only small segments — multiple threads can read/write different keys simultaneously with no contention.
Java
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

public class Main {

  static final ConcurrentHashMap<String,Integer> map = new ConcurrentHashMap<>();

  public static void main(String[] args) throws InterruptedException {

    map.put("pasta", 1);         // thread-safe
    map.putIfAbsent("pizza", 0);  // atomic check+put — no-ops if key already exists

    // 10 threads, all incrementing the SAME key concurrently — no external lock needed
    ExecutorService pool = Executors.newFixedThreadPool(10);
    for (int i=0; i<10; i++) {
      pool.submit(() -> map.compute("pasta", (k, v) -> v == null ? 1 : v + 1));
      // compute() is atomic per-key — read, recompute, write happens as one step
    }

    pool.shutdown();
    pool.awaitTermination(5, TimeUnit.SECONDS);

    System.out.println(map.get("pasta")); // always 11 (1 + 10 increments)

    // ❌ Never share a plain HashMap between threads like this:
    // Map<String,Integer> unsafe = new HashMap<>();
    // concurrent writers can corrupt internal bucket pointers — possible infinite loop 💀
  }
}
💡

Never share a HashMap between threads. ConcurrentHashMap = segment locking = much better throughput. Note: no null keys or values allowed.

14
Advanced CountDownLatch
Counter starts at N. Each thread calls countDown() when done. Main calls await() and blocks until counter hits zero. Cleaner than multiple join() calls — works with thread pools.
🏪

Restaurant opening: Counter starts at 5 (staff). Each arrival decrements. When it hits 0, restaurant opens — main thread was waiting at await().

Java
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

public class Main {

  public static void main(String[] args) throws InterruptedException {

    CountDownLatch latch = new CountDownLatch(5); // counter starts at 5

    ExecutorService pool = Executors.newFixedThreadPool(5);
    for (int i=1; i<=5; i++) {
      int cookId = i;
      pool.submit(() -> {
        System.out.println("Cook " + cookId + " arrived ✅");
        latch.countDown(); // 5→4→3→2→1→0, one per cook
      });
    }

    latch.await(); // main BLOCKS here until the count reaches 0
    System.out.println("Restaurant open! 🎉");

    // alternative — with a timeout, in case a cook never shows up:
    // boolean done = latch.await(10, TimeUnit.SECONDS);
    // if (!done) System.out.println("Timeout — opening anyway");

    pool.shutdown();
  }
}
💡

One-time gate — once it hits zero it stays zero. You'll use this in Kafka integration tests to wait for N messages to arrive before asserting.

15
Advanced Semaphore
Controls how many threads access a resource simultaneously. N permits — acquire() takes one, release() gives it back. When all taken, new threads wait. Perfect for rate limiting.
🅿️

Parking lot with 3 spots: 3 permits. Cars 1-3 enter. Car 4 waits. When Car 1 leaves and releases, Car 4 gets the permit and enters.

Java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Semaphore;
import java.util.concurrent.TimeUnit;

public class Main {

  public static void main(String[] args) throws InterruptedException {

    Semaphore parking = new Semaphore(3); // only 3 permits — 3 cars can park at once

    ExecutorService pool = Executors.newFixedThreadPool(6); // all 6 cars arrive "simultaneously"

    for (int i=1; i<=6; i++) {
      int car = i;
      pool.submit(() -> {
        try {
          parking.acquire(); // wait for a permit — blocks here if all 3 are taken
        } catch (InterruptedException e) {
          Thread.currentThread().interrupt();
          return; // never acquired a permit — must NOT release one below
        }

        try {
          System.out.println("Car "+car+" parked 🚗");
          Thread.sleep(2000); // occupies the spot for 2 seconds
        } catch (InterruptedException e) {
          Thread.currentThread().interrupt();
        } finally {
          parking.release(); // ALWAYS in finally — guaranteed even if sleep() is interrupted
        }
      });
    }

    pool.shutdown();
    pool.awaitTermination(10, TimeUnit.SECONDS);
    System.out.println("All cars processed.");
  }
}

// real Spring Boot services use the same idea to cap concurrent work:
Semaphore dbPool   = new Semaphore(5); // max 5 concurrent DB connections
Semaphore apiLimit = new Semaphore(3); // max 3 concurrent external API calls
💡

Semaphore(1) = mutex like synchronized. Semaphore(N) = allow N concurrent threads. Always release() in finally.
