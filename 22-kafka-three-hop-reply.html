The Three-Hop Reply

How a synchronous-feeling request/reply was built across three services on Kafka — A → B → C, with C answering A directly — at 200 TPS, with manual acknowledgment, tuned retries, circuit breakers on the enrichment calls, and dead-letter queues as the backstop against data loss.

01The problem

Three services, one logical transaction, no message broker feature that does this for you out of the box.

Three internal services — call them A, B, and C — needed to behave like a synchronous call chain while actually communicating over Kafka. A sent a unit of work to B. B transformed it and forwarded it to C. C did the final processing and sent the result directly back to A, not back through B. The caller of A was blocked (or held a callback) waiting on that final answer, at a sustained volume of roughly 200 transactions per second.

Every public example of Kafka request/reply — Spring's own documentation included — covers exactly two participants: a requester and a replier, using the same topic pair for the whole exchange. Almost nothing describes what happens when the reply has to come from a service that never received the original request directly. That gap, plus the requirement that no in-flight message could ever silently disappear, is what made this a genuinely non-trivial design rather than a copy-paste of a tutorial.

Constraints going in Sustained 200 TPS · zero tolerance for silent data loss · a three-service hop where the reply originates from the last hop, not the first · internal "massaging" calls inside each service that were themselves unreliable enough to need their own protection.

02Architecture

A initiates and waits; B relays and transforms; C answers on A's behalf. Every arrow that can fail has a dead-letter exit.

Two things make this different from the two-service tutorials: the reply on the dashed teal line originates at C, not at the service A actually called — and every solid arrow has a dashed red exit ramp, because at 200 TPS over a day, "retries exhausted" stops being a hypothetical.

03The hard part: a reply from the wrong service

ReplyingKafkaTemplate is built for a two-party exchange. Making C answer on A's behalf meant treating its correlation headers as a payload B had to carry, not consume.

ReplyingKafkaTemplate works by attaching two headers to the outbound record when the request is sent: KafkaHeaders.REPLY_TOPIC (the topic the caller is listening on) and KafkaHeaders.CORRELATION_ID (a UUID, added by an internal CorrelationIdPostProcessor if you don't set one yourself). The template registers a reply container — its own @KafkaListener-style consumer on the reply topic — and keeps a map of correlation ID → pending RequestReplyFuture. When a record lands on the reply topic with a matching correlation ID, that future completes and whoever called sendAndReceive() gets their answer.

That mechanism assumes the same process that consumed the request is the one that produces the reply. Here it isn't — B consumes A's message but C produces the reply. So B's job on the way out is not to terminate those headers, but to copy them, byte for byte, onto the record it sends to C. C's job is to read them back off the record it receives from B and stamp them onto the reply it sends to A, rather than generating anything of its own.

Service A — initiates the chainReplyingKafkaTemplate
ProducerRecord<String, OrderPayload> record =
    new ProducerRecord<>("req.b.topic", orderId, payload);

// template.replyTopic + a correlation id are attached automatically
RequestReplyFuture<String, OrderPayload, OrderResult> future =
    replyingKafkaTemplate.sendAndReceive(record, Duration.ofSeconds(8));

try {
    ConsumerRecord<String, OrderResult> reply = future.get(8, TimeUnit.SECONDS);
    handle(reply.value());
} catch (ExecutionException ex) {
    // underlying cause is a KafkaReplyTimeoutException if C never answered
    handleNoReply(orderId, ex);
}
Service B — plain listener, forwards headers untouched@KafkaListener
@KafkaListener(topics = "req.b.topic", groupId = "svc-b", containerFactory = "manualAckFactory")
public void onOrder(ConsumerRecord<String, OrderPayload> inbound, Acknowledgment ack) {

    OrderPayload enriched = enrichmentClient.massage(inbound.value()); // circuit-breaker guarded

    ProducerRecord<String, OrderPayload> outbound =
        new ProducerRecord<>("req.c.topic", inbound.key(), enriched);

    // the two headers that make the 3-hop reply possible
    outbound.headers().add(inbound.headers().lastHeader(KafkaHeaders.REPLY_TOPIC));
    outbound.headers().add(inbound.headers().lastHeader(KafkaHeaders.CORRELATION_ID));

    kafkaTemplate.send(outbound).get(5, TimeUnit.SECONDS); // block for the producer ack
    ack.acknowledge(); // only now — see §04
}
Service C — terminal hop, replies as Aplain KafkaTemplate, not Replying
@KafkaListener(topics = "req.c.topic", groupId = "svc-c", containerFactory = "manualAckFactory")
public void onEnrichedOrder(ConsumerRecord<String, OrderPayload> inbound, Acknowledgment ack) {

    OrderResult result = finalize(inbound.value()); // circuit-breaker guarded

    byte[] replyTopic = inbound.headers().lastHeader(KafkaHeaders.REPLY_TOPIC).value();
    byte[] correlationId = inbound.headers().lastHeader(KafkaHeaders.CORRELATION_ID).value();

    ProducerRecord<String, OrderResult> reply =
        new ProducerRecord<>(new String(replyTopic, UTF_8), inbound.key(), result);
    reply.headers().add(KafkaHeaders.CORRELATION_ID, correlationId); // verbatim — never regenerate

    kafkaTemplate.send(reply).get(5, TimeUnit.SECONDS);
    ack.acknowledge();
}
Why this is the interview story, not the boilerplate Every off-the-shelf write-up assumes request and reply share a topic pair and a service. The actual design work here was recognizing that REPLY_TOPIC and CORRELATION_ID are just headers — ordinary bytes that survive a hop as long as something deliberately copies them — and that the entire three-service illusion of a synchronous call collapses to "propagate two headers, ack in the right order, and let the reply container do the rest."

04Manual acknowledgment

Every hop only confirms the message it received once the side-effect of that message is durably on its way — never before.

By default, Spring Kafka commits offsets automatically in the background (enable.auto.commit=true), on a timer, regardless of whether your listener method actually finished successfully. That's fine for idempotent, disposable work. It is not fine here: if B crashed after acking A's message but before its own send to C reached the broker, that unit of work would vanish — read once, never produced downstream, gone. So auto-commit was switched off and every listener container was configured for manual acknowledgment.

@Bean
public ConcurrentKafkaListenerContainerFactory<String, OrderPayload> manualAckFactory(
        ConsumerFactory<String, OrderPayload> cf) {

    ConcurrentKafkaListenerContainerFactory<String, OrderPayload> factory =
        new ConcurrentKafkaListenerContainerFactory<>();
    factory.setConsumerFactory(cf);
    factory.getContainerProperties().setAckMode(ContainerProperties.AckMode.MANUAL_IMMEDIATE);
    factory.setConcurrency(12); // see §05
    factory.setCommonErrorHandler(errorHandler()); // see §06
    return factory;
}

The ordering rule applied at every hop was the same: do the downstream work, confirm the downstream write, then acknowledge the inbound record — never the reverse. That single discipline, repeated at B and at C, is what turns three independently-acking Kafka consumers into something that behaves like an all-or-nothing chain. It's not a distributed transaction — a crash between the downstream send and the ack still causes a redelivery, which is why producer idempotency (enable.idempotence=true, acks=all) and consumer-side dedupe keys mattered as much as the ack mode itself; see the pitfalls in §10.

05Concurrency & throughput at 200 TPS

Sustained throughput came from matching partition count to listener concurrency, then giving the consumer enough runway to survive a slow downstream hop without a false rebalance.

200 TPS end-to-end, across three hops with synchronous confirmation at each one, meant no single-threaded consumer could keep up. The lever for parallelism in Spring Kafka is concurrency on the listener container — it spins up that many consumer threads inside the same consumer group, and each one is only useful up to the number of partitions on the topic; a 12th thread against a 6-partition topic just sits idle.

Per-hop sizing that held 200 TPSapplication.yml
req.b.topic:
  partitions: 12
spring.kafka.listener.concurrency: 12   # one consumer thread per partition, no idle threads

spring.kafka.consumer:
  max-poll-records: 50        # bound how much unacked work one poll can hand out
  max-poll-interval-ms: 90000 # room for a full retry+circuit-breaker cycle before "you're dead, rebalance"
  session-timeout-ms: 30000
  heartbeat-interval-ms: 10000
  enable-auto-commit: false   # see §04
  auto-offset-reset: earliest

spring.kafka.producer:
  acks: all
  properties.enable.idempotence: true
  properties.delivery.timeout.ms: 30000
  properties.linger.ms: 5      # tiny batching window — latency-sensitive per hop
  properties.compression.type: snappy

The property that mattered most in practice was max.poll.interval.ms. Manual-ack processing that calls out to a downstream service — one that might itself be sitting in a circuit-breaker's waitDurationInOpenState — takes longer per record than a fire-and-forget consumer. If the whole cycle (call, retry backoff, produce downstream, wait for the producer ack) exceeded the poll interval, Kafka assumed the consumer was dead and triggered a rebalance mid-processing, which is its own source of duplicate work. Sizing that timeout to comfortably exceed the worst-case retry-plus-backoff budget — not just the happy-path latency — was what stopped rebalances from becoming a second, self-inflicted failure mode.

06Retries & backoff

Not every exception deserves a retry, and not every retry deserves the same delay. Both were made explicit rather than left to defaults.

Spring Kafka's DefaultErrorHandler sits in front of the listener and decides, per exception, whether to retry the record (seeking the consumer back to it) or hand it to a recoverer. Two decisions had to be made deliberately: how long to back off between attempts, and which exceptions are even worth retrying. A deserialization failure or a validation error will fail identically on attempt six as it did on attempt one — retrying it just delays the inevitable DLT trip and wastes consumer-group time that could go to good records.

Classified, backed-off error handlerDefaultErrorHandler
@Bean
public DefaultErrorHandler errorHandler(DeadLetterPublishingRecoverer recoverer) {

    ExponentialBackOffWithMaxRetries backOff = new ExponentialBackOffWithMaxRetries(5);
    backOff.setInitialInterval(500);   // 0.5s
    backOff.setMultiplier(2.0);
    backOff.setMaxInterval(10_000);    // cap at 10s

    DefaultErrorHandler handler = new DefaultErrorHandler(recoverer, backOff);

    // transient — worth retrying
    handler.addRetryableExceptions(
        TimeoutException.class, ResourceAccessException.class, TransientDataAccessException.class);

    // permanent — fail straight to the DLT, don't burn retry budget
    handler.addNotRetryableExceptions(
        DeserializationException.class, IllegalArgumentException.class, ValidationException.class);

    return handler;
}

Where a single blocking retry loop inside the listener would have stalled that partition — and, at 200 TPS, backed up behind it — the alternative Spring Kafka offers is non-blocking retries via @RetryableTopic, which republishes the failed record to a series of -retry-0, -retry-1… topics with their own backoff, freeing the main partition to keep moving while a failed record waits its turn on a side topic:

Non-blocking alternative — used where in-order blocking retry was too costly@RetryableTopic
@RetryableTopic(
    attempts = "5",
    backoff = @Backoff(delay = 500, multiplier = 2.0, maxDelay = 10_000),
    autoCreateTopics = "true",
    dltStrategy = DltStrategy.FAIL_ON_ERROR)
@KafkaListener(topics = "req.c.topic", groupId = "svc-c")
public void onEnrichedOrder(ConsumerRecord<String, OrderPayload> inbound, Acknowledgment ack) { … }

Both approaches route the same place on final failure: a DeadLetterPublishingRecoverer, covered in §08.

07Circuit breakers on the internal calls

Kafka-level retries protect the pipeline. Something else had to protect the pipeline from a downstream service that was slow rather than simply down.

Inside B and C, the "massaging" step called other internal services to enrich or validate the payload. A dependency that's fully down fails fast and is easy to retry around. A dependency that's slow is worse: every thread that calls it gets tied up waiting, retries pile on top of an already-struggling service, and the backlog on the Kafka side grows because nothing is completing fast enough to keep up with 200 TPS coming in. That's what a circuit breaker is for — it isn't a retry mechanism, it's a mechanism for giving up on a dependency early once it's clearly unhealthy, instead of finding out the hard way on every single call.

Resilience4j's CircuitBreaker tracks outcomes over a sliding window and moves through three states: CLOSED (calls flow normally), OPEN (calls fail immediately with CallNotPermittedException — no network round trip at all), and HALF_OPEN (a small number of probe calls are allowed through to test recovery before deciding whether to close again or re-open).

Circuit breaker + retry + timeout, composedapplication.yml
resilience4j.circuitbreaker.instances.enrichmentService:
  sliding-window-type: COUNT_BASED
  sliding-window-size: 50
  minimum-number-of-calls: 20
  failure-rate-threshold: 50        # open once >=50% of the last window failed
  slow-call-duration-threshold: 2s
  slow-call-rate-threshold: 50      # "slow" counts as a failure too

Applied to the enrichment callResilience4j annotations
@CircuitBreaker(name = "enrichmentService", fallbackMethod = "enrichmentFallback")
@Retry(name = "enrichmentService")
@TimeLimiter(name = "enrichmentService")
public CompletableFuture<EnrichedPayload> massage(OrderPayload payload) {
    return CompletableFuture.supplyAsync(() -> enrichmentClient.call(payload));
}

private CompletableFuture<EnrichedPayload> enrichmentFallback(OrderPayload payload, Throwable t) {
    // breaker open or all retries exhausted — surface as a retryable-by-Kafka failure,
    // which lets §06's error handler decide whether to retry the record or DLT it
    throw new EnrichmentUnavailableException(payload.getId(), t);
}

The composition order matters: TimeLimiter bounds how long any single call is allowed to hang, the CircuitBreaker decides whether to attempt the call at all, and Retry sits closest to the call itself. Retry is explicitly told to ignore CallNotPermittedException — retrying against an already-open breaker just wastes attempts and delays the fallback that lets the record fall through to Kafka's own retry/DLT handling.

08Dead letter queues — the non-negotiable backstop

"No data loss" isn't a property of the happy path. It's a property of what happens when everything above has already failed.

Once retries were exhausted — Kafka-level backoff exhausted, or the circuit breaker's fallback threw a non-retryable exception — the record could not simply be dropped or, worse, silently acked-and-forgotten to unblock the partition. Spring Kafka's DeadLetterPublishingRecoverer is what the DefaultErrorHandler (§06) falls through to: it republishes the original record, untouched, to a dead-letter topic — by convention <original-topic>.DLT — and stamps it with headers recording the original topic, partition, offset, and the exception's class name and message, so a human downstream doesn't have to guess what happened.

Recoverer wired into the error handlerDeadLetterPublishingRecoverer
@Bean
public DeadLetterPublishingRecoverer recoverer(KafkaTemplate<Object, Object> template) {
    return new DeadLetterPublishingRecoverer(template,
        (record, ex) -> new TopicPartition(record.topic() + ".DLT", record.partition()));
        // default resolver already does topic+".DLT"; shown explicitly for clarity
}

Two DLT-shaped gaps had to be closed explicitly rather than assumed away:

  • Failure inside B or C. Handled directly by the recoverer above — the record lands on req.b.topic.DLT or req.c.topic.DLT with full failure context, and is manually acked on the original topic only after the DLT publish succeeds, so the failure record itself can't be lost either.
  • A reply that never arrives. If C's message dies on req.c.topic.DLT, A is left holding a RequestReplyFuture that will never complete. That's not a Kafka-level loss — the request is safely parked on the DLT for the manual-review team — but it does mean A's future.get(timeout) call throws a KafkaReplyTimeoutException. A's timeout path logs the correlation ID and order ID against the same key the DLT record carries, so the on-call team can join the two: "A never heard back" and "here's exactly why, on the DLT" are answerable from the same identifier.
Why this closes the loop Retries and circuit breakers reduce how often a message needs to go to the DLT. They do not — and are not meant to — guarantee it never happens. The DLT, paired with a timeout path on the waiting side, is what turns "we tried our best" into "we can account for every message," which was the actual requirement.

10Pitfalls, and the way to tell the story

What actually broke first, and the shape of the answer that holds up under a follow-up question.

  • Redelivery after a partial hop. Manual ack means a crash between "sent to C" and "acked from B" causes B to reprocess and send to C again on restart. Kafka's producer idempotence stops duplicate low-level sends, but a fresh application-level send after redelivery is a new message from the broker's point of view — so C also carried a dedupe check keyed on the order ID for the narrow window where exactly-once wasn't otherwise guaranteed.
  • Rebalances caused by slow downstream calls, not slow consumers. The first version had max.poll.interval.ms at the framework default, which was shorter than a full retry-plus-open-circuit-breaker cycle at C. Under load, the group coordinator would rebalance C's partitions mid-processing, which look identical to a stuck consumer until you correlate the timing against circuit-breaker OPEN windows.
  • Retrying an already-open circuit breaker. Without explicitly telling Resilience4j's Retry to ignore CallNotPermittedException, every retry attempt against an open breaker still counted as an "attempt," burning the retry budget instantly and reaching the DLT far more eagerly than the actual dependency health warranted.

Three-service pipeline over Kafka, A → B → C, with C replying directly to A, at 200 TPS, with zero tolerance for silent message loss.
Task
Make the chain behave like a synchronous call without a two-service tutorial to follow, and without losing a message under any single failure.
Action
