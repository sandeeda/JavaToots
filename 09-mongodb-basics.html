01
Basic Document Model vs Relational
MongoDB stores documents (BSON — binary JSON) inside collections, instead of rows inside tables. A document can nest arrays and objects directly — no join needed to read related data that lives together.
📁

Folder vs filing cabinet: A relational DB is a filing cabinet with separate drawers (tables) you cross-reference by ID. MongoDB is a folder where the whole record — including its "child" data — lives in one self-contained document.

Relational — 2 tables, needs a JOIN
posts(id, title, author) comments(id, post_id, text, author) -- SELECT * FROM posts JOIN comments ON comments.post_id = posts.id
mongosh
// MongoDB — same data, one self-contained document
{
  _id: ObjectId("65f1a2b3c4d5e6f7a8b9c0d1"),
  title: "Why I Switched to Spring Boot 3",
  author: "sandeep",
  comments: [
    { text: "Great post!", author: "alice" },
    { text: "Did you try WebFlux?", author: "bob" }
  ]
}
// One read returns the post AND its comments — no JOIN required
💡

MongoDB trades strict normalization for read locality. Data that's always read together can live together — at the cost of needing a plan for keeping duplicated data in sync.

02
Basic CRUD Basics
The four basics: insertOne/insertMany, find with a filter, updateOne/updateMany with update operators, and deleteOne/deleteMany. All of these are runnable directly in the mongosh shell.
mongosh
// run mongosh, then: use bookstore

db.books.insertOne({ title: "Effective Java", author: "Bloch", price: 45, tags: ["java", "best-practices"] });

db.books.insertMany([
  { title: "Clean Code", author: "Martin", price: 38, tags: ["java"] },
  { title: "Designing Data-Intensive Applications", author: "Kleppmann", price: 55, tags: ["systems"] }
]);

// find — filter is a JSON document matching fields
db.books.find({ author: "Bloch" });

// updateOne — $set replaces a field, $inc bumps a number, $push appends to an array
db.books.updateOne(
  { title: "Effective Java" },
  { $set: { price: 40 }, $push: { tags: "interview-prep" } }
);

// deleteOne — removes the FIRST matching document only
db.books.deleteOne({ title: "Clean Code" });
find() output
[ { _id: ObjectId("65f1a..."), title: 'Effective Java', author: 'Bloch', price: 40, tags: [ 'java', 'best-practices', 'interview-prep' ] } ]
💡

updateOne/updateMany need an update operator like $set — passing a plain object without one REPLACES the whole document, wiping every other field.

03
Basic Query Operators
Beyond exact-match filters, Mongo gives you comparison ($gt/$lt), set membership ($in), existence ($exists), pattern matching ($regex), and boolean logic ($or/$and).
mongosh
// sample data first
db.books.insertMany([
  { title: "Effective Java", price: 40, inStock: true },
  { title: "Clean Code", price: 38, inStock: false },
  { title: "Java Concurrency in Practice", price: 52, inStock: true }
]);

// $gt / $lt — comparison
db.books.find({ price: { $gt: 39, $lt: 55 } });

// $in — value is one of a set
db.books.find({ price: { $in: [38, 40] } });

// $exists — field is present (or absent with false)
db.books.find({ inStock: { $exists: true } });

// $regex — pattern match on a string field (case-insensitive with 'i')
db.books.find({ title: { $regex: "java", $options: "i" } });

// $or / $and — combine conditions
db.books.find({
  $or: [ { price: { $lt: 39 } }, { inStock: false } ]
});
💡

Query operators always live as a nested object under the field name: { field: { $op: value } }, not { $op: field, value }.

04
Intermediate Embedding vs Referencing
The single most important MongoDB schema decision: should related data live inside the parent document (embed) or in its own collection referenced by ID (reference)? Get this wrong and everything downstream (indexes, queries, growth) gets harder.
⚖️

Rule of thumb: Embed when it's "one-to-few" and always read together (a blog post's tags). Reference when it's "one-to-many-at-scale" or updated independently (a customer's thousands of orders).

mongosh
// EMBED — address is small, fixed-size, always read with the user
{
  _id: ObjectId("..."),
  name: "Sandeep",
  address: { street: "123 Main St", city: "Toronto" }
}

// REFERENCE — an order history can grow unbounded; keep it in its own collection
// users collection:
{ _id: ObjectId("user1"), name: "Sandeep" }

// orders collection — each order POINTS BACK at the user by id:
{ _id: ObjectId("order1"), userId: ObjectId("user1"), total: 129.99 }
{ _id: ObjectId("order2"), userId: ObjectId("user1"), total: 45.50 }
// thousands more orders for user1 never bloat the user document
💡

A document has a hard 16MB size limit. Any array that grows without bound (orders, log entries, comments on a viral post) is a signal to reference, not embed.

Intermediate Indexes
Without an index, find() does a full collection scan — checking every document. An index is a sorted structure on one or more fields that lets Mongo jump straight to matches. Compound indexes (multiple fields) care about field order.
mongosh
// single-field index — speeds up queries filtering/sorting by email
db.users.createIndex({ email: 1 }, { unique: true }); // 1 = ascending

// compound index — field ORDER matters!
// this index helps queries that filter by status, then sort/filter by createdAt
db.orders.createIndex({ status: 1, createdAt: -1 });

// this query USES the index efficiently (matches field order):
db.orders.find({ status: "SHIPPED" }).sort({ createdAt: -1 });

// this query on createdAt ALONE can't use the compound index efficiently —
// status isn't a prefix of the filter, so Mongo can't seek directly
db.orders.find().sort({ createdAt: -1 });

// verify index usage
db.orders.find({ status: "SHIPPED" }).explain("executionStats");
// look for "stage": "IXSCAN" (good) vs "stage": "COLLSCAN" (bad — full scan)
💡

Compound index {a:1, b:1} serves queries on a alone or a+b together — but NOT efficiently on b alone. Order fields by what you filter on most, equality before range.

Intermediate Aggregation Pipeline
A pipeline of stages, each transforming the documents flowing through it — like Java Streams for your whole collection. $match filters, $group aggregates, $sort orders, $project reshapes.
mongosh
// sample sales data
db.sales.insertMany([
  { category: "books", amount: 40 },
  { category: "books", amount: 25 },
  { category: "electronics", amount: 300 },
  { category: "electronics", amount: 150 }
]);

// total sales per category, highest first
db.sales.aggregate([
  { $match: { amount: { $gt: 0 } } },                // stage 1: filter (like WHERE)
  { $group: { _id: "$category", total: { $sum: "$amount" } } }, // stage 2: aggregate (like GROUP BY)
  { $sort: { total: -1 } },                             // stage 3: order
  { $project: { _id: 0, category: "$_id", total: 1 } } // stage 4: reshape output fields
]);
Output
[ { category: 'electronics', total: 450 }, { category: 'books', total: 65 } ]
💡

Stages run in order, each one's output feeding the next. Put $match as early as possible — filtering first means later stages process fewer documents.

Intermediate $lookup — the Mongo "Join"
When you DID reference instead of embed, $lookup performs a left-outer-join-style merge inside the aggregation pipeline, pulling in matching documents from another collection.
mongosh
// users: { _id: ObjectId("u1"), name: "Sandeep" }
// orders: { _id: ObjectId("o1"), userId: ObjectId("u1"), total: 99.99 }

db.orders.aggregate([
  {
    $lookup: {
      from: "users",           // the other collection
      localField: "userId",     // field on THIS (orders) document
      foreignField: "_id",       // field on the OTHER (users) document
      as: "customer"            // result is added as an ARRAY under this name
    }
  },
  { $unwind: "$customer" } // flatten the 1-element array into a plain object
]);
Output
{ _id: ObjectId("o1"), userId: ObjectId("u1"), total: 99.99, customer: { _id: ObjectId("u1"), name: 'Sandeep' } }
💡

$lookup works, but it's not free — heavy use of it across large collections is often a sign you actually wanted embedding, or that a relational DB might fit better.

Advanced Schema Validation
"Schemaless" doesn't mean "no rules allowed." A $jsonSchema validator attached to a collection rejects documents that don't match required fields/types — a safety net against application bugs writing garbage.
mongosh
db.createCollection("books", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["title", "price"],
      properties: {
        title: { bsonType: "string" },
        price: { bsonType: "number", minimum: 0 }
      }
    }
  },
  validationAction: "error" // "error" rejects writes; "warn" just logs
});

// rejected — price is negative, violates "minimum": 0
db.books.insertOne({ title: "Bad Data", price: -5 });
// MongoServerError: Document failed validation
💡

Validation is enforced at the collection level on every write, not just by your application code — a second line of defense if a different service writes to the same collection without your app's checks.

Advanced Multi-Document Transactions
A single-document write is always atomic in MongoDB, no transaction needed. But updating two SEPARATE documents (e.g. across collections) atomically requires an explicit session-based transaction, available since MongoDB 4.0.
mongosh
// transferring money between two account documents — needs a transaction
const session = db.getMongo().startSession();
session.startTransaction();

try {
  const accounts = session.getDatabase("bank").accounts;

  accounts.updateOne({ _id: "acc1" }, { $inc: { balance: -100 } });
  accounts.updateOne({ _id: "acc2" }, { $inc: { balance: 100 } });

  session.commitTransaction(); // both updates become visible together, or neither does
} catch (e) {
  session.abortTransaction(); // roll back both on any failure
  throw e;
} finally {
  session.endSession();
}
💡

Transactions in Mongo carry a real performance cost. If a single atomic updateOne with $inc on ONE document can solve your problem, prefer that over a multi-document transaction.

Advanced Replica Sets
A replica set is a group of mongod servers holding the same data: one primary accepts all writes, and one or more secondaries replicate from it. If the primary dies, the set automatically elects a new primary.
📝

One writer, many readers of the carbon copy: Only the primary's "ledger" is authoritative. Secondaries continuously copy it, so if the primary goes down, a secondary that's caught up can take over.

mongosh
// connection string targeting a 3-node replica set named "rs0"
mongodb://node1:27017,node2:27017,node3:27017/?replicaSet=rs0

// reading from a secondary — accepts slightly stale data for less load on primary
db.books.find().readPref("secondaryPreferred");
// "primary" (default, always fresh) | "secondaryPreferred" | "secondary" | "nearest"
💡

Reading from a secondary trades consistency for throughput — you may read data that's a few milliseconds (or more, under load) behind the primary. Fine for dashboards, risky for "did my payment go through" checks.

Advanced Sharding Basics
When one replica set can't hold or serve all your data, sharding splits a collection across multiple replica sets ("shards") by a chosen shard key. Pick a bad shard key and one shard does all the work — a "hotspot."
mongosh
// enable sharding on a database, then shard a collection by customerId
sh.enableSharding("shopdb");
sh.shardCollection("shopdb.orders", { customerId: 1 });

// ❌ BAD shard key: an auto-incrementing createdAt timestamp —
// every new write has the HIGHEST value, so all inserts hit the SAME shard
sh.shardCollection("shopdb.orders", { createdAt: 1 }); // hotspot!

// ✅ GOOD shard key: high-cardinality, evenly distributed, matches query patterns
sh.shardCollection("shopdb.orders", { customerId: "hashed" });
💡

A good shard key has high cardinality (many distinct values), spreads writes evenly, and — ideally — matches the field you filter by most, so queries can target one shard instead of scattering to all of them.

Intermediate Spring Data MongoDB
Spring Data MongoDB maps a @Document-annotated class to a collection, and a MongoRepository interface gives you CRUD + derived query methods for free — the same DI-friendly pattern as Spring Data JPA.
Java
package com.example.demo.book;

import org.springframework.data.annotation.Id;
import org.springframework.data.mongodb.core.mapping.Document;

@Document(collection = "books")
public class Book {

    @Id
    private String id;
    private String title;
    private String author;
    private double price;

    public Book() {}

    public Book(String title, String author, double price) {
        this.title = title;
        this.author = author;
        this.price = price;
    }

    public String getId() { return id; }
    public String getTitle() { return title; }
    public String getAuthor() { return author; }
    public double getPrice() { return price; }
}
Java
package com.example.demo.book;

import org.springframework.data.mongodb.repository.MongoRepository;
import java.util.List;

public interface BookRepository extends MongoRepository<Book, String> {
    List<Book> findByAuthor(String author); // derived query — no implementation needed
    List<Book> findByPriceLessThan(double price);
}
Java
package com.example.demo.book;

import org.springframework.stereotype.Service;
import java.util.List;

@Service
public class BookService {

    private final BookRepository bookRepository;

    public BookService(BookRepository bookRepository) {
        this.bookRepository = bookRepository;
    }

    public Book addBook(String title, String author, double price) {
        return bookRepository.save(new Book(title, author, price));
    }

    public List<Book> cheapBooksBy(String author, double maxPrice) {
        return bookRepository.findByAuthor(author).stream()
            .filter(b -> b.getPrice() < maxPrice)
            .toList();
    }
}
💡

Method names like findByPriceLessThan are parsed by Spring Data into a real Mongo query — no @Query annotation needed for simple cases.

Advanced Common Pitfalls
Three recurring mistakes: letting an embedded array grow without bound, forgetting indexes (every query becomes a full scan), and forcing relational thinking onto a document model (or the opposite — embedding everything and hitting the 16MB limit).
mongosh
// ❌ unbounded embedded array — a "viral" post's comments array
// keeps growing until the document hits the 16MB hard limit and writes start failing
{ _id: "post1", comments: [ /* could become millions of entries */ ] }

// ✅ fix — reference instead, paginate comments from their own collection
{ _id: "comment1", postId: "post1", text: "..." }
db.comments.find({ postId: "post1" }).limit(20).skip(0);

// ❌ missing index — this silently does a full COLLSCAN on a huge collection
db.orders.find({ customerEmail: "sandeep@email.com" }); // slow at scale

// ✅ fix — index the field you actually filter on
db.orders.createIndex({ customerEmail: 1 });
💡

"Schemaless" is a trap if taken literally — design your documents as deliberately as you would design SQL tables. The flexibility is for evolving the shape over time, not for skipping the design step.

Basic ObjectId
The default _id type. It's 12 bytes: a 4-byte creation timestamp, plus bytes that make it unique across machines and processes without a central counter — which means it's naturally roughly sortable by creation time.
mongosh
const id = ObjectId("65f1a2b3c4d5e6f7a8b9c0d1");

print(id.getTimestamp()); // extracts the embedded creation Date — no separate createdAt field needed!

// sorting by _id ascending is (approximately) sorting by creation time —
// great for "most recent N documents" without a dedicated timestamp index
db.events.find().sort({ _id: -1 }).limit(10);
💡

ObjectId's timestamp granularity is only 1 second — for events created in the same second, relative order isn't guaranteed. Add an explicit timestamp field if you need millisecond precision.

Advanced Senior Interview FAQ
The questions that come up once an interviewer knows you've used Mongo beyond a tutorial — they're testing judgment, not syntax recall.
FAQ
// Q: When would you choose Mongo over Postgres, and vice versa?
// A: Mongo — flexible/evolving schema, data naturally nested (catalogs, CMS
//    content, event logs), horizontal scale via sharding is a first-class
//    feature. Postgres — strong relational integrity, complex multi-table
//    JOINs and ad-hoc reporting queries, ACID transactions are the norm
//    rather than the exception. Many real systems use BOTH.

// Q: How do transactions work in Mongo and what's the tradeoff?
// A: Session-based, two-phase-commit-like under the hood across replica set
//    members. Single-document writes are atomic for free; multi-document
//    transactions add real latency, so reach for them only when you truly
//    need atomicity across more than one document.

// Q: What's a shard key and how do you pick a good one?
// A: The field (or fields) Mongo uses to decide which shard owns a document.
//    A good one has high cardinality, distributes writes evenly (avoiding a
//    monotonically increasing key like a timestamp), and ideally matches
//    your most common query filter so reads can target one shard.

// Q: Embedding vs referencing — what's your decision framework?
// A: Embed when the data is bounded in size, always read together, and
//    rarely updated independently. Reference when it grows unbounded, is
//    queried/updated on its own, or is shared across multiple parents.
💡

Senior interviews aren't testing command syntax — they're testing whether you can justify a schema/scaling decision and explain its tradeoff out loud.
