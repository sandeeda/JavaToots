01
Basic What is Redis?
Redis (REmote DIctionary Server) is an in-memory data store. Everything lives in RAM, so reads/writes take microseconds instead of the milliseconds a disk-backed database needs. It's commonly used as a cache, but it's really a fast key-value engine with several built-in data structures.
📝

Sticky notes on your desk vs filing cabinet down the hall: Your database is the filing cabinet — durable, organized, but a walk away. Redis is the sticky note stuck to your monitor — instantly visible, but if the building burns down (server restarts without persistence), it's gone unless you photographed it first (RDB/AOF).

redis-cli
# start a local Redis server (default port 6379), then connect:
redis-cli

# every Redis command below is typed straight into that prompt
127.0.0.1:6379> SET greeting "hello"
OK
127.0.0.1:6379> GET greeting
"hello"
127.0.0.1:6379> PING
PONG
💡

Redis is single-threaded for command execution — one command runs to completion before the next starts. That's actually why it's fast and predictable (no lock contention), but it also means a slow command (like KEYS * on a huge keyspace) blocks every other client until it finishes. Use SCAN instead of KEYS in production.

02
Basic Core Data Structures
Redis isn't just key → string. Every key can hold a String, List, Set, Sorted Set, or Hash — each with its own commands. Picking the right structure for the job is most of what "knowing Redis" means.
redis-cli
# STRING — simplest type: counters, flags, cached blobs
SET page:views 0
INCR page:views          # atomic +1, returns 1
INCRBY page:views 5      # atomic +5, returns 6

# LIST — ordered, duplicates allowed: queues, recent-activity feeds
LPUSH recent:logins "sandeep"   # push to the LEFT (front)
RPUSH recent:logins "alice"     # push to the RIGHT (back)
LRANGE recent:logins 0 -1    # 0 to -1 = the whole list
# 1) "sandeep"  2) "alice"

# SET — unordered, unique members: tags, "has this user done X"
SADD user:42:roles "ADMIN" "USER"
SMEMBERS user:42:roles
SINTER user:42:roles user:43:roles   # roles BOTH users share

# SORTED SET — unique members ranked by a score: leaderboards, rate limits
ZADD leaderboard 1500 "sandeep"
ZADD leaderboard 2200 "alice"
ZRANGE leaderboard 0 -1 WITHSCORES
# 1) "sandeep" 2) "1500"  3) "alice" 4) "2200" — sorted ascending by score
ZSCORE leaderboard "alice"            # "2200"

# HASH — field/value pairs under one key: storing an object's fields
HSET user:42 name "Sandeep" city "Toronto"
HGET user:42 name           # "Sandeep"
HGETALL user:42             # all fields at once
💡

Sorted Set is the one senior engineers reach for most — score-ranked uniqueness covers leaderboards, priority queues, time-windowed rate limiters, and "top N" feeds without a single SQL ORDER BY.

03
Basic TTL and Expiration
A key can have a Time-To-Live — after it expires, Redis deletes it automatically. This is the single most important habit for using Redis as a cache: almost every cache key should have a TTL, or you'll eventually run out of memory holding stale data forever.
redis-cli
SET session:abc123 "sandeep"
EXPIRE session:abc123 1800    # expires in 1800 seconds (30 min)
TTL session:abc123         # how many seconds are left? e.g. "1797"

# SETEX = SET + EXPIRE in one atomic command — prefer this
SETEX session:def456 1800 "alice"

# remove the expiration — key now lives forever again
PERSIST session:abc123
TTL session:abc123         # "-1" means no TTL set

# TTL on a key that doesn't exist:
TTL no_such_key            # "-2" means the key is missing entirely
💡

Prefer SETEX (atomic) over a separate SET + EXPIRE — between those two calls a crash or race could leave the key without a TTL forever.

PracticeQ3 — Expiring cache key

04
Basic Eviction Policies
Redis has a configured maxmemory limit. When it's hit, the eviction policy decides what gets deleted to make room for new writes. Pick the wrong policy and either writes start failing, or the wrong keys disappear.
📦

A full fridge: When there's no room for new groceries, do you refuse to buy more (noeviction), throw out whatever's oldest (LRU), or throw out whatever you eat least often (LFU)? Each strategy fits a different kitchen.

redis.conf
# set in redis.conf, or live with CONFIG SET
maxmemory 100mb
maxmemory-policy allkeys-lru

# the policy options:
# noeviction      — refuse new writes once full (errors out, nothing deleted)
# allkeys-lru     — evict the Least Recently Used key, from ANY key
# allkeys-lfu     — evict the Least Frequently Used key, from ANY key
# volatile-lru    — evict LRU, but ONLY among keys that have a TTL set
# volatile-ttl    — evict the key with the SHORTEST remaining TTL first
# allkeys-random  — evict a random key (rarely what you want)

# check current usage at any time:
127.0.0.1:6379> INFO memory
# used_memory_human:87.50M
# maxmemory_policy:allkeys-lru
💡

For a pure cache, allkeys-lru is the safe default. For a mixed workload (some keys are cache, some are durable data with no TTL), use volatile-lru so Redis only ever evicts keys you explicitly marked as expendable.

PracticeQ4 — Watch eviction happen

05
Intermediate Cache-Aside Pattern
The most common caching pattern: check cache first, fall back to the database on a miss, then populate the cache for next time. The application owns the logic — Redis itself doesn't know about your database.
Java
import org.springframework.data.redis.core.RedisTemplate;
import org.springframework.stereotype.Service;
import java.time.Duration;

@Service
public class ProductService {

    private final RedisTemplate<String, Product> redis;
    private final ProductRepository db;

    public ProductService(RedisTemplate<String, Product> redis, ProductRepository db) {
        this.redis = redis;
        this.db = db;
    }

    public Product getProduct(String id) {
        String key = "product:" + id;

        Product cached = redis.opsForValue().get(key); // 1. check cache
        if (cached != null) {
            return cached;             // cache hit — fast path, done
        }

        Product fromDb = db.findById(id)        // 2. miss — go to the DB
            .orElseThrow(() -> new ProductNotFoundException(id));

        redis.opsForValue().set(key, fromDb, Duration.ofMinutes(10)); // 3. populate cache, with a TTL
        return fromDb;
    }
}
💡

Cache-aside is lazy — nothing is cached until it's actually requested once. That's usually exactly what you want: you only spend cache memory on data that's actually being read.

06
Intermediate @Cacheable, @CacheEvict, @CachePut
Spring's caching annotations write the cache-aside pattern from concept 5 for you, via an AOP proxy (the same proxy mechanism behind @Transactional and @PreAuthorize). One annotation replaces the manual check-miss-populate dance.
Java
import org.springframework.cache.annotation.CacheEvict;
import org.springframework.cache.annotation.CachePut;
import org.springframework.cache.annotation.Cacheable;
import org.springframework.stereotype.Service;

@Service
public class ProductService {

    private final ProductRepository db;
    public ProductService(ProductRepository db) { this.db = db; }

    @Cacheable(value = "products", key = "#id")
    public Product getProduct(String id) {
        System.out.println("Cache MISS — hitting the DB for " + id);
        return db.findById(id).orElseThrow();
        // Spring only runs this method body on a cache miss.
        // On a hit, the method body never executes at all — the proxy
        // intercepts the call and returns the cached value directly.
    }

    @CachePut(value = "products", key = "#product.id")
    public Product updateProduct(Product product) {
        return db.save(product);
        // @CachePut ALWAYS runs the method, then updates the cache with the
        // return value — used for writes, where you want the DB updated
        // AND the cache refreshed to match, not served from a stale cache.
    }

    @CacheEvict(value = "products", key = "#id")
    public void deleteProduct(String id) {
        db.deleteById(id);
        // removes the entry from the cache so the next getProduct(id)
        // call is forced to go back to the DB (or correctly 404)
    }
}
💡

Just like @PreAuthorize and @Transactional, these annotations are proxy-based — calling getProduct() from inside the same class bypasses the proxy and skips the cache entirely. Same self-invocation gotcha, every time.

07
Intermediate Cache Invalidation Strategies
"There are only two hard things in Computer Science: cache invalidation, and naming things." Stale cached data is worse than no cache at all if nobody ever clears it. There are three main strategies, often combined.
Java
// STRATEGY 1 — TTL-based: just let it expire. Simple, eventually consistent.
redis.opsForValue().set("product:42", product, Duration.ofMinutes(10));
// up to 10 minutes of staleness after a DB update — fine for product listings,
// NOT fine for a bank balance

// STRATEGY 2 — explicit eviction on write: clear it the moment data changes
@CacheEvict(value = "products", key = "#product.id")
public void onProductUpdated(Product product) { System.out.println("evicted"); }
// zero staleness window, but only works if EVERY write path remembers to evict —
// miss one update path and you have a silent, hard-to-find stale-cache bug

// STRATEGY 3 — stale-while-revalidate: serve the old value immediately,
// kick off a background refresh, so nobody ever waits on a cache miss
public Product getProductStaleOk(String id) {
    Product cached = redis.opsForValue().get("product:" + id);
    if (cached != null) {
        if (isNearExpiry(id)) refreshInBackground(id); // async, doesn't block this request
        return cached; // caller still gets an instant response
    }
    return loadAndCache(id);
}
💡

Default to TTL + explicit eviction together: evict on write for correctness, but keep a TTL as a safety net in case an eviction path is ever missed. Belt and suspenders.

08
Advanced Cache Stampede
A hot key expires. In the same instant, thousands of requests all miss the cache and all hammer the database at once trying to refill it — the "thundering herd." The DB that was handling 200 cached reads/sec suddenly gets 200 simultaneous queries.
🏛️

One door, one cashier, a sold-out concert: The moment the box office opens, everyone rushes the same door at once. A bouncer who lets one person through to "check if tickets exist" while everyone else waits outside avoids the crush.

Java
import org.springframework.data.redis.core.RedisTemplate;
import org.springframework.stereotype.Service;
import java.time.Duration;
import java.util.concurrent.ThreadLocalRandom;

@Service
public class ProductService {

    private final RedisTemplate<String, String> redis;
    public ProductService(RedisTemplate<String, String> redis) { this.redis = redis; }

    public String getProduct(String id) {
        String key = "product:" + id;
        String cached = redis.opsForValue().get(key);
        if (cached != null) return cached;

        String lockKey = "lock:" + key; // 1. only ONE caller wins this lock
        boolean gotLock = Boolean.TRUE.equals(
            redis.opsForValue().setIfAbsent(lockKey, "1", Duration.ofSeconds(5)));

        if (!gotLock) {
            sleepBriefly();                  // 2. losers back off and retry the cache read
            return getProduct(id);            // the winner will have populated it by then
        }

        try {
            String fromDb = loadFromDatabase(id); // 3. only the lock winner hits the DB
            int jitterSeconds = ThreadLocalRandom.current().nextInt(30); // jittered TTL
            redis.opsForValue().set(key, fromDb, Duration.ofMinutes(10).plusSeconds(jitterSeconds));
            return fromDb;
        } finally {
            redis.delete(lockKey);
        }
    }
}
💡

Two cheap mitigations, usually used together: request coalescing (a short lock so only one caller refills) and jittered TTLs (add a random few seconds so 10,000 keys cached at the same moment don't all expire in the same millisecond).

09
Advanced Distributed Locks
The SET key value NX EX seconds pattern from concept 8 generalizes into a full distributed lock: across multiple application instances (not just multiple threads in one JVM, which is what synchronized/ReentrantLock from the Java threading tutorial handle).
redis-cli
# NX = only set if the key does NOT already exist (the "acquire")
# EX 10 = auto-expire in 10s — a safety net if this process crashes
#         while holding the lock, so it's never held forever
127.0.0.1:6379> SET lock:order:42 "worker-A-uuid-1234" NX EX 10
OK                          # we got the lock

# a second worker tries the SAME lock while it's held:
127.0.0.1:6379> SET lock:order:42 "worker-B-uuid-5678" NX EX 10
(nil)                       # denied — someone else holds it

# releasing MUST check you still own it before deleting (a Lua script,
# run atomically, to avoid a race between the check and the delete) —
# otherwise worker A could delete a lock that worker B now legitimately holds
EVAL "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end" 1 lock:order:42 "worker-A-uuid-1234"
💡

This is "good enough" for most use cases (e.g. preventing two cron-job replicas from both running the same nightly batch). It is NOT bulletproof under clock drift or a process pausing past its TTL (a GC pause longer than the lock's expiry can let two holders overlap) — that's exactly the controversy behind the formal "Redlock" algorithm. For hard correctness (e.g. financial settlement), use a database-backed lock with real transactional guarantees instead.

10
Intermediate Pub/Sub
Redis can broadcast messages to anyone currently subscribed to a channel — the Observer pattern, network-wide instead of in-process — but it's fire-and-forget: nothing is stored, so a subscriber that's offline for even a second misses the message forever.
redis-cli
# terminal 1 — subscribe and wait (this call blocks)
127.0.0.1:6379> SUBSCRIBE room:general
Reading messages... (press Ctrl-C to quit)
1) "subscribe" 2) "room:general" 3) (integer) 1

# terminal 2 — publish a message to that channel
127.0.0.1:6379> PUBLISH room:general "sandeep joined the room"
(integer) 1          # 1 subscriber received it

# back in terminal 1, this appears instantly:
1) "message" 2) "room:general" 3) "sandeep joined the room"
💡

If you need "deliver this even if the consumer was briefly down" guarantees — durable, replayable, at-least-once delivery — Pub/Sub is the wrong tool. Reach for Redis Streams (concept 11) or a real broker like Kafka/RabbitMQ instead.

11
Advanced Redis Streams
Redis's answer to "I need Pub/Sub, but durable and replayable." A Stream is an append-only log — messages stay around after being read, consumers track their own position, and a consumer group lets several workers split the load without double-processing the same entry.
redis-cli
# producer appends entries — each gets an auto-generated ID like "1716220800000-0"
127.0.0.1:6379> XADD orders * orderId 1001 status "PLACED"
"1716220800000-0"

# a consumer GROUP lets multiple workers share the stream without overlap
XGROUP CREATE orders order-processors 0

# each worker calls XREADGROUP — Redis hands out entries round-robin,
# and remembers what's been delivered to this group
XREADGROUP GROUP order-processors worker-1 COUNT 1 STREAMS orders >
# 1) "1716220800000-0" 2) "orderId" "1001" "status" "PLACED"

# worker MUST acknowledge once it's done — unacked entries can be reclaimed
# by another worker if this one crashes (at-least-once delivery)
XACK orders order-processors 1716220800000-0
💡

Streams give you replay and consumer groups like Kafka, but Kafka still wins for huge multi-day retention, partition-level ordering guarantees at massive scale, and a richer ecosystem. Reach for Streams when you already run Redis and need "good enough" durable messaging without standing up a whole new system.

12
Intermediate Persistence — RDB vs AOF
"In-memory" doesn't have to mean "gone on restart." Redis offers two optional persistence mechanisms, and you can use either, both, or neither depending on whether you're caching (fine to lose everything) or storing real data (need durability).
redis.conf
# RDB — point-in-time SNAPSHOT, written on a schedule
save 900 1      # snapshot if >=1 key changed in the last 900s
save 60 10000  # snapshot if >=10000 keys changed in 60s
# compact single file, fast restarts, BUT you can lose everything
# written since the last snapshot if the process dies right before one

# AOF — every write command is appended to a log as it happens
appendonly yes
appendfsync everysec  # fsync to disk once per second (the safe default)
# much smaller data-loss window (at most ~1s), but a larger file on disk
# and slightly slower writes than RDB-only

# most production setups use BOTH — AOF for durability, RDB for fast
# restarts and easy backups (just copy the .rdb file)
💡

A pure cache in front of a real database (concept 5) can usually run with persistence fully OFF — if Redis restarts empty, cache-aside just refills it from the DB on the next request, no data lost forever. A session store or primary data store needs AOF.

13
Advanced Redis as a Session Store
If you DO need server-side session state (not every app gets to be stateless like the JWT tutorial's approach), storing sessions in Redis instead of in-process memory means any instance behind the load balancer can serve any user's request — the horizontal-scaling requirement from the high-TPS API design tutorial.
Java
import org.springframework.data.redis.core.RedisTemplate;
import org.springframework.stereotype.Service;
import java.time.Duration;
import java.util.Map;
import java.util.UUID;

@Service
public class SessionService {

    private final RedisTemplate<String, Object> redis;
    public SessionService(RedisTemplate<String, Object> redis) { this.redis = redis; }

    public String createSession(String userId) {
        String sessionId = UUID.randomUUID().toString();
        redis.opsForHash().putAll("session:" + sessionId,
            Map.of("userId", userId, "loginTime", System.currentTimeMillis()));
        redis.expire("session:" + sessionId, Duration.ofMinutes(30)); // idle timeout
        return sessionId; // this is what you'd put in a cookie
    }

    public String getUserId(String sessionId) {
        Object userId = redis.opsForHash().get("session:" + sessionId, "userId");
        if (userId == null) throw new SessionExpiredException(sessionId);
        redis.expire("session:" + sessionId, Duration.ofMinutes(30)); // sliding expiry
        return userId.toString();
    }
}
💡

Using a HASH per session (not a JSON string blob) means you can update one field — like lastActiveTime — with HSET without reading, deserializing, modifying, and rewriting the whole session object.

Advanced Rate Limiting
An in-process Semaphore (from the Java threading tutorial) only limits requests on one server. The moment you have multiple instances behind a load balancer, the counter needs to live somewhere shared — Redis is the standard place.
Java
import org.springframework.data.redis.core.RedisTemplate;
import org.springframework.stereotype.Service;
import java.time.Duration;

@Service
public class RateLimiter {

    private final RedisTemplate<String, String> redis;
    public RateLimiter(RedisTemplate<String, String> redis) { this.redis = redis; }

    // fixed-window limiter: max N requests per user per 60s window
    public boolean allow(String userId, int maxRequests) {
        String key = "ratelimit:" + userId + ":" + (System.currentTimeMillis() / 60_000);
        // the window number changes every 60s, so the key naturally rotates

        Long count = redis.opsForValue().increment(key); // atomic INCR, returns the new count
        if (count == 1L) {
            redis.expire(key, Duration.ofSeconds(60)); // only set TTL on the FIRST request in the window
        }
        return count <= maxRequests;
    }
}

// usage in a filter/interceptor:
if (!rateLimiter.allow(userId, 100)) {
    response.setStatus(429); // Too Many Requests
    return;
}
💡

Fixed-window is simple but has an edge case: a burst right at a window boundary (e.g. 100 requests at 0:59 and another 100 at 1:01) can let through 200 requests in 2 seconds. A sliding-window algorithm (tracked with a sorted set of timestamps, ZADD + ZREMRANGEBYSCORE) fixes this at the cost of more memory per user.

Advanced Redis Cluster Basics
A single Redis instance is bound by one machine's RAM and CPU. Redis Cluster shards data across multiple nodes automatically using 16,384 hash slots — every key is hashed to exactly one slot, and each node owns a range of slots.
redis-cli
# which slot does a key land in? CRC16(key) mod 16384
127.0.0.1:6379> CLUSTER KEYSLOT user:42
(integer) 6918

# a multi-key operation across DIFFERENT slots fails in cluster mode:
127.0.0.1:6379> MGET user:42 user:43
(error) CROSSSLOT Keys in request don't hash to the same slot

# FIX — hash tags: only the part inside {} is hashed, so you can force
# related keys onto the SAME slot/node on purpose
127.0.0.1:6379> CLUSTER KEYSLOT {user:42}:profile
(integer) 6918          # identical slot to user:42 — same node
127.0.0.1:6379> CLUSTER KEYSLOT {user:42}:orders
(integer) 6918          # also identical — now MGET across these two works
💡

A bad shard key (e.g. one giant tenant ID that 90% of your traffic shares) creates a hot node — one shard doing all the work while the rest sit idle. The same hotspotting risk already covered for SQL sharding in the high-TPS tutorial, just applied to Redis.

16
Advanced Senior Interview FAQ
Four questions that come up constantly in senior backend interviews — each one is really asking whether you can connect Redis concepts together, not just recite commands.
notes
// Q: "How would you use Redis to prevent a cache stampede?"
// A: Request coalescing — the first caller to miss takes a short SETNX
//    lock and refills the cache; everyone else briefly retries the read
//    instead of also hitting the DB (concept 8). Combine with jittered
//    TTLs so thousands of keys don't expire in the same millisecond.

// Q: "Pub/Sub vs a message queue like Kafka/RabbitMQ — what's the difference?"
// A: Pub/Sub is fire-and-forget with zero persistence — an offline
//    subscriber misses messages forever (concept 10). A real queue
//    persists messages and guarantees delivery even to a consumer
//    that's down when the message is sent. Redis Streams (concept 11)
//    close some of this gap with consumer groups + replay, but Kafka
//    still wins on retention scale and partition ordering guarantees.

// Q: "How does Redis achieve such high throughput despite being single-threaded?"
// A: Everything lives in RAM (no disk seeks on the hot path), data
//    structures are purpose-built for O(1)/O(log n) operations, and a
//    single thread means ZERO lock contention between commands — no
//    context switching or synchronization overhead. It trades away
//    multi-core parallelism for predictability; that's the deal.

// Q: "How would you implement a distributed lock with Redis, and what's risky about it?"
// A: SET key uniqueOwnerToken NX EX seconds to acquire; a Lua script that
//    checks ownership before DEL to release (concept 9). The risk: if a
//    process pauses (GC, network partition) longer than the lock's TTL,
//    a second process can acquire the "same" lock while the first still
//    thinks it holds it — this is exactly why naive Redis locks are
//    considered unsafe for hard correctness guarantees without something
//    like the more rigorous (and debated) Redlock algorithm.
💡
