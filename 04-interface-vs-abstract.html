🤔 Understanding the Why

An abstract method is a method with no body — just a signature ending in a semicolon: abstract void cookSignatureDish();. It's a promise, not an implementation: "every concrete subclass must supply this behaviour, but I'm not going to say how."

Because it has no body, it can't run. That's precisely why any class containing an abstract method must itself be declared abstract, and why it can never be instantiated — Java can't create an object that might have a method with nothing to execute. Every method you declare in an interface (other than default/static) is implicitly abstract for the exact same reason: interfaces exist to declare what must be done, never how.

Before Java 8, interfaces had zero implementation on purpose — a pure contract, nothing to inherit but a signature. That's what let a class implement five unrelated interfaces without any risk: there was no behaviour to collide over.

default methods were added in Java 8 purely as a backward-compatibility escape hatch — so library authors could add a new method (like forEach() to Collection) without breaking every class that already implemented that interface. They were never meant to carry core design logic the way abstract-class methods do.

And you can still see the old danger peeking through: if a class implements two interfaces that both define the same default method, Java refuses to compile until you manually resolve the conflict. Ordinary concrete methods (with real fields to work against) would make that collision the norm instead of the rare exception — so Java deliberately keeps interfaces state-free and restricts them to default/static only.

An interface is the public contract — every method on it exists so that outside code can call it through the type. A private or protected method on an interface would make no sense: nobody holding a reference to the interface could ever invoke it, which defeats the entire point of declaring it there. So Java makes every interface member public implicitly (Java 9 added true private methods, but only as internal helpers for default methods — never part of the contract itself).

An abstract class is a different animal — it's a partial implementation, not a pure contract. Subclasses interact with it through inheritance, not just through a public reference, so it legitimately needs the same access-control toolkit as any normal class: private helper methods hidden even from subclasses, protected members visible only inside the family, and public members for the real external contract.

You never call it yourself — the subclass calls it, via super(...), as the first line of its own constructor. Its job is to initialize the fields that live in the abstract class, before the subclass's own fields and logic are set up.

This falls straight out of the "shared state" answer above: the moment an abstract class is allowed to hold instance fields, something has to initialize them reliably, exactly once, before any subclass code runs. A constructor is that something. Interfaces skip this entirely because they hold zero fields — there's nothing to initialize, so there's nothing for a constructor to do. See the Constructor Deep Dive tab for the full call-chain walkthrough.

👉 Start with Interface. Switch to Abstract Class only when you need shared fields or a constructor.
🎤 Interview One-Liner

"Interface defines a contract for what a class can do; abstract class defines a partial implementation of what a class is. Use interface for capability and multiple inheritance; use abstract class when subclasses need shared state or construction logic."

Same Problem, Two Approaches

Scenario: You're building a payment system. See how each construct handles the same requirement.

Java Interface Approach 
// ✅ Interface — defines the CAPABILITY contract
public interface PaymentProcessor {

    // All methods are public + abstract by default
    void processPayment(double amount);
    void refund(double amount);
    boolean validateCard(String cardNumber);

    // Java 8+ default method (backward compat, not design intent)
    default void logTransaction(double amount) {
        System.out.println("Transaction: $" + amount);
    }
}

// A second, unrelated interface — to show multiple inheritance below
public interface Loggable {
    void logTransaction(double amount); // re-declared here on purpose — see note below
}

// A class can implement MULTIPLE interfaces
public class StripeProcessor implements PaymentProcessor, Loggable {

    @Override
    public void processPayment(double amount) {
        System.out.println("Stripe: processing $" + amount);
    }

    @Override
    public void refund(double amount) {
        System.out.println("Stripe: refunding $" + amount);
    }

    @Override
    public boolean validateCard(String cardNumber) {
        return cardNumber.length() == 16;
    }

    @Override
    public void logTransaction(double amount) {
        System.out.println("[Stripe audit log] $" + amount);
    }
}

// Usage — run it: this is a complete file
public class Main {
    public static void main(String[] args) {
        PaymentProcessor processor = new StripeProcessor();

        boolean valid = processor.validateCard("4242424242424242");
        System.out.println("Card valid? " + valid);   // true

        if (valid) processor.processPayment(99.99); // Stripe: processing $99.99
    }
}
Java Abstract Class Approach 
// ✅ Abstract Class — shared state + shared behaviour
public abstract class BasePaymentProcessor {

    // Shared FIELDS — this is the key advantage over interface
    protected String merchantId;
    protected String apiKey;
    private int retryCount = 3;

    // Constructor — sets up shared state
    public BasePaymentProcessor(String merchantId, String apiKey) {
        this.merchantId = merchantId;
        this.apiKey = apiKey;
    }

    // Shared CONCRETE method — same for every subclass
    public void logTransaction(double amount) {
        System.out.println("[Merchant: " + merchantId + "] $" + amount);
    }

    // Left blank — each provider defines their own
    public abstract void processPayment(double amount);
    public abstract void refund(double amount);
}

// Subclass extends — gets fields + logTransaction() for FREE
public class StripeProcessor extends BasePaymentProcessor {

    public StripeProcessor(String merchantId, String apiKey) {
        super(merchantId, apiKey); // 👈 calls abstract class constructor
    }

    @Override
    public void processPayment(double amount) {
        System.out.println("Stripe charging $" + amount);
    }

    @Override
    public void refund(double amount) {
        System.out.println("Stripe refunding $" + amount);
    }
}

// Usage — run it: this is a complete file
public class Main {
    public static void main(String[] args) {
        BasePaymentProcessor processor = new StripeProcessor("merchant-001", "sk_test_abc123");

        processor.processPayment(99.99);     // Stripe charging $99.99
        processor.logTransaction(99.99);     // [Merchant: merchant-001] $99.99 — inherited for FREE
    }
}
Java Best of Both Worlds 
// 💡 Real-world pattern: use BOTH together
// Interface for the public contract
public interface PaymentProcessor {
    void processPayment(double amount);
    void refund(double amount);
}

// Abstract class implements interface partially, adds shared state
public abstract class BasePaymentProcessor implements PaymentProcessor {
    protected String merchantId;

    public BasePaymentProcessor(String merchantId) {
        this.merchantId = merchantId;
    }

    public void refund(double amount) {  // shared refund logic
        System.out.println("Refunding $" + amount + " to merchant: " + merchantId);
    }
    // processPayment still abstract — each provider must define it
}

// Concrete class — just fills in the gap
public class StripeProcessor extends BasePaymentProcessor {
    public StripeProcessor(String id) { super(id); }

    @Override
    public void processPayment(double amount) {
        System.out.println("Stripe: $" + amount);
    }
}

// Usage — run it: this is a complete file
public class Main {
    public static void main(String[] args) {
        PaymentProcessor processor = new StripeProcessor("merchant-001");

        processor.processPayment(75.00); // Stripe: $75.0 — own implementation
        processor.refund(20.00);       // Refunding $20.0 to merchant: merchant-001 — inherited
    }
}

Constructor in Abstract Class

🤔 "You can't instantiate it — so why have a constructor?"

The constructor isn't called by you — it's called by the subclass via super(). It exists to initialize the shared fields that live in the abstract class.

Java Abstract Class with Constructor 
abstract class RestaurantChef {

    // Fields live here — subclasses inherit them
    String kitchenName;
    int yearsExperience;

    // Constructor — initializes shared fields
    RestaurantChef(String kitchenName, int yearsExperience) {
        this.kitchenName = kitchenName;
        this.yearsExperience = yearsExperience;
        System.out.println("Chef initialized for: " + kitchenName);
    }

    // Shared concrete method
    void doMorningPrep() {
        System.out.println(kitchenName + ": sharpening knives...");
    }

    // Must be implemented by subclass
    abstract void cookSignatureDish();
}

class TorontoChef extends RestaurantChef {

    TorontoChef(String name, int exp) {
        super(name, exp);  // 👈 MUST call parent constructor first
    }

    @Override
    void cookSignatureDish() {
        System.out.println(kitchenName + ": butter chicken poutine! 🍛");
    }
}

// Usage — run it: this is a complete file
public class Main {
    public static void main(String[] args) {
        TorontoChef chef = new TorontoChef("Downtown Kitchen", 5);
        chef.doMorningPrep();      // inherited — free!
        chef.cookSignatureDish();  // own implementation
    }
}

// Output:
// Chef initialized for: Downtown Kitchen   ← runs FIRST, before TorontoChef's body
// Downtown Kitchen: sharpening knives...
// Downtown Kitchen: butter chicken poutine! 🍛

🏗️ The Mental Model

When you build a TorontoChef, Java runs up the chain first — it initializes the parent's fields before the child even starts. The abstract class constructor is the foundation pour before the building goes up.

❌ Interface has no constructor — why?

Because interfaces have no instance fields to initialize. A constructor's job is to set up state. No state = no constructor needed. This is the clearest way to remember the difference between the two.

Java Multiple Constructors — Overloading 
abstract class BaseService {
    String serviceName;
    String version;

    // Constructor 1 — minimal
    BaseService(String serviceName) {
        this(serviceName, "1.0");  // delegates to Constructor 2
    }

    // Constructor 2 — full
    BaseService(String serviceName, String version) {
        this.serviceName = serviceName;
        this.version = version;
    }

    abstract void start();
}

class PaymentService extends BaseService {
    PaymentService() {
        super("PaymentService", "2.1");  // picks which parent constructor
    }

    @Override
    void start() {
        System.out.println(serviceName + " v" + version + " starting...");
    }
}

// Usage — run it: this is a complete file
public class Main {
    public static void main(String[] args) {
        new PaymentService().start(); // PaymentService v2.1 starting...
    }
}

Click a scenario — guess which to use

🔌
Serializable marker
You want to mark a class as "this object can be saved to a file." No methods needed.
→ Interface — pure capability marker, no state needed.
🗄️
Base repository
All your repos share a database connection URL and a common findById() implementation.
→ Abstract Class — needs shared fields (dbUrl) and shared method (findById).
⚖️
Comparable sorting
You want your Employee class to be sortable by salary.
→ Interface — Comparable<T> is a capability contract. Implements perfectly.
💳
Payment processors
Stripe, PayPal, Razorpay all share merchantId, apiKey, and a logTransaction() method.
→ Abstract Class — shared state (fields) + shared concrete method = abstract class.
🦆
Duck typing — Flyable
Birds, planes, and superheroes can all fly — but they're completely different things.
→ Interface — unrelated classes sharing a capability. Multiple impl works great.
🎮
Game characters
Warrior, Mage, Archer all have health, mana, and a shared takeDamage() method. Each has a unique attack().
→ Abstract Class — shared fields (health, mana) + partial implementation pattern.
📦
Spring @Repository
You want to define a contract that any data-access layer class must honour.
→ Interface — Spring's own JpaRepository is an interface for exactly this reason.
📧
Notification sender
Email, SMS, Push share an app name, sender ID, and a format() helper. Each has its own send() logic.
→ Abstract Class — shared fields + shared helper method + one abstract method.

What should I use?

Answer a few questions about your design:
1. Do your classes need to share instance variables (fields)?
2. Do you need a constructor to initialize shared setup?
3. Will unrelated classes need to implement this?
4. Does a class need to be "multiple things" at once?
